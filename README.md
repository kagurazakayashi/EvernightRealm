# EvernightRealm

> Host your own private world for your group — immersive activities, characters and virtual assets on a machine you own.

[English](./README.md) · [简体中文](./README.zh-CN.md) · [繁體中文（台灣）](./README.zh-TW.md) · [日本語](./README.ja-JP.md)

## What is EvernightRealm?

EvernightRealm is a self-hosted, offline-first platform for a small group of players: run immersive activities together, play characters, and trade virtual assets — all on a local network, with no internet, cloud accounts or telemetry.

## Features (under development)

- **Immersive activities** — organize scenes, phases and events for your group
- **Characters & identities** — player, NPC and admin roles in one private world
- **Virtual assets** — items with real ownership and auditable trades
- **Private chat** — messages stay on your own server
- **Offline-first** — everything runs on a machine you own; no cloud required

## Current status

EvernightRealm is under active development and no stable release is available yet. The server can already be built as a **single executable**: one port serves both the web interface (so far the app shell — switchable UI language and a server connectivity probe, with business features still in development) and the API endpoints, so a browser pointed at that address is all you need — no separate static hosting.

The server also ships a maintenance command that produces a **consistent backup package**: a single-file database snapshot — taken while the server keeps running, and not a copy of the live write-ahead-log file — together with the config file and the media, document and upload directories, each file recorded with its size and SHA-256 in a manifest. A matching `restore` command turns such a package back into a **fresh, empty data directory**: it re-verifies every file against the manifest, reads the snapshot's database facts and compares them with the manifest both before and after the files land, refuses to overwrite any existing directory (back up that directory yourself first), refuses a database schema newer than the running executable, and records the restore itself as a server-side audit entry. A backup package still cannot be encrypted, and old packages are not pruned automatically.

A one-time Root initialization is available as a **local command only**:

    evernight-server init-root --password-stdin --data-dir <data directory>

It reads the password from stdin (two lines: the password and its confirmation), stores an Argon2id hash in the data directory's `config.yaml`, and prints nothing secret — no plaintext, no default password is ever generated or shown. Because handing out the server's highest privilege is authorized by being able to run a command on the server host, this step opens no HTTP endpoint and no listening socket at all; CORS, client-reported addresses or hiding a button are not authorization. Initialization is refused while the service holds the single-writer instance lock, while `ER_SECURITY_ROOT_PASSWORD_HASH` overrides the file, or while the audit table does not exist yet, and it can never run a second time — the Root password is rotated through the authenticated in-service change flow (`POST /auth/password/change` after signing in as Root); only a genuinely lost password justifies the local recovery command below. A read-only `evernight-server root-status` reports whether Root exists without creating or changing anything, and reports only that much: never a config path, hash or bootstrap secret. Success and refusal both land in the Root audit table without any password.

Recovering a lost Root password is likewise a **local command only**:

    evernight-server recover-root --password-stdin --confirm --data-dir <data directory>

It also reads the new password from stdin (two lines, password and confirmation) and never accepts a password value on the command line, and it requires the service to be stopped: a running server holds the credential in memory, so editing the config file would not make it re-read — the result would be "the terminal said it succeeded while the old password still works", a state far harder to diagnose than a refusal. Recovery neither asks for nor verifies the old password: being able to run this command on the host and to read that config file is the entire authorization for the action, which is why there is also no backdoor password, no downloadable recovery file and no HTTP endpoint. On success the credential in the config file is overwritten with the Argon2id encoding of the new password, every Root session is revoked inside the same database transaction (the next request from those devices is rejected), and a `server.root_recover` audit entry is written; ordinary account sessions are not touched at all. If that transaction cannot be committed, the config file is switched back to the credential it held and the command reports failure, leaving the usable state exactly as it was (a double fault where even the rollback fails is recorded as an Error in the persistent log file and explicitly asks for a manual follow-up entry). `--confirm` must be given explicitly, because the price of an overwrite is that the old password dies permanently and every Root device is signed out. When the config file has no credential yet the command refuses and points at `init-root`; an existing value that is too corrupt to verify can still be recovered — that is precisely the shape `init-root` refuses, and the two write paths each have exactly one success shape.

A first-run screen has to state honestly whether the server is not initialized yet, so the server also answers a read-only `GET /root/init-status`: three booleans only — whether the config file exists, whether a Root credential is present, and whether the environment override is set. It returns no path, no length, no fragment of any credential, and it writes neither to the database nor to the audit log. It says whether, never how to change: initializing Root is still reachable only through `init-root` run on the server host itself (overwriting a lost credential is the `recover-root` command above, and neither one is reachable over the network).

## Signing in and managing your own account

The identity stage is implemented and usable today: signing in, reading the current session, signing out, managing your own devices, changing your own password, Root creating accounts and managing the administrator directory, including disabling and restoring an administrator's sign-in, resetting an administrator's sign-in credential, and soft-deleting an administrator (next section), Root setting the server's account-creation policy (the section after that), and administrators creating ordinary accounts, browsing the ordinary-account directory, reading and maintaining a single record, suspending or restoring an ordinary account's sign-in under that policy, and resetting an ordinary account's sign-in password (the creation part is the section above; the directory, profile, sign-in and credential parts are the four sections that follow). Two limits are stated just as plainly. First, accounts come into existence through exactly these entries: the Root credential itself comes from `init-root` on the server host, server administrators come from `POST /root/admins`, and ordinary accounts come either from `POST /admin/accounts` — the last one only while `admin_create_standard` is open and only for an authenticated server-level administrator — or from anonymous self-registration at `POST /auth/register`, which is offered only while `sign_up_open` is true, hands back a standard account whose password the person chose themselves, issues no session of its own, and can never mint an administrator. Self-registration is implemented now, in all three of its shipped modes — open, approval, and the invite-code mode (`POST /auth/register` redeems a valid code into an active ordinary account, and `invite_code_required` from `GET /auth/capabilities` tells the shared form when to reveal the field). Guest entry is implemented too, as the deliberately restricted path it is: `POST /auth/guest` creates a **server-named** `account_type` of `guest` and issues a session in the same transaction, while `guest_open` from the same anonymous endpoint tells the pre-login screen whether to show that door at all. The account is named by the server (`guest_<uuid>`), never by the request; a nickname is display information only — it may duplicate, it is not a credential, and there is no path that trades it for a session. Guests carry no server-level grant, so every administrator and Root endpoint answers them with 2011 and they cannot enumerate the site's accounts. The session itself is ordinary: same expiry, idle line, revocation and device-slot rules as any other account, and signing out or losing it ends the visit. Second limit for this path: nothing is created until a person presses the button — loading, refreshing and reconnecting never write, and there is no scheduled job purging old guest rows. Second, the server terminates no TLS itself — the default listen address is plain HTTP on `127.0.0.1:5206`, and the session cookie is marked `Secure` (with HSTS sent) only when a request actually arrives over TLS, that is, when you put your own TLS-terminating reverse proxy in front of it. There is no bundled certificate handling, and HTTPS is a deployment choice outside this program.

The identity endpoints carry no version prefix — there is no `/api/v1`:

- `POST /auth/root/login` (Root password only) and `POST /auth/login` (login name and password). Every success issues a brand-new session and replaces any previous cookie, so an old cookie is never carried on.
- `GET /auth/session`, `POST /auth/logout` and `POST /auth/session/rotate` — read the current session, revoke exactly this session (idempotent), or rotate this session's secret.
- `GET /auth/devices` and `POST /auth/devices/revoke` — list and revoke the sessions of the signed-in subject only; no request can name another account's device.
- `POST /auth/password/change` — the current password must be handed over in the request itself; on success every session of that subject, this device included, is revoked.

On the browser path the session secret lives in an `HttpOnly` cookie; native clients carry it as a bearer secret read from the response header. Sign-in is throttled per source address and target after repeated failures (HTTP 429 with `Retry-After`), and the Root entry is covered too; a throttled attempt does not reveal which account was hit. With `device_policy` set to `single` or `limited`, older sessions are dropped or a new sign-in is refused once the cap is reached. Accounts flagged "must change password at first sign-in" are served only the session read, sign-out and the change-password flow; every other protected endpoint answers 2010 until the change is done.

Two operational boundaries are unchanged: backup and restore stay `evernight-server` subcommands with no HTTP entry point, and audit records are written by the service layer only — there is still no audit query endpoint or web console. The run log is rotated by calendar day and is not deleted automatically by default (`retention_days=0`): keeping the log from growing without bound is the operator's job, and nothing in the server caps the total volume over time.

## Root manages the administrator directory

A Root session is how the first human operators get in. `POST /root/admins` creates one with `login_name`, `display_name` and `password`; `GET /root/admins` is the paginated administrator directory (`page`, `page_size` up to 100, `status` filtered to `all`/`active`/`disabled`/`deleted`, ordered newest grant first, answering `page`, `page_size` and `total`); `GET /root/admins/{account_id}` reads one record; `PUT /root/admins/{account_id}` edits it; `DELETE /root/admins/{account_id}` soft-deletes that account and carries no request body at all — any field is refused with 1004; and `PUT /root/admins/{account_id}/status` disables or restores that account's sign-in, its body carrying only `status` and `expected_status`; `PUT /root/admins/{account_id}/password` resets that account's sign-in password, its body carrying only `password`. What makes the new account an administrator is the endpoint, not the body: there is no `role`, `account_type` or `subject_kind` field to fill, and an unexpected field is refused with 1004. The authorization input is the session that resolved to Root, so an ordinary account and an administrator's own session both get 2011 (403) — an administrator cannot create a peer, manage a peer, or promote themselves, and signing in again changes nothing about that. The directory lists administrator accounts only; the configured Root is not one of its rows and never becomes an editable record.

The initial password is handed over by Root and is single-use. It is hashed by the same Argon2id service that every other credential uses, the account is stored with `must_change_password` set, the server never echoes the password back in any response, and there is no default password anywhere. That person's first sign-in therefore gets a session that is allowed only the session read, sign-out and the change-password flow — every other protected endpoint answers 2010 until the change is done — and completing the change signs every device of that account out. These are the rules that already existed for any account; this step is where the flag now comes from.

Login name uniqueness is the same normalized key the login path uses (NFKC plus full case folding), enforced by the unique index on the account table: a name that is already taken answers 2012 and creates nothing, so a double submit or a retry after a lost response cannot produce a second account, and that refusal echoes neither the existing account's data nor any credential. Creating the account, granting `server_admin` and appending the `admin.create` record to the Root audit happen inside one transaction — a failure anywhere leaves no half-created administrator and no unrecorded privilege change — and the audit entry carries the identity fields, never the password or its hash.

The edit whitelist is one field: `display_name`, saved together with `expected_display_name` — the value the edit is based on. Hidden fields (status, credential, the first-change flag, account type) are not editable here, and the update statement touches only that one column, so a plain profile save cannot overwrite them even by accident. If the stored value changed after the record was opened, the whole edit is refused with 2013 (409) and nothing is written — the same last-writer-protection the password rotation uses. A malformed or missing account id, an account outside the directory, and a genuinely missing account all answer the same 1001, so the endpoint is not an enumeration probe. Responses carry display facts only — never a password hash, session secret, recovery code or configuration — and a successful Root edit appends one `admin.profile_update` audit record with the before and after display name; refused edits write nothing.

Disabling and restoring sign-in ride a separate single-field endpoint. Disabling blocks new sign-ins (answered indistinguishably from other sign-in failures - the server never says "this account is locked"), revokes the account's existing sessions in the same database transaction, and appends one `admin.disable` Root audit record carrying the status pair, the `disabled_at` pair and `revoked_sessions`; whether a principal is still usable is re-read from the database on every request, so a disabled administrator's live sessions cannot resolve to a trusted subject at any protected entry. Restoring (`admin.enable`) brings back only the ability to sign in again: sessions revoked at disable time stay dead, a pending `must_change_password` stays required, and neither Root nor an administrator acting on a peer is ever a valid target. A status write is one compare-and-set on the status the caller saw - a stale basis or a repeated operation is refused with 2014 (409) and does nothing at all: no status write, no revocation, no audit. Completed work never reverts; only work attempted after the disable takes effect is refused. The update statements touch only `status` and `disabled_at`, so "disabling quietly resets a credential or a flag" has no place to happen, and disabled administrators stay in the directory - their grant rows are kept - which is exactly what makes them restorable.

Resetting a sign-in credential is the third single-field sub-resource endpoint. `PUT /root/admins/{account_id}/password` carries one field only - the temporary password Root hands over personally, under the same approved delivery scheme as provisioning: the server generates no password, no response ever echoes it, and it appears in the request body exactly once; logs, audits and responses contain no credential material, and the offline hand-off lives outside the protocol. One successful reset lands three facts in a single transaction: the old password dies immediately, every session under the account is revoked (`revoked_sessions` is the authoritative count), and the account must change its password at next sign-in - the very same 2010 gate that guards self-service changes. Resetting someone else is deliberately a different use case from changing one's own password: the self-service flow authenticates by presenting the current password and clears the obligation, while a Root reset exists precisely for the case where the current password is unavailable - and its success re-arms the obligation instead. A reset therefore carries no compare-and-set basis: any such anchor would verify something other than what it claims. Repeated submissions are not stale-basis refusals like 2013/2014 - each one is a complete, effective reset, each leaving its own `admin.password_reset` audit entry (the obligation-flag pair and the revocation count, never credentials), so clients must never re-send automatically when an outcome is unclear. What a reset does not change is equally real: the update statement never touches `status` or `disabled_at` - resetting a disabled target succeeds, the account stays disabled and new sign-ins stay refused (indistinguishable from other sign-in failures); restoring sign-in remains the job of the `/status` endpoint. A reset is not de-authorizing, renaming, or deleting either; grant rows stay intact. Malformed identifiers, ghost identifiers, ungranted accounts and physically deleted targets all answer 1001 - a soft-deleted account answers 2015 instead, because there the record still exists and the refusal is about its state; non-Root subjects get 2011, and a password failing the credential shape gate gets 1004 naming the `password` field.

Deleting an administrator is a state, not a purge. `DELETE /root/admins/{account_id}` has no body and lands three facts in one transaction: sign-in stops, every session under the account is revoked (the response reports `revoked_sessions`), and one `admin.delete` Root audit record is appended carrying the identity snapshot a later reader needs - login name, the display name as it was and as it becomes, the status pair, the `deleted_at` pair, the revocation count - and no credential material. The account row itself stays: its identifier, its login-name key, its grant rows, its session rows and its audit rows all keep resolving to the same stable account, so historical operations never end up pointing at nothing and are never quietly reattributed to Root. That is also why physical database purging is not implemented here, and why it cannot be done casually: a referenced row cannot be removed at all. Deletion is terminal. There is no restore endpoint - `PUT /status` refuses, because disabled and deleted are different states and the existing restore path must not resurrect a deleted account - and editing, resetting the credential or deleting an already-deleted target each answer 2015 (409), the machine code that means "this account exists but is deleted". A database trigger makes the deleted row immutable in addition, so no future write path can silently bring it back. One display projection is anonymized on the way out: `display_name` is rewritten to a placeholder of the form `DEL_<UTC date>_<former name>` within the same length budget, so a live record no longer presents the old name as current. Append-only history is deliberately left alone - the audit entries written before the deletion keep the name they recorded, which is exactly what makes those old operations explainable. The login name stays normalized-keyed and therefore stays taken: a deleted account cannot be re-registered under the same name. Deleted administrators stay visible in the directory (`status=deleted`, with `deleted_at` in the directory and single-record responses) and their detail is read-only. Bulk deletion is not offered, no reason text is carried in the request, and the configured Root credential is not a directory row, so it can never be a delete target.

Two response fields were added, both following the append-only evolution rule: the sign-in and current-session responses now include `roles`, the grants the server read for that principal (absent when there are none), and clients use it to decide which entries to load. It authorizes nothing on its own — every endpoint re-checks the trusted principal on every request.


For a deployment that lets a whitelisted cross-origin browser call these endpoints, `cors.allowed_methods` must also list `PUT` alongside `POST`, and `DELETE` for the delete endpoint — the shipped default stays `GET`/`HEAD`/`OPTIONS`, the origin whitelist remains a config choice, and nothing here relaxes it.

## Server account-creation policy

Three values say what this deployment intends about new ordinary sign-ins: `admin_create_standard` (whether administrators may create ordinary accounts), `self_register_mode` (`closed`, `open`, `approval` or `invite`, all four now shipped: open creates an active account, approval lands a pending application, invite redeems a valid code into an active ordinary account) and `guest_enabled` (whether temporary guest accounts may be created). `GET /root/account-policy` reads them, `PUT /root/account-policy` writes all three as one document. Only Root may read or write it: an administrator's own session gets 2011, no session gets 2002, and a cross-site origin gets 2005 before the database is touched — "may administrators create ordinary accounts" is a value this endpoint sets, while "may an administrator change server policy" is not a value at all. The three fields are independent, and all three must be present: an omitted switch is refused with 1004 naming that field, because silence is a dropped form field, not a decision to close an entry.

There is deliberately no compare-and-set basis here, because this is one document that only Root writes: a repeated save is another confirmation of the same state, and each one appends a single `server.account_policy_update` Root audit record carrying the before/after pair of every field that actually moved (nothing else — no account identifier, no credential material). Values are persisted in a one-row table created by migration `0008`, so a saved change is effective for the next request immediately and reads back the same after a restart with no restart action; nothing is written back to `config.yaml`, and the row can be neither deleted nor duplicated.

A policy value is not a capability. The composition is still computed as "the policy says open" **and** "that path exists" — it just so happens that every path is now shipped, so the three booleans currently track the switches themselves: `GET /auth/capabilities` is anonymous, `no-store`, and returns exactly three booleans — `sign_up_open`, `invite_code_required` and `guest_open`. `guest_open` is the pre-login screen's only hint about the guest door and never the admission decision: `internal/guestacct` re-reads the policy inside its own write transaction, so a stale or bypassed `false` cannot let anybody in either. `invite_code_required` lights up only when the effective mode is `invite`, so the shared sign-up form knows to reveal an invite-code field; it is a display hint, never the mode name and never the admission decision (the write-time transaction re-reads the policy). It reveals no mode name, no `updated_at`, no administrator switch, no account list and no limit values. All four mode names — `closed`, `open`, `approval` and `invite` — are now writable; writing a still-unshipped mode would be refused with 2016 (400), the sentence that means "recognised name, flow not shipped", which is deliberately different from 1004's "that value does not exist", though no approved mode is in that state at this version. No unrecognised value is ever rounded down to `closed` or up to the loosest mode. When a later step ships one of those flows, it registers its own capability and re-reads the effective policy inside its own transaction instead of caching a value it read earlier.

The three switches do not reach Root itself: creating administrators (`POST /root/admins`) and the host-local credential commands (`init-root`, `recover-root`) never consult this table, so closing `admin_create_standard` cannot leave a server with neither an administrator nor a way back in. As with the other write endpoints, a cross-origin deployment has to list `PUT` in `cors.allowed_methods` for this endpoint; the shipped default still allows only `GET`, `HEAD` and `OPTIONS`.

## Administrator-created ordinary accounts

An authenticated server-level administrator creates one ordinary account per request with `POST /admin/accounts`. The body carries exactly `login_name`, `display_name` and a one-time `password`: there is no field for a role, an account type, an approval state or an activity, because the endpoint — not the request — decides what kind of subject appears: `standard`, active, no server-level grant, and `must_change_password` on, the same one-time-credential policy Root's own provisioning uses.

Whether the path is open is judged at write time: the creating transaction re-reads the policy row and refuses with 2017 (403) while `admin_create_standard` is closed — Root included, this switch exempts nobody — while a principal without server-level permission gets 2011 and a taken login name (after normalization) gets 2012. There is deliberately no switch-preview endpoint for administrators: the policy's current values stay readable only by Root, and the authoritative answer is always the one given inside the creating transaction. The new account then uses the system through the same paths as any other account: first sign-in must change the password (every other protected entry answers 2010 until then). A created account is only an account — no activity profile, no assets, no roster seat — and interfaces say so instead of pretending an activity lobby exists.

A successful creation appends one `account.create_standard` record in the Root audit domain with the real operating administrator as the actor (an account-level identity, not Root and not the system): a server-level action does not borrow an `activity_id` it does not have, and the row structurally cannot carry one. No audit query endpoint is added by this: an administrator who creates accounts still cannot read the Root audit domain, which remains Root's own. As with the other write endpoints, a cross-origin deployment has to list `POST` in `cors.allowed_methods`; the shipped default still allows only `GET`, `HEAD` and `OPTIONS`.


## Administrators maintain the ordinary-account directory

An authenticated server-level administrator can do more than create accounts: `GET /admin/accounts` is a paginated directory (`page`, `page_size` capped at 100, `status` filtered by `all`／`active`／`disabled`, `type` by `all`／`standard`／`guest`, and `q` as a substring match on the login or display name), ordered newest-created first and echoing `page`, `page_size` and `total`; `GET /admin/accounts/{account_id}` reads one record; `PUT /admin/accounts/{account_id}` edits it, and the body carries exactly two fields - `display_name` and the `expected_display_name` it is based on.

The scope of this directory is a boundary, not a preference. It lists accounts that **hold no server-level grant at all** and have not entered the deleted terminal state - ordinary and guest accounts both, with `account_type` stating where each one comes from. People holding `server_admin` (including the operator calling this endpoint) belong to Root's administrator directory, and the configured Root is not a row in `accounts` at all, so structurally it can never appear. The two directories are therefore disjoint: nobody "helpfully" lists the other's rows. A principal without server-level administration gets 2011 (403) for the directory, the detail and the edit, and an anonymous caller gets 2002 - ordinary and guest accounts cannot enumerate the site's accounts, and that holds because of the server-side decision, not because a button is hidden. A malformed identifier, a missing account, an account that is an administrator, and an account that has been deleted all answer the same 1001, so the endpoint is not a probe for "is this person an administrator".

Editing the display name keeps the rules already settled for the identity stage and for Root's side: the login name is an immutable identity anchor from creation onwards (the interface says so too), and credentials, roles and security state (the password, the first-change flag, the account type, and status - which has its own sub-resource) are not on that profile form at all - an extra hidden field in the body is a 1004, and those columns never appear in the UPDATE statement. Concurrency uses the same compare-and-set shape: when the value the edit was based on is no longer what is stored, nothing is written and the answer is 2013 (409), with the same disposition as on Root's side (re-read the server's current value, then decide), which is why this step adds no machine code at all. A refused edit leaves no audit record; a successful one appends `account.profile_update` in the Root audit domain with the real operating administrator as the actor (an account-level identity, not Root and not system) and only the before and after display name. As before, no audit query endpoint is added.

Responses carry display facts only - never a plaintext password, an Argon2id hash, session material or the internal normalisation key of a login name. A single record also shows no activities, assets or messages: those modules do not exist yet and nothing here is padded with an empty array or a zero. Deleting an ordinary account and changing roles are also not open yet - today those two capabilities exist only for Root, on administrators; suspending and restoring an ordinary account's sign-in is the next section, and resetting its credential is the one after that. A cross-origin browser deployment has to list `GET` in `cors.allowed_methods` to read the directory (the shipped default already allows `GET`, `HEAD` and `OPTIONS`) and `PUT` as well to save a profile; the shipped default is not relaxed for this.

## Administrators suspend and restore an ordinary account's sign-in

`PUT /admin/accounts/{account_id}/status` suspends or restores one ordinary account's sign-in, and the body carries exactly two fields - `status` (`active` or `disabled`) and the `expected_status` it is based on. What this changes is the account's ability to sign in to the whole server, not a player's restriction inside one activity: after a suspension new sign-ins are refused and every current session on every device is revoked, so those people have to sign in again. Muting inside an activity, freezing transfers and faction restrictions are not this endpoint, and are not implemented.

Suspension reuses the same underlying mechanism already approved on Root's side (the status write and the session revocation land in one transaction), while the target's eligibility is decided independently: this path only accepts accounts that hold no server-level grant at all and have not entered the deleted terminal state. A plain administrator therefore cannot suspend a fellow administrator, and cannot suspend themselves - those three inputs answer the same 1001 as an unknown account, and the configured Root is not a row in `accounts` at all. The authorization level stays server-level administration (anything below it gets 2011, anonymous gets 2002): this feature does not promote any activity-scoped role into a server-level suspension, and it adds no new role.

Restoring brings back exactly one thing - the ability to sign in again. Sessions revoked while the account was suspended stay revoked and never come back (revocation is an irreversible fact and the restore path touches no session at all), an unfinished first password change is still owed (signing in again is still gated by 2010), and no other restriction on the account is lifted. Suspended accounts that have been deleted cannot be restored this way either. Several limits on one account were never a single `active` boolean: `status` answers whether one can sign in, `must_change_password` answers whether a password change is owed first, `account_type` states where the account comes from, and deletion is a terminal state - each question has its own column and its own path.

Concurrency and repeats use the same compare-and-set shape: when the `expected_status` is no longer what is stored, nothing happens - no status write, no revoked session, no audit record - and the answer is 2014 (409). That sentence is word-for-word what Root's side already says, and so is the disposition: re-read the target's current state and confirm again, rather than pressing the button a second time, which is why this feature adds no machine code. SQLite's single writer serialises concurrent attempts, so a write that already committed is a fact that does not roll backwards, while any new operation after the suspension takes effect is refused at the session-resolution boundary. A successful change appends `account.disable` or `account.enable` in the Root audit domain with the real operating administrator as the actor (an account-level identity, not Root and not system), carrying the before and after status, the before and after suspension timestamp and the number of sessions revoked; a refused change leaves no audit record, and no audit query endpoint is added here either.

Responses echo the server's value after the change together with `revoked_sessions`, and never a password, a credential hash or session material. Guest accounts take the same path; since a guest has no credential path that can sign in today, suspending one usually revokes nothing (the count is 0) while the status write is still a real fact. The interface states the target, the blast radius and "this is not a deletion" in a confirmation dialog before submitting, and re-reads the directory and the record afterwards instead of painting its own result. A cross-origin deployment has to list `PUT` in `cors.allowed_methods` for this write; the shipped default is not relaxed for it.

## Administrators reset an ordinary account's credential

`PUT /admin/accounts/{account_id}/password` replaces one ordinary account's sign-in password with the one-time password the administrator hands over themselves; the body carries exactly one field, `password`. It reuses the pieces Root's administrator credential reset already established - the same password-deriving implementation, the same forced hash replacement, the same targeted session revocation - while the operator, the target type and the managed scope are each checked on their own: the authorization level is still server administration (without it 2011, anonymous 2002), and the target range is still that directory of accounts carrying no server-level grant and no deletion terminal state. An ordinary administrator therefore cannot reset a peer, cannot reset themselves, and cannot reach the configured Root - all of those collapse into 1001, the same answer as "nobody by that name", because this path does not report which half is missing.

One successful reset lands three facts together, and any one of them alone would be a half measure: the current password dies immediately (the whole hash column is replaced, so the old plaintext never verifies again), every session that account holds is revoked inside the same transaction (`revoked_sessions` is exactly that count), and the first-change obligation is armed again (his next sign-in is still gated by 2010 until he changes it himself). Delivery follows the approved shape: the operator hands the password over personally, the server generates nothing, echoes nothing in any response and knows no default password, and the offline channel that carries it lives outside the protocol. On screen that string only exists between the field and the request: it is cleared before the request goes out and appears nowhere afterwards, and it never reaches logs, audit rows, readable preferences or an auto-copied clipboard.

What a reset does not change is stated just as plainly. A suspension stays exactly as it was - that UPDATE carries neither `status` nor `disabled_at`, so the account still cannot sign in afterwards and restoring sign-in remains the `/status` path's job. A deleted account is not resurrected by a reset. Someone who still owes the first change still owes it. Approval-queued applications are outside this directory's scope, so a reset can never reach a person who has not been waved through yet: aiming at a `pending` or `rejected` account id gives the same 1001 as an unknown id, and no administrator can wave somebody through along this path either — approval is not a side effect of any of these three write entries.

A guest account (`account_type` of `guest`) is not this path's business: its password column is frozen to NULL in the schema, so writing one for a guest would quietly promote that guest into an ordinary account, and that call belongs to the dedicated guest-upgrade path (`PUT /admin/accounts/{account_id}/upgrade`), not to a password-reset column. Guests therefore get this feature's one new machine code, 2018 (403). That sentence is not 1004's "fix how you wrote the password", not 1001's "pick another target" and not 2011's "use a different identity": the permissions are there, the wording is fine, and what has to happen is to walk the explicit upgrade path - while the directory lists guests by definition, so "he is not in this book" would be a lie.

Concurrency and repeats: this endpoint deliberately carries no anchor value, because the operator has no honest anchor such as "the current hash", and any substitute would verify something other than what it claims. SQLite's single writer serializes every reset; each success is a whole "new hash + revocations + audit", and a repeated submission honestly performs another reset (revoking whatever sessions were minted in between, writing another audit row) rather than the 2014 "stale anchor refused". The interface therefore never auto-resends when the outcome is unclear - pressing that button again is not a retry. A successful reset appends one `account.password_reset` row in the Root scope, recorded with the real administrator who issued it (an account-level actor, neither Root nor system), carrying the before and after values of the first-change flag and the number of sessions revoked; refused resets write no audit, and this feature adds no audit query endpoint.

The response shows the server's post-reset values and `revoked_sessions`, and never any shadow of the password - not even a prefix or a length. A cross-origin deployment has to list `PUT` in `cors.allowed_methods` to save a credential; the shipped default (`GET`, `HEAD`, `OPTIONS`) is not relaxed for this. Email recovery, a network path for Root's own restore, and a separate one-time recovery-code system are not here and do not exist because of this step.

## Approval-queued sign-ups and the applicant's own status lookup

With `self_register_mode` set to `approval`, `POST /auth/register` stops creating an account that can sign in and starts filing an application instead. The same three whitelisted fields, the same password the person chose themselves, the same standard account with no server-level grant — the only difference is the state it lands in: `pending` rather than `active`, and the stable account identifier exists from the first submission, because under the unified account model an applicant does not become a different person when somebody finally approves them. The login name is occupied from that moment on, and `must_change_password` stays off: what an applicant is waiting for is an approval, not a password.

Waiting is not a half-usable state, and that is not a matter of wording. Sign-in checks whether the account is `active`, and a `pending` (or `rejected`) row fails that test exactly like a wrong password does — same 2001, no signal about which names exist. The session store refuses to issue or resolve a principal for any non-active account, so there is no cookie, no bearer secret and no "restricted session" a pending applicant could use to reach ordinary business. The administrator's ordinary-account directory excludes both approval states, and aiming at one of their ids by any of the four entries (detail, profile edit, status, credential reset) gets 1001 — "that person is not in this book". Reviewing lives on its own pair of endpoints, described below; it is never a side effect of the directory's four write entries.

An applicant who wants to know where their application stands can ask through `POST /auth/registration-status`, and the answer is only reachable by proving the credentials again: the body carries `login_name` and `password`, verified against the same Argon2id credential as sign-in. A success returns the outcome (`pending`, `approved` or `rejected`), the submission time, and the decision time when one exists — nothing else. No reviewer identity, no reason text, no queue position, nobody else's application, and no session material: this path writes no `Set-Cookie` and creates no session row, so there is no temporary status token that would need an expiry or a revocation boundary. It is POST-only for the same reason: a secret never goes into a URL, a query string, a preFetchable request or a pasted address bar. Unknown name, guest account and a wrong password all collapse into the same 2001, so the entry adds no enumeration signal beyond sign-in itself, and throttling uses the login guard's own ledger — a second door cannot hand out a second password-guessing budget. Code 2020 (403) is the one answer that appears only after the credentials have proven who is asking: the account exists and this is its owner, but it never went through the approval path, so the disposition is "use the sign-in page", not "wait" or "change your name".

Switching the mode governs new submissions only, and historical applications are left in place. Root may set the mode back to `closed` or over to `open`, and neither decision says anything about any individual applicant: rows already filed stay `pending`, stay queryable by their owner, and are neither waved through nor deleted. That also means a repeated submission under the same login name meets the same uniqueness index as everybody else (2019), because a pending or rejected row keeps occupying the name — a declined applicant does not get a second bite at the same name, and no one else can take it either.

Migration `0009` widens the account status set with `pending` and `rejected` and adds one `reviewed_at` timestamp, which is how the status path can tell "approved earlier and suspended since" apart from "never applied"; a decision time can never sit on a row that is still waiting or already declined, and no freshly created row can carry one. The submission still appends one `account.self_register` record in the Root audit domain with the system as actor (an anonymous request has no trustworthy subject to record), and the recorded `status` is the state that actually landed, so "we filed an application" and "we created a signer" are distinguishable in the audit trail without inventing an audit query entry point. Cross-origin deployments have to list `POST` in `cors.allowed_methods` for both paths; the shipped default still allows only `GET`, `HEAD` and `OPTIONS`. The pre-login entry capability now carries three booleans — `sign_up_open`, `guest_open` and `invite_code_required` — but the mode name itself still does not leave the anonymous entry: the question "usable now or still waiting" is answered by the write's own status, and `invite_code_required` only says "this round needs a code" (it lights up only in invite mode), never which mode is in effect.

## Reviewing registration applications

`GET /admin/registrations` lists the applications that came through the approval path — `page`, `page_size`, a `status` filter of `all`／`pending`／`rejected`, and an optional name keyword; the rows carry the account id, both names, the status, the submission time and, when one exists, the decision time. Nothing else is in the projection: no password, no credential hash, no normalized login key, no roles, and no reviewer or reason field, because the account table has no such column. Someone who was approved leaves this book — that row now belongs to the standard-account directory, where suspension, credential reset and renaming are handled. Grant holders, guests and deleted rows are outside the scope and get the same indistinguishable 1001 as an unknown id, so this path never becomes an oracle for "who exists but is not an applicant".

`PUT /admin/registrations/{account_id}/decision` makes the decision, and the body has exactly one field: `decision`, `approve` or `reject`. There is no anchor value to carry, because a reviewer has no honest one — the current value of an undecided row just is `pending`, so an `expected_status` field would only add a form control that is guaranteed to fail when misspelled; the real concurrency control is the database guard `WHERE status = 'pending'` (the same reasoning as the delete and credential-reset entries). There is no role field, no status field, no password field and no reason field: the UPDATE statement does not even mention `account_server_roles`, so "approving quietly mints another administrator" has no place to happen, and approving issues no session — the applicant still signs in themselves through `/auth/login` with the password they chose, and what they get is an ordinary account with no server-level grant. Approval also does not lift anything independent: `must_change_password`, `disabled_at` and `deleted_at` are not in that statement, so a person who was approved and later suspended is simply not a pending row any more, and the review entry cannot re-enable him.

A decision is one-way, and concurrent reviewers form exactly one result. Only a `pending` row can be decided; once somebody has approved or declined it, there is no path that reverses, re-files over, or overwrites that decision — the loser of a concurrent pair, and anyone clicking again on a decided application, gets code 2021 (409) "this application has already been decided", which is deliberately not 2014's "your anchor is stale, read it again and you may press the same button". The disposition for 2021 is reloading the list: that button no longer exists for that row. Rejected rows are kept, the login name stays occupied, and reopening them is not a product decision this step makes. Reviewing never consults the account-creation policy either: Root switching the mode to `closed` or `open` retires nobody's pending application and blocks no reviewer from deciding the one in front of them, because a policy governs new submissions only.

Both entries are gated by `NeedServerAdmin` — the same bar as creating, listing, suspending and resetting ordinary accounts — so an administrator with ordinary-account management rights reviews ordinary-account applications, and Root passes too. An ordinary account, a guest and the system subject get 2011 before anything is read, and an anonymous caller gets 2002 before the database is touched. A successful decision appends exactly one Root-scope audit row (`account.approve` or `account.reject`) whose actor is the real reviewer obtained from the trusted subject — never system, never Root-by-impersonation — carrying the before and after values of `status` and `reviewed_at` and a fixed server-authored reason sentence; refused decisions write no audit, and this step adds no audit query endpoint or console. Neither the reviewer's identity nor any reason text is ever returned to the applicant: what they can learn is the outcome and the decision time, through `POST /auth/registration-status` below.

## Managing server registration invite codes

An invite code is a credential that admits a new ordinary account to the server: it carries no Root or administrator role and joins no activity. Only Root manages these, on `POST`／`GET`／`HEAD /root/invite-codes` (issue and a paged roster) and `DELETE /root/invite-codes/{code_id}` (revoke) — all gated by `NeedRoot`, the same side as the account-creation policy, because "who may hand out the pass" is itself a server-level admission decision. An administrator who manages ordinary accounts still cannot issue or revoke codes.

Each code has its own quota and lifetime. `max_uses` is how many times it may be redeemed (at least 1; 1 is a single-use code — there is no separate "single-use" flag, which would just be a second copy of `max_uses = 1`); `used_count` only ever advances by one per redemption, and the roster shows `remaining = max_uses - used_count`. `expires_at` is optional: `0` means the code never expires, otherwise it is an absolute expiry that must be later than issuance. Status is never a stored column — `active`／`expired`／`exhausted`／`revoked` are computed at read time from those facts plus the injected clock, so nothing purges or flips rows on a schedule and no clock reading can disagree with another. Revoking is a one-way terminal fact: it immediately blocks any further redemption and freezes the row (used count is kept as history), and repeating it returns code 2022 (409) "this invite code has already been revoked" — the disposition is reloading the roster, not pressing the button again.

The full code is shown exactly once, in the `201` response to the issue call, and the server stores only its SHA-256 — a code is high-entropy random, so (like session secrets, and unlike human passwords, which stay on Argon2id in `internal/credential`) a fast hash is the right verification material and a database dump cannot yield a usable code. The roster and the revoke echo carry only label, status, quota and times — never the code, never the hash. A lost code is re-issued, not recovered from the database. Issuance and revocation each append one Root-scope audit row (`invite.issue`／`invite.revoke`) whose actor is Root from the trusted subject, and neither the plaintext code nor its hash is ever written to an audit, a log or an error.

Redemption — turning a valid code into an account — is now wired into the **same** anonymous `POST /auth/register` the open mode uses, as its `invite` branch: the request carries an optional `invite_code` field, and only when the policy's effective mode is `invite` at write time is that code read and redeemed (open and approval never look at it, so a code is never quietly consumed on a side that does not need one). Redemption and account creation share one `BEGIN IMMEDIATE` transaction through `internal/invitecode`'s `Store.Redeem` (the `used_count` guard `revoked_at = 0`, `used_count < max_uses`, `expires_at = 0 OR expires_at > now`), so a duplicate login name, an invalid password or any write failure rolls the whole thing back and no quota is burned; a single-use code concurrent-submitted lets exactly one sign-up win and returns the same non-leaky rejection to the rest; a retried or response-lost request creates no second account and consumes no extra quota. What lands is always an ordinary account — the code grants no role — and it can sign in immediately, on the same path as open mode (registration still issues no session). The pre-login `GET /auth/capabilities` gained a third boolean, `invite_code_required`, which lights up only in `invite` mode so the shared sign-up form knows to reveal the field; it never reveals the mode name. A code that cannot produce an account for any reason — missing, malformed, never issued by this server, revoked, expired, exhausted, or lost to a concurrent sign-up — collapses to one code, 2023 (403), deliberately undifferentiated so the endpoint is not a validity oracle; throughput is bounded by the same per-source sign-up throttle as the open mode. Switching `self_register_mode` to `invite` is Root's separate decision on `/root/account-policy`, which now accepts all four names.

## Restricted guest entry

`POST /auth/guest` is the anonymous path by which a person outside the server becomes a **temporary, restricted subject**. It exists only while the account-creation policy says so, and its answer is computed the same way as every other entry: `guest_enabled` **and** "this binary actually ships the path" (`internal/acctpolicy`'s `AllowsGuest`, read again inside the write transaction). A closed switch is answered with the existing 2017 (403) — "this account-creation path is closed by server policy right now" — because that sentence was always about account-creation paths, and giving guests their own code would just be one decision with two spellings.

The subject is server-named, and that is the whole point. `login_name` is generated as `guest_<uuid>` and the request has no field to supply it, so a guest cannot reserve a name a real person will want later, and the anonymous entry never becomes an existence probe for login names (which is exactly what `POST /auth/register` structurally is, and why that path carries a distinguishable 2019 instead). The stable identity is the Account ID the server mints; the nickname is display information only — optional, validated by the same domain rules as any display name, allowed to duplicate somebody else's, and never a credential. Leaving it blank gets a language-neutral temporary code (`guest-<6 hex>`), because a server-generated string must not embed any one language's words.

The account has no credential by construction: `password_hash` is NULL and `must_change_password` is 0, frozen by a schema CHECK and re-checked in the domain, so there is no password here to guess, reset, or hand over. That is also why this path — unlike self-registration — **does** issue a session: a guest has no later password login to walk, so the door would be a wall without it. The session comes from the one signing point in `internal/session` and is distributed by the one cookie path in the transport layer: same absolute expiry, same idle line, same revocation on sign-out and password change, same device-slot policy, same rotation. There is no guest-flavoured cookie that ignores those constraints, and the secret reaches the client only through `Set-Cookie` (managed by the browser on the web path, stored in platform secure storage on native), never in a response body.

Being inside is not being an administrator. The guest principal is built with an empty grant set — and `identity.NewAccountPrincipal` rejects a guest that carries any role, so this is a type-level wall, not a convention. Consequently every `NeedServerAdmin` and `NeedRoot` path answers 2011 (403) while an anonymous caller gets 2002, and guests cannot list the account directories or write through them; the ordinary self-service paths (`/auth/session`, `/auth/logout`, `/auth/session/rotate`, `/auth/devices`) work exactly as they do for anybody else, because revoking one's own sessions is not a privilege. What a guest is *not* told is also deliberate: no activity, asset, chat or NPC surface pretends to be available, and the interface's player view states plainly that this identity belongs to no activity yet.

Two decisions were made explicitly rather than quietly. First, **there is no self-service recovery**: when the session expires, the person signs out, switches device, or clears local credentials, that visit is over. A nickname-based "bring me back" path would be a guessable credential that anyone could present for somebody else's identity, and this step deliberately does not invent one — an administrator verifies the person in the ordinary-account directory (which lists guests by definition) and decides there. Second, **guest creation counts attempts, not failures**: `security.register_guard`'s thresholds are reused in a third, separate in-memory guard keyed on "source address × this path", and a successful entry burns budget like a rejected one. Self-registration self-limits through login-name uniqueness, but every successful guest entry really does add an account row, a session row and an audit row, so metering only the failures would leave "the switch is on, therefore create without limit" open — and no scheduled bulk deletion of guests is provided either, which is why the cap has to be at the door.

What lands is one `account.guest_enter` row in the Root audit domain with the system as actor (an anonymous request has no trustworthy subject to record), carrying the generated login name, the display name, `account_type` of `guest` and `must_change_password` of false — and no source address, no session material and no nickname beyond the display name itself. The response echoes the account id, the display name, the device id and the expiry, and the `account_type` field that also appears in `/auth/login` and `/auth/session` responses is what lets a refreshed client still say "guest (temporary identity)" instead of flattening everybody into "account".

## Guest accounts upgraded in place

`PUT /admin/accounts/{account_id}/upgrade` is the administrator-only path that converts a guest row of the ordinary-account directory **in place rather than rebuilding it**. The body whitelist is two fields, `login_name` and `password`: the upgrade gives the person a real login name and a one-time credential the operator hands over personally, and the upgraded shape is always `standard` plus `active` plus `must_change_password` - there is no field for `account_type`, `roles`, `status` or the flag to declare, so "promote the guest into an administrator" has no box to fill at the protocol layer, and the identity matrix would refuse a grant that does not exist anyway.

What is preserved is the point. The update touches five columns of the same account row (login name, its normalized key, account type, password hash, first-change flag), while the Account ID, the creation moment, the display name, every reference that actually exists toward that stable identity, and the `account.guest_enter` audit row that recorded how this person was born all stay byte for byte. Audits are append-only: the upgrade adds one `account.guest_upgrade` row in the Root domain (the real administrator as actor, the login name and account type before and after, the change obligation and the number of revoked sessions), and nothing rewrites history, because a historical event describes the guest as he was at that moment. That is the difference between upgrading in place and linking the guest to *another* existing standard account - the second verb still has no execution path, but a read-only pre-check with conflict preview exists now; the interface keeps the two sentences apart on the very same card.

Old sessions do not survive the upgrade. Session resolution re-reads the account row on every request, so leaving a guest cookie alive would mean whoever holds that stale temporary credential silently gains a standard account without taking any new action; revoking every session the account holds therefore happens inside the same transaction as the upgrade - the very primitive that disable and reset already use - the response reports `revoked_sessions`, and the only way back in is a real sign-in with the new credential, which immediately meets the first-change gate (2010). If any step fails, nothing lands: no half-upgraded identity without a password, no revocation whose audit row is missing.

The three creation switches do not gate this path: they answer "may one more account exist", while the upgrade edits the shape of an account that already exists - closing the guest door must not strip administrators of the means to process the guests who are already inside. The conclusions stay one sentence apart: 1004 names the malformed `login_name` or `password` field; 2012 says that name belongs to somebody else and the guest row is not touched; 2011 says the caller is not an administrator - the guest himself included, since this path exists precisely to answer him with that; 1001 is a target this directory does not list by definition (an administrator, a deleted account, an applicant); and the upgrade's own new code, 2024 (409), answers "not an upgradable guest right now" - either already upgraded (a repeated submit) or currently disabled. Those two read as "nothing left to do" and "restore his login first", and both point at reloading the server's current values rather than at 1001's "pick another target": the directory lists him. Password delivery follows the same rules as creation and reset: the server generates nothing, echoes nothing, and the offline handover stays outside the protocol.

## Guest binding pre-check (read-only preview)

The verb "merge a guest into *another* existing standard account" still has no execution path, but a read-only pre-check with conflict preview now exists: `POST /admin/accounts/{account_id}/bind-preflight`, called by a server-level administrator (NeedServerAdmin), whose body whitelist is exactly one field - `target_account_id`. One request evaluates one pair, "this guest times this target"; no reading lists bindable targets for a guest, and the request shape itself is the anti-enumeration boundary. The target identifier belongs in the body rather than a query string: it is an input under verification, not something bookmarkable or cacheable.

This path writes nothing: no account changes, no session revokes, no grant touched, and not even one security audit row (the user-approved R2-018 decision: purely read-only; the interface's "nothing has been linked" sits in the result panel's first line). "Not bindable right now" is a stable reason token inside a 200 preview, not an error: when `executable` is false, `blockers` names each cause - the same account on both sides (`same_source_target`), a source who is no longer a guest (`source_not_guest`), a disabled source (`source_not_active`), a guest unexpectedly carrying grants (`source_has_grants`, a defect direction), a guest as the target (`target_not_standard`), a disabled target who could not confirm a binding in his own session anyway (`target_not_active`), and `unknown_references`. The response also reports the `schema_version` this snapshot ran against, the number of the guest's not-yet-revoked sessions (`source_open_sessions`), and a `consent_mode` that is always `target_self_initiated`: a binding may only be initiated by the target account's owner from his own authenticated session, and an administrator never gets a button that binds on someone's behalf - an equal login name or a typed-in target ID is not consent.

Blocking on unknown references is the load-bearing rule of this section. Every pre-check run rescans the live schema's foreign-key edges: if any table references accounts while missing from the disposition registry (tables future activity, ledger or NPC modules will add), every binding is refused rather than silently merging permissions or assets nobody evaluated; that module must be wired into the pre-check before bindings resume. Unregistered table names go only into the server log, never into the response. No new machine code was published for this step: request-level refusals reuse existing codes - a source or target outside the ordinary-account directory (absent, administrator, deleted, pending) collapses into the same indistinguishable 1001 as the detail endpoint, so the preview is never a brighter searchlight than the detail already is; 2011 says the caller is not an administrator (the guest himself included); 1004 names `target_account_id`; 1002 is the method.

The previewed impacts are also part of a contract about "when a future step executes": the guest's open sessions would be revoked in the same transaction, the guest row would enter a retired, non-sign-in, non-reusable terminal state (a future migration's shape; it does not exist today), records pointing at him stay byte for byte, future attribution lands on the target's identifier, and the target's password, status, display name and permissions are untouched.


## How it will work (once released)

- One person hosts the server on their machine (Windows or Linux)
- Everyone else joins from a browser on the same local network
- No third-party registration; data stays on the host's machine
