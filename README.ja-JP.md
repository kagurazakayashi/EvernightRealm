# 長夜幻境（EvernightRealm）

> あなた自身のマシンで、仲間のためのプライベートな仮想世界を — アクティビティ管理、キャラクター、仮想アセット。

[English](./README.md) · [简体中文](./README.zh-CN.md) · [繁體中文（台灣）](./README.zh-TW.md) · [日本語](./README.ja-JP.md)

## これは何？

長夜幻境（ちょうやげんきょう／EvernightRealm）は、自己ホスト型・オフライン優先のプラットフォームです。小規模なプレイヤーグループが没入型アクティビティを一緒に進め、キャラクターを演じ、仮想アセットを取引できます — すべてローカルネットワーク内で完結し、インターネットもクラウドアカウントもテレメトリも不要です。

## 機能（開発中）

- **没入型アクティビティ** — グループ向けにシーン、フェーズ、イベントを編成
- **キャラクターとアイデンティティ** — プレイヤー・NPC・管理者の役割が共存するプライベートな世界
- **仮想アセット** — 真正な所有権と監査可能な取引
- **プライベートチャット** — メッセージは自分のサーバーだけに保存
- **オフラインファースト** — すべて自分のマシンで動作し、クラウドに依存しない

## 現在の状況

長夜幻境は活発に開発中で、安定版は未リリースです。サーバーはすでに**単一の実行ファイル**としてビルドできます：同じポートがウェブ画面（現在はアプリのシェル部分で、表示言語の切替とサーバー接続の試行が可能。業務機能は開発中）と API エンドポイントの両方を提供する為、ブラウザでそのアドレスを開くだけで利用でき、静的ホスティングを別途用意する必要はありません。

サーバーにはさらに、**整合性のあるバックアップパッケージ**を作る運用コマンドがあります。単一ファイルのデータベーススナップショット（サーバー稼働中でも取得でき、稼働中の WAL 主ファイルをコピーするのではありません）に設定ファイルとメディア／文書／アップロードディレクトリを添え、各ファイルのサイズと SHA-256 をリストに記録します。対応する `restore` コマンドで、このパッケージを**新しい空のデータディレクトリ**へ復元できます。マニストに従い全ファイルのチェックサムを再計算し、スナップショットのデータベース実体を着地前後で二回読み取って照合します。既存ディレクトリは上書きしません（上書きしたい場合は当該ディレクトリを先に自分でバックアップしてください）、実行ファイルより新しいスキーマ版の復元は拒否し、復元操作自体をサーバー側監査記録として書き込みます。バックアップの暗号化と旧パッケージの自動削除はまだ未実装です。

一度限りの Root 初期化は**ローカルコマンドだけが入口です**：

    evernight-server init-root --password-stdin --data-dir <データディレクトリ>

標準入力からパスワードを読み取り（先頭の 2 行は本体と確認）、そのデータディレクトリの `config.yaml` に Argon2id のハッシュとして保存します。平文は書かず、初期パスワードを自動生成して表示することもありません。サーバーの最高権限を渡す認証は「サーバーのホストでコマンドを実行できること」なので、この手順は HTTP エンドポイントも待ち受けポートも一切開きません。CORS、クライアントが自己申告したアドレス、画面からボタンを隠す、どれも認証にはなりません。サービスが単一書き込みインスタンスロックを保持している間、`ER_SECURITY_ROOT_PASSWORD_HASH` が設定されている間、監査テーブルがまだ存在しない間はすべて拒否し、書き込み成功後は二度と開放されません（パスワードの交代は認証済みのサービス内フローで行い、Root でサインイン後に `POST /auth/password/change` を使います。次の段落のローカル復旧が該当するのは、本当にパスワードを失念した場合だけです）。読み取り専用の `evernight-server root-status` は「いま Root があるか」だけを答え、ファイルを作成も変更もせず、設定パス・ハッシュ・導入手順上の秘密は一切返しません。成功も拒否も Root 監査テーブルに記録され、パスワードは残りません。

失念した Root パスワードの復旧も、ローカルコマンドだけが入口です：

    evernight-server recover-root --password-stdin --confirm --data-dir <データディレクトリ>

このコマンドも標準入力から新しいパスワードを読み取り（先頭の 2 行は本体と確認）、コマンドライン上のパスワード値は一切受け取りません。また、サービスの停止を要求します：稼働中のサービスは認証情報をメモリに読み込んでおり、設定ファイルを書き換えてもそれを再読み込みしないためです。そうなると「端末は成功だと言ったのに、旧パスワードはまだ通る」という、拒否よりも調査の難しい状態が生まれます。復旧は旧パスワードを尋ねず、検証もしません——このホストでコマンドを実行でき、この設定ファイルを読み書きできること自体が、この操作の認証のすべてです。ゆえにバックドア用パスワード、ダウンロード可能な復旧ファイル、HTTP エンドポイントも一切ありません。成功時は設定ファイル内の認証情報が新しいパスワードの Argon2id エンコードに置き換わり、Root 配下の全セッションが同一のデータベーストランザクション内で取り消され（次のリクエストから拒否されます）、`server.root_recover` の監査記録が 1 件残ります。通常アカウントのセッションは 1 つも動きません。取り消しと監査が書き込めない場合は、設定ファイルを書き換える前の認証情報に戻して失敗を返し、利用可能な状態は着手前と一致します（ロールバックさえ失敗する二重障害は、実行ログのファイルに Error として残り、手動での追記を明示的に要求します）。`--confirm` は明示的に必要なフラグです。上書きの代償は、旧パスワードの恒久的な失効と Root の全端末のサインアウトだからです。設定ファイルにまだ認証情報が無い場合は拒否して `init-root` を案内し、逆に、既存の値が壊れて復号不能（誰もサインインできない状態）でも復旧はできます——これはまさに `init-root` が拒否する形であり、二つの書き込み経路はそれぞれ成功形態を一つだけ持ちます。

初めての起動画面は「未初期化」を正直に示す必要があるため、サーバー側は読み取り専用の `GET /root/init-status` にも答えます。返すのは 3 つの真偽値だけです（設定ファイルの有無、Root 認証情報の有無、環境変数による上書きが設定されているか）。パス・長さ・認証情報の断片は返さず、データベースにも監査にも書き込みません。これは「有るか無いか」を言うのであって「どう変えるか」ではありません。Root の初期化は引き続き、サーバー本体で実行する `init-root` だけが経路です（失念したパスワードの書き換えは上の `recover-root` が担い、どちらもネットワーク越しには到達できません）。

## サインインと自分のアカウントの管理

アイデンティティ段階の機能はすでに実装済みで利用できます。サインイン、現在のセッションの確認、サインアウト、自分のデバイスの管理、自分のパスワードの変更、そして Root によるアカウント作成、管理者カタログの管理、管理者のログイン停止と再開、管理者ログイン認証情報のリセット、管理者のソフト削除（次の節）、そして Root によるサーバーのアカウント作成ポリシーの設定（その次の節）、さらにそのポリシーに基づく管理者による通常アカウントの作成、通常アカウントカタログの参照、単一レコードの参照と維持、そして通常アカウントのログイン停止と再開、通常アカウントのログインパスワードのリセット（作成は前の節、カタログ・資料・停止・認証情報はこの後の四つの節）までがそうです。二つの制限も同じようにはっきり書いておきます。第一に、アカウントは次の入口からのみ発生します。Root の認証情報自体はサーバー本体上で `init-root` により作成され、サーバー管理者は `POST /root/admins` で作成され、通常アカウントは `POST /admin/accounts` によって作成されます（これは `admin_create_standard` が開いている間だけ、かつ認証済みのサーバーレベル管理者に対して成り立ちます）。あるいはセルフ登録 `POST /auth/register` によっても作成されます。セルフ登録は匿名で読め、`sign_up_open` が真のあいだだけ開放され、本人が自分で選んだパスワードを持つ通常アカウントを返し、セッションは発行せず、管理者を作成することはありません。セルフ登録はすでに実装済みです。招待コードとゲストアカウントは未実装で、対応するスイッチとモードは今や設定できますが、その裏の経路はまだ存在しません。したがってそれらの入口は用意も表示もしていません。第二に、サーバー自身は TLS を終端しません。既定の待ち受けは `127.0.0.1:5206` の平文 HTTP で、セッション Cookie に `Secure` が付き HSTS が送出されるのは、リクエストが実際に TLS で届いたときだけです（つまり、自分で TLS 終端のリバースプロキシを前に置いた場合）。証明書の取り扱いは同梱しておらず、HTTPS はこのプログラムの外側にある配置の選択です。

アイデンティティ関連のエンドポイントにバージョン接頭辞はありません — `/api/v1` は存在しません：

- `POST /auth/root/login`（Root パスワードのみ）と `POST /auth/login`（ログイン名とパスワード）。成功のたびに新しいセッションを発行して以前の Cookie を置き換えるので、古い Cookie が引き継がれることはありません。
- `GET /auth/session`、`POST /auth/logout`、`POST /auth/session/rotate` — 現在のセッションを読む、まさにこのセッションだけを取り消す（冪等）、またはこのセッションの秘密を交換する。
- `GET /auth/devices` と `POST /auth/devices/revoke` — サインイン中の主体自身のセッションだけを一覧・取り消しします。他人のデバイスを名指しできるリクエストはありません。
- `POST /auth/password/change` — 現在のパスワードをリクエスト内でその場で渡す必要があります。成功するとその主体の全セッション（このデバイスを含む）が取り消されます。

ブラウザ経路ではセッションの秘密は `HttpOnly` Cookie に入り、ネイティブクライアントは応答ヘッダーから読み取った bearer 秘密として持ちます。サインインの失敗が繰り返されると「送信元アドレスとログイン対象」ごとに制限され（HTTP 429、`Retry-After` 付き）、Root の入口も同様です。制限された試行がどのアカウントに当たったかは示しません。`device_policy` を `single` または `limited` にすると、古いセッションが破棄されるか、上限に達した時点で新しいサインインが拒否されます。「初回サインイン時にパスワード変更必須」のアカウントには、セッション確認・サインアウト・パスワード変更の流れだけが許され、他の保護されたエンドポイントは変更が済むまで 2010 を返します。

二つの運用境界は変わりません。バックアップと復元は `evernight-server` のサブコマンドのままで HTTP の入口はなく、監査記録はサービス層だけが書き込み、監査の照会エンドポイントやウェブコンソールは依然としてありません。実行ログは暦日で切り替わり、既定では自動削除しません（`retention_days=0`）。ログを際限なく増やさないのは運用者の仕事であり、プログラム側が時間の経過でログ総量に上限を設けることはありません。

## Root による管理者カタログの管理

Root のセッションは、最初に人の手で動かす運用者を迎え入れる経路です。`POST /root/admins` に `login_name`、`display_name`、`password` を渡して作成し、`GET /root/admins` がページ付きの管理者カタログです（`page`、上限 100 の `page_size`、`all`／`active`／`disabled`／`deleted` の `status` 絞り込み、授与の時刻が新しい順に並び、`page`・`page_size`・`total` を返し）、`GET /root/admins/{account_id}` が単一の記録を読み、`PUT /root/admins/{account_id}` がそれを編集し、`DELETE /root/admins/{account_id}` がそのアカウントをソフト削除します（本文は一切持たず、どんな項目を付けても 1004 で拒否されます）、`PUT /root/admins/{account_id}/status` がそのアカウントのログインを停止または再開します（本文は `status` と `expected_status` の二項目だけ）、`PUT /root/admins/{account_id}/password` がそのアカウントのログインパスワードをリセットします（本文は `password` の一項目だけ）。新しいアカウントを管理者にするのはリクエスト内容ではなくエンドポイントそのものです。`role`、`account_type`、`subject_kind` といった項目は存在せず、余計な項目を付ければ 1004 で拒否されます。許可の入力になるのは「このリクエストから解決された主体が Root である」という事実だけなので、通常アカウントも管理者自身のセッションも 2011（403）を受け取ります。管理者が同格の管理者を作ることも、同格を管理することも、自分自身を昇格させることもできず、サインインし直してもその状況は変わりません。カタログに並ぶのは管理者アカウントだけで、設定上の Root はここに行として現れず、通常アカウント用の接口で編集できるレコードになることもありません。

初期パスワードは Root が手渡し、一回限りのものです。他のあらゆる認証情報と同じ Argon2id サービスでハッシュされ、アカウントは `must_change_password` を付いて保存され、サーバーはいかなる応答でもそのパスワードを表示し返し、既定のパスワードも一切存在しません。そのためその人の初回サインインで得られるセッションに許されるのは、現在のセッションの確認、サインアウト、パスワード変更の入口だけで、他の保護されたエンド点はすべて 2010 を返します。変更が完了すると、そのアカウントの全デバイスがサインアウトします。これらの規則は元からあらゆるアカウントに適用されていたものであり、今回のステップが補うのはこの旗印の出所です。

ログイン名の一意性はサインインと同じ正規化キー（NFKC に全面の大文字小文字折り返し）を使い、accounts テーブルのユニークインデックスが保証します。既に使われている名前は 2012 を返し何も作成しません。だから二重送信も、応答を失った後の再試行も、第二のアカウントを生むことはなく、その拒否応答は既存アカウントのデータも認証情報も返しません。アカウントの作成、`server_admin` の授与、`admin.create` を Root 監査へ追記することは、すべて同一トランザクション内で起きます。どこかが失敗すれば半端な管理者も、痕跡の特権変更も残らず、監査記録には身元を示す項目だけが残り、パスワードやそのハッシュは決して残りません。

編集が受け付けるのは `display_name` の一つだけで、根拠にした現在の値 `expected_display_name` と共に送信します。状態、認証情報、初回変更の旗印、アカウントタイプはこの通路に存在せず、UPDATE 文が触れるのもこの列だけです。保存の直後に他人が変更していた場合は、編集全体が 2013（409）で拒否され何も書き込まれません。これはパスワードのローテーションと同じ compare-and-set の守りです。标识の形が不正な場合、アカウントがカタログにない場合、アカウントが本当に存在しない場合は、いずれも同じ 1001 を返します。このエンドポイントをアカウント列挙の探りに使えないようにするためです。応答に表示できる事実だけが載り、パスワードハッシュ・セッション秘密・リカバリーコード・設定は一切載りません。Root による編集が成功するたびに `admin.profile_update` の監査が一件追加され、そこには表示名の前と後の値だけが記録されます。拒否された編集は何も残しません。

ログインの停止と再開は、項目を一つに絞った別のエンドポイントを通ります。停止すると新規サインインは拒否され（他のサインイン失敗と同じ形での返しで、「この人がロックされた」とは言いません）、そのアカウントの既存セッションは同一のデータベーストランザクション内で全て取り消され、状態の前後値、`disabled_at` の前後値、`revoked_sessions` を備えた `admin.disable` の Root 監査が一件追加されます。主体が今も使えるかは各リクエストでデータベースの現在値を読むため、停止された管理者の既存セッションはどの保護された入口でも受信主体に解決できません。再開（`admin.enable`）が回復するのは新規サインインの能力だけです。停止時に取消されたセッションは復活せず、未完了の初回パスワード変更義務は有効なままです。Root も、管理者が同格の管理者を停止することも、どちらも正当な対象になりません。状態の書き込みは、送信元が見た現状に対する compare-and-set で、根拠が古い場合も重複操作も 2014（409）で拒否され、何も実行されません（状態変更なし、セッション取消なし、監査記録なし）。すでに完了した作業は巻き戻らず、停止有効化後に始まった新しい作業だけが拒否されます。UPDATE 文が触れるのは `status` と `disabled_at` の二列だけなので、「停止が認証情報やフラグをこっそり消す」ことは SQL の形自体で起こりようがなく、停止中の管理者は（授与行が残るため）カタログに残り続けます。それがそのまま再開できる前提になります。

ログイン認証情報のリセットは、単一項目の子リソースとしては三本目のエンドポイントです。`PUT /root/admins/{account_id}/password` が担うのは `password` の一項目だけ——Root が自ら手渡す一時パスワードであり、配信の意味合いは開設時と同じ承認済み方式です。サーバーはパスワードを生成せず、どの応答にもリプレイせず、パスワードはリクエスト本文に一度だけ現れます。ログ・監査・応答に認証情報材料は一切含まれず、対面・オフラインでの受け渡しはプロトコルの外側にあります。一回の成功は同一トランザクションで三つの事実を確定させます。旧パスワードは直ちに無効、名下の全セッションは直ちに取消（`revoked_sessions` が権威ある計数）、そして次回サインイン時のパスワード変更が義務付け（本人変更と同じ 2010 ゲートをそのまま適用）。他人のリセットは、自分のパスワード変更とはあえて別ユースケースです。本人変更は現行パスワードの提示で再認証し義務を晴らす一方、Root による他人のリセットはまさに現行パスワードが提出できない——すべきでもない——場面に存在し、成功すると義務は改めて有効になります。リセットに compare-and-set の根拠値がないのはそのためで、無理に作った錨はそれが主張するものを検証しません。重複送信は 2013/2014 のような「根拠陳腐化による拒否」ではなく、每一次完整に効くリセットであり、それぞれ `admin.password_reset` 監査（パスワード変更義務フラグの前後値と取消数、認証情報は絶対に含まない）を一件残します。結果が不明なとき、画面側が自動で再送してはならないのはこのためです。リセットが変わらない事実も同じように真実です。UPDATE 文は `status` と `disabled_at` に触れません——停止中の対象へのリセットは成功し、対象は停止のまま、新規サインインは拒否され続けます（他のサインイン失敗と同じ形）。再開は引き続き status 経路の仕事で、リセットは権限剥奪でも改名でも削除でもなく、授与行はそのまま残ります。形式不正の識別子、幽霊識別子、未授与のアカウント、物理削除済みの対象は全て 1001 を受け取ります。ソフト削除済みのアカウントは 2015 です。あちらでは記録がまだ存在し、拒否の理由はその状態だからです。Root 以外は 2011、形状基準を満たさないパスワードは `password` を名指しする 1004 を受け取ります。

管理者の削除は状態であり、データベースの掃除ではありません。`DELETE /root/admins/{account_id}` は本文を持たず、一回の成功が同一トランザクションで三つの事実を確定させます。ログインが止まり、名下の全セッションが直ちに取り消され（応答は権威ある計数として `revoked_sessions` を返し）、`admin.delete` の Root 監査が一件追記されます。そこに載るのは、この削除を後から説明するのに必要な身元の記録——ログイン名、書き換え前後の表示名、状態の前後値、`deleted_at` の前後値、取り消し数——だけで、認証情報の材料は一切残りません。アカウント行そのものは残ります。識別子も、ログイン名のキーも、授与行も、セッション行も、監査行も、同じ安定したアカウントを指し続けるため、過去の操作が何も指さないという形にはならず、Root の名下へ静かに付け替えられることもありません。物理的なデータベース掃除がこのステップに含まれない理由もここにあります。参照されている行はそもそも削除できません。削除は終了した状態です。再開の入口はありません。`PUT /status` は拒否します。停止と削除は別の状態であり、既存のログイン再開通路が削除済みアカウントを復活させてはならないからです。削除済みの対象に対する編集・認証情報のリセット・二度目の削除はいずれも 2015（409）を返します。この機械コードの意味は「このアカウントは存在する、ただし削除済み」です。加えてデータベース層には、削除済みの行を書き換え不可にするトリガーがあり、今後のどの書き込み通路もこっそり元に戻せません。表示用データのうち一箇所だけが削除のときに匿名化されます。`display_name` は `DEL_<UTC 日付>_<旧名>` の形の仮の文字列に書き換えられ、長さの予算は今までと同じ上限を使います。これで現在の記録が以前の名を現在の名として提示することはありません。追記専用の歴史はあえて触りません。削除の前に書かれた監査記録は当時の名前を保つ——古い操作が今日も説明できるのはそのためです。ログイン名の正規化キーは占有され続けるため再利用もできません。削除済みの管理者はカタログに残り（`status=deleted`、カタログと単一記録の応答に `deleted_at` を含む）、その詳細は読み取り専用です。一括削除は提供せず、リクエストに理由の文章も載せません。設定上の Root 認証情報はカタログの行ではないので、削除の対象にはなり得ません。

応答には「追加のみ」の進化規則に従った項目が二つ増えました。サインインと現在のセッションの応答に `roles` が含まれ、サーバーがその主体について読み出した授与が記されます（授与がなければ項目自体現れません）。クライアントはこれを見てどの入口を読み込むか決めます。しかしそれ自体は何も許可しません。各エンド点は毎回、信頼できる主体を読み直します。


設定したホワイトリスト上のクロスオリジンブラウザからこれらのエンドポイントを呼ぶ配置では、`cors.allowed_methods` に `PUT` を `POST` と共に列挙し、削除エンドポイントのために `DELETE` も加える必要があります。出荷時の既定は `GET`／`HEAD`／`OPTIONS` のままで、オリジンのホワイトリストは常に設定の選択であり、この節はその境界を緩めません。

## サーバーのアカウント作成ポリシー

3 つの値が、この構成が「ログイン可能な一般アカウントを新たに増やす」ことについての方針を示します。`admin_create_standard`（管理者が一般アカウントを作成できるか）、`self_register_mode`（`closed`・`open`・`approval`。`invite` は承認済みの名称ですが、対応する流れはまだ提供されていません）、`guest_enabled`（一時的なゲストアカウントを作成できるか）です。`GET /root/account-policy` がこの 3 つを読み、`PUT /root/account-policy` が 1 つのドキュメントとしてまとめて書き込みます。読み書きできるのは Root だけです。管理者自身のセッションは 2011、資格情報なしは 2002、クロスオリジンの発信点はデータベースに触れる前に 2005 で拒否されます。「管理者が一般アカウントを作成できるか」はこのエンドポイントが設定する値ですが、「管理者がサーバーポリシーを変更できるか」はそもそも値として存在しません。3 つの項目は互いに独立しており、どれも省略できません。スイッチが 1 つ欠けていると 1004 がその項目名を挙げて拒否します。沈黙は画面から項目が落ちただけで、「その入口を閉じる」という決定ではないからです。

ここには意図的に compare-and-set の根拠値を設けていません。これは Root だけが書く 1 つのドキュメントだからです。同じ内容の再保存は同じ状態の再確認であり、その都度 `server.account_policy_update` の Root 監査が 1 件追加され、実際に動いた各項目の前後の値が記録されます（それ以外に何も入りません。アカウント識別子も資格材料も入りません）。値は移行 `0008` が作る単一行のテーブルに永続化されるため、保存した変更は次のリクエストから即時に有効し、プログラムを起動し直しても再起動操作なしに同じ値を読み戻します。`config.yaml` には一切書き戻しません。あの行は削除できず、2 行目が生まれることもありません。

ポリシーの値は能力ではありません。三つの経路のうち「管理者による通常アカウント作成」と「セルフ登録」はすでに実装済みですが、ゲストの経路はまだ実装されていないため、未ログインのブラウザが照会できる入口の答えは、その経路が実際に存在する場所でのみ開きます。`GET /auth/capabilities` は匿名で読め、`no-store` で、応答はちょうど 2 つの真偽値——`sign_up_open` と `guest_open`——です。それぞれの求め方は「ポリシーが開けと言っている」**かつ**「その経路が本当に存在する」です。モード名も `updated_at` も、管理者の作成スイッチも、アカウント一覧や上限値も返しません。`invite` の書き込みは 2016（400）で拒否されます。この応答は「名前は知っているが、流れは未提供」という意味であり、1004 の「その値は存在しない」と意図的に文を分けています。申請を受け付ける経路が提供された `approval` は書き込めるようになり、それでもモード名が匿名の入口から外に出ることはありません。知らない値が `closed` に丸められることも、最も緩いモードにされることも決してありません。いずれかの流れが実際に提供される段階では、その能力がここに登録され、作成処理は自分のトランザクション内で有効なポリシーを読み直します。先に読んだ値をキャッシュすることはしません。

3 つのスイッチは Root 自身には及びません。管理者の作成（`POST /root/admins`）とサーバー手元の資格情報コマンド（`init-root`、`recover-root`）はこの表を読みません。だから `admin_create_standard` を閉じても、「管理者が 1 人もおらず、元に戻す道もない」サーバーにはなりません。他の書き込みエンドポイントと同じく、クロスオリジンでの利用を開く構成では `cors.allowed_methods` に `PUT` を列挙する必要があります。出荷時の既定は `GET`、`HEAD`、`OPTIONS` のみです。

## 管理者による通常アカウントの作成

認証済みのサーバーレベル管理者は `POST /admin/accounts` で通常アカウントを一回に一件作成します。リクエスト本体は `login_name`・`display_name`・使い捨ての `password` の三つのフィールドだけです。役割・アカウント種別・承認状態・活動用の欄は存在しません。「どの種の主体が生まれるか」はエンドポイント自身が定め、リクエストは定めないので、結果は `standard`・有効・サーバーレベルの授与なし・`must_change_password` 真となり、Root による管理者作成と同じ使い捨ての認証情報方針を適用します。

経路が開いているかは書き込みの瞬間に判定します。作成トランザクションはポリシー行を読み直し、`admin_create_standard` が閉じていれば 2017（403）を返します。Root がこのエンドポイントを使った場合も同じく拒否されます。このスイッチはどんな主体も除外しません。サーバーレベルの権限を持たない主体には 2011、正規化後のログイン名が埋まっている場合には 2012 を返します。管理者向けの「スイッチ事前読み取り」エンド点は意図的にありません。ポリシーの現在値を読み取れるのは依然 Root だけであり、権威ある答えは常に作成トランザクション内部の読み直しから出ます。新しいアカウントはその後は他のアカウントと同じ経路でシステムを使います。初回サインイン時にパスワードの変更が必須で、変更するまでの他の保護された入口はすべて 2010 を返します。作成されたアカウントはアカウントにすぎません。活動プロフィールも資産も名簿の席もなく、界面はそれを正直に伝え、設定済みの活動ロビーを装いません。

成功した作成は Root 監査ドメインに `account.create_standard` を一件追記し、操作者は実際に発行した管理者本人です（アカウントレベルの身元であり、Root でも system でもありません）。サーバーレベルの操作は、持たない `activity_id` を借りることはなく、そもそもそのテーブルの形状にその列はありません。この機能は監査照会エンドポイントを増やしません。アカウントを作成できる管理者でも Root ドメインの監査は引き続き読み取れず、それは Root 自身のものままです。他の書き込みエンドポイントと同じく、クロスオリジンで呼び出す配置では `cors.allowed_methods` に `POST` を列挙する必要があります。出荷時の既定は引き続き `GET`・`HEAD`・`OPTIONS` のみです。

## 管理者による通常アカウントカタログの維持

サーバーレベル管理権を持つ認証済み管理者は、作成以外にもこの名簿を扱えます。`GET /admin/accounts` はページ区切りのカタログで（`page`、上限 100 の `page_size`、`all`／`active`／`disabled` による `status` 絞り込み、`all`／`standard`／`guest` による `type` 絞り込み、ログイン名と表示名の部分一致による `q`）、作成時刻の新しい順に並び、`page`・`page_size`・`total` をそのまま返します。`GET /admin/accounts/{account_id}` は単一の詳細を、`PUT /admin/accounts/{account_id}` はその編集を読み、リクエスト本体は `display_name` と根拠にする `expected_display_name` の二つの項目だけです。

このカタログの範囲は好みではなく境界です。並ぶのは**サーバーレベルの授与を一切持たない**、しかも削除の終態に入っていないアカウントです（通常も訪問者も並び、`account_type` がその出所をありのまま示します）。`server_admin` を持つ人——このエンドポイントを叩いた操作者自身も含む——は Root の管理者カタログに属し、設定された Root は `accounts` テーブルに行を持たないので、構造上行になることがありません。二つのカタログは相互に排他的で、どちらもうっかり相手の行を並べることがありません。サーバーレベル管理権を持たない主体はカタログ・詳細・編集のいずれも 2011（403）、匿名は 2002 を受け取ります。通常アカウントと訪問者アカウントが全サイトのアカウントを列挙できないのは、ボタンを隠しているからではなくサーバー側の判定だからです。識別子の形が不正、アカウントが存在しない、その人は管理者、すでに削除済み、という四つの入力はすべて同じ 1001 を返すので、このエンドポイントは「あの人が管理者かどうか」を突き止める探針にはなりません。

表示名の編集は、身分段階と Root 側で承認済みのルールをそのまま引き継ぎます。ログイン名は作成以降変更できない身分の錨点で（画面もその旨を表示します）、認証情報・権限・安全状態（パスワード、初回変更フラグ、アカウント種別、そして別のサブリソースとして扱われる状態）はこの資料フォームに一切ありません——本体にそれらの項目を足せば 1004、UPDATE 文にそれらの列は現れません。並行保護も同じ形の compare-and-set です。根拠にした値がもう現在の値でなければ編集は丸ごと発生せず 2013（409）を返すので、処置は Root 側と一字一句同じ（サーバー側の現在の値を読み直してから決める）であり、本ステップは機械コードを一つも増やしません。拒まれた編集は監査を残さず、成功した編集は Root 域に `account.profile_update` を一件追記します。操作者は実際に発行した管理者本人（アカウント級の身分であり Root でも system でもない）で、前後の値は表示名の項目だけです。同様に、監査照会の HTTP エンドポイントは追加しません。

応答は表示して良い事実だけです——平文のパスワード、Argon2id ハッシュ、セッション材料、ログイン名の内部正規化キーは一切含みません。単一の記録に活動・資産・メッセージの三つの欄もありません。それらのモジュールは未実装であり、空配列や 0 を並べて調べられる真実を装ったりはしません。通常アカウントの削除と役割の変更もまだ開放されていません——今日その二つの能力は Root が管理者に対して持つ片側だけです。通常アカウントのログイン停止と再開は次の節に、認証情報のリセットはその次の節に書いてあります。クロスオリジンのブラウザからカタログを読むには `cors.allowed_methods` に `GET` を（出荷時既定はすでに `GET`・`HEAD`・`OPTIONS` を含む）、資料を保存するにはさらに `PUT` を列挙する必要があります。出荷時の既定はこのために緩和されていません。

## 管理者による通常アカウントのログイン停止と再開

`PUT /admin/accounts/{account_id}/status` は一つの通常アカウントのログインを停止または再開します。リクエスト本体は `status`（`active` または `disabled`）と、それの根拠にする `expected_status` の二つの項目だけです。動くのはこのアカウントがサーバー全体で持つログイン能力であり、ある活動の中だけのプレイヤー制限ではありません。停止すれば今後のログインは拒否され、すべてのデバイス上の既存セッションは取り消されて再ログインが必要になります。活動内での発言禁止、取引凍結、陣営制限はここでなく、まだ実装もされていません。

停止と再開は Root 側で承認済みの同じ基盤機構を利用します（状態の書き込みとセッション取り消しが同一のトランザクションで確定する）。ただし対象の適格性は独立に判定します。この通路が認めるのは、サーバーレベルの授与を一切持たず、削除の終態にも入っていないアカウントだけです。したがって一般の管理者は他の管理者を停止できず、自分自身も停止できません。これらの三種は「その人はいない」と同じ 1001 に収束し、設定された Root は `accounts` テーブルに行を持たないので、構造上行になりようがありません。承認の段階はサーバーレベル管理権のままです（持たなければ 2011、匿名は 2002）。本機能は活動スコープの役割をサーバーレベルの停止に格上げせず、新しい権限段階も追加していません。

再開が戻すのは「再度ログインできる」ことのただ一つです。停止中に取り消されたセッションは失効したままで復活しません（取り消しは戻せない事実であり、再開の通路はセッションを一つも触らない）。未完了の初回パスワード変更は引き続き義務として残ります（再開後のログインでも 2010 に阻まれます）。削除済みのアカウントをこれで復活させることもできません。複数の制限は以前から一つの Active ブール値で覆えるものではありません。`status` はログイン可否を、`must_change_password` はログイン後にまず変更が必要かどうかを、`account_type` は出所を語り、削除は終態です。四つの問いはそれぞれ別々の列と別々の通路が答えます。

並行と重複は同じ形の compare-and-set で扱います。`expected_status` がもうデータベースの現在の値でなければ、操作は丸ごと発生せず（状態も変わらず、セッションも取り消されず、監査も残らず）、2014（409）を返します。この一文は Root 側と一字一句同じで、処置も同じです。対象の現在の状態を読み直して改めて確認するのであって、同じボタンをもう一度押すのではありません。よって本機能も機械コードを増やしません。SQLite の単一書き込み者が並行を直列化するので、すでに確定した書き込みは戻らない事実であり、停止が確定した後の新しい操作はセッション解決の境界で拒否されます。成功した変更は Root 域に `account.disable` または `account.enable` を一件追記します。操作者は実際に発行した管理者本人（アカウント級の身分であり Root でも system でもなく）、前後の状態、前後の停止時刻、そして今回取り消したセッションの件数を携えます。拒まれた変更は監査を残さず、本機能も監査照会のエンドポイントを追加しません。

応答は変更後のサーバー側の現在の値と `revoked_sessions` をそのままただ返し、平文のパスワード、認証情報のハッシュ、セッション材料は一切含みません。訪問者アカウントも同じ通路を通ります。今日そのアカウントにはログインできる認証情報の通路がないため、停止しても通常は取り消すセッションがなく（件数は 0）、それでも状態の書き込みはありのままの事実です。画面は送信前に確認ダイアログで対象と影響範囲、「これは削除ではない」を言い切り、成功後はカタログと記録を読み直してサーバーの結果を表示します。クロスオリジン配置でこの書き込みを使うには `cors.allowed_methods` に `PUT` を列挙する必要があります。出荷時の既定はそのために緩和されていません。

## 管理者による通常アカウントの認証情報リセット

`PUT /admin/accounts/{account_id}/password` は、ある通常アカウントのログインパスワードを、管理者が自分で手渡す一時パスワードに置き換えます。リクエスト本体は `password` の 1 項目だけです。Root が管理者の認証情報をリセットするときに作った部品をそのまま再利用しています——同じパスワード導出の実装点、同じ「ハッシュを強制的に置き換える」リポジトリの書き方、同じ「対象を絞ったセッション取消」の刃——しかし実行者・対象の種類・管理範囲はそれぞれ別々に検証します。権限の段階はサーバーレベルの管理権のまま（なければ 2011、匿名なら 2002）、対象の範囲は「サーバーレベルの授権を一切持たず、削除の終態にも入っていない」あのカタログのままです。したがって一般管理者は別の管理者をリセットできず、自分自身もリセットできず、設定済み Root にも触れられません。これらの形は「その名前の人は居ない」と同じ 1001 に収束します。この経路は「どちら半分が足りない」を答えないからです。

1 回のリセットが成功すると 3 件の事実が同時に着地します。現行パスワードはただちに死に（ハッシュの列ごと置き換わるので旧平文は二度と検証を通らない）、そのアカウント名下の既存セッションはすべて同一トランザクション内で取消され（`revoked_sessions` はまさにその件数）、初回変更の義務は再び有効になります（本人が変更し終えるまで、次回のログインは従来どおり 2010 で止まります）。受け渡しの方式は承認済みの形沿用です。パスワードは実行者が自分で渡し、サーバーは生成せず、どんな応答にもエコーせず、既定パスワードも置きません。線下の手渡しはプロトコルの外側にあります。画面では、その文字列入力欄からリクエストへ至る一瞬だけ存在します。送信前に清空され、その後どこにも表示されず、ログ・監査・閲覧可能な設定・自動コピーのクリップボードにも書き込まれません。

リセットが変わらない事実も同じ率直さで書いてあります。停止状態はそのままです（あの UPDATE には `status` も `disabled_at` も無く、リセット後もその人はログインできず、復帰は引き続き `/status` の仕事です）。削除の終態がリセットで復活することはありません。初回変更をまだ果たしていない人は、リセットされても義務が消えません。承認待ちと却下済みの申請はこの名簿の範囲外です。それらの状態のアカウント識別子でリセットを試みても、存在しない人と同じ 1001 返ります。だからこの経路は誰も通過させられず、まだ承認されていない人にも届きません。承認はこれらの書き込み経路の副作用ではありません。

ゲストアカウント（`account_type` が `guest`）はこの経路の仕事ではありません。彼のパスワード欄はスキーマ側で NULL に凍結されており、代わりに値を書き込むことはゲストを通常アカウントへ昇格させるのと同じです。それは未実装の「ゲスト昇格」経路が決めるべきことで、パスワード 1 欄の PUT が決めるべきことではありません。ゲストはこの機能で唯一の新しい機械コード 2018（403）を受け取ります。あの一文は 1004 の「書き方を直して」、1001 の「対象を変えて」、2011 の「身分を変えて」のどれもではありません。権限は足りており書き方も正しい、待つべきはその経路が作られることです。カタログは定義上ゲストを載せているので、「この台帳に彼は居ない」とも申しません。

同時実行と重複：このエンドポイントは意図的に依拠値を持ちません。実行者には「現行のハッシュ」といった誠実な錨がありえず、取り繕った依拠値は自分が謳うものを検証しないからです。SQLite の単一書き手が各リセットを直列化し、每一次の成功は「ハッシュ交換＋セッション取消＋監査」のひとまとまりです。重複送信は、2014 式の「陳腐化した依拠値が拒否された」ではなく、実際にあと 1 回リセットを行います（その間に発行されたかもしれないセッションをもう一巡取消し、監査をもう 1 件残します）。界面はこの理により、結果が不明なときに自動で再送しません。ボタンの押し直しは再試行ではありません。成功したリセットは Root 域に `account.password_reset` を 1 件追加し、実行者は実際に起票したその管理者（アカウント単位の身元であり、Root でも system でもない）として記録され、初回変更フラグの前後値と今回の取消件数を携えます。拒否されたリセットは監査を残さず、この機能も監査照会の HTTP 入口を増やしません。

応答はリセット後のサーバー側現値と `revoked_sessions` を返すだけで、パスワードの影（接頭辞や長さすら）を一切エコーしません。クロスソース運用でこの認証情報を保存するには `cors.allowed_methods` に `PUT` を列挙する必要があります。出荷既定（`GET`、`HEAD`、`OPTIONS`）はこのために緩められていません。メールによる復旧、Root のネットワーク経由の復旧、独立した一時復旧コード体系は、ここにはなく、このステップによって存在し始めることもありません。

## 承認待ちの登録と本人による状態照会

`self_register_mode` を `approval` にすると、`POST /auth/register` はすぐにサインインできるアカウントを作るのではなく、申請を受け付けます。許可された三項目は同じで、パスワードは本人が選び、生まれるのもサーバーレベルの授与を持たない通常アカウントです。違いは状態だけ。`active` ではなく `pending` になり、安定したアカウント識別子は提出の瞬間から存在します。統一アカウント・モデルでは、承認された日に別人へ切り替わる設計にしないためです。ログイン名はその瞬間から占有され、`must_change_password` はオフのまま。申請者が待っているのは承認であってパスワードではありません。

「待機」は半分使える状態ではなく、それは言い回しではなく実装で担保されます。サインインはアカウントが `active` かどうかだけを見るので、`pending`（および `rejected`）はパスワード誤りと同じ形——同じ 2001 で、どの名前が存在するかは一切分かりません。セッションストアは利用不可のアカウントに対する発行も主体の解決も拒否するため、Cookie もベアラー秘密も、待機中の人が通常の業務へ届くための「制限付きセッション」も存在しません。管理者の通常アカウント名簿はこの二状態を範囲外にし、識別子を直接指定して四つの経路（詳細・表示名編集・停止／再開・認証情報リセット）を叩いても 1001——「この名簿にその人はいない」です。承認と却下はこのバージョンでは未提供で、HTTP の入口もコンソールも裏口もないため、ここで誰でも通り抜けることはできません。

申請者自身の状態照会は `POST /auth/registration-status` を通りますが、答えは認証情報をそのつど証明した人にだけ届きます。本体は `login_name` と `password` の二項目で、検証はサインインと同じ Argon2id の認証情報です。成功時の応答は結局（`pending`・`approved`・`rejected`）、提出時刻、そして決定がある場合の決定時刻だけで、他を含みません。誰が審査したかも、却下の理由も、待ち位置も、他人の申請も、セッション材料もありません。この経路は `Set-Cookie` を書かずセッション行も作らないので、有効期限や失効境界を持つ「一時状態証明書」は必要になりません。同じ理由で POST のみです。秘密は URL にもクエリ文字列にも乗らず、プリフェッチされず、アドレス欄に貼られません。名前が存在しない・ゲストアカウント・パスワード誤りはすべて 2001 に収束し、この入口はサインイン以上の列挙信号を作りません。速度制限はサインインと同じ台帳を使うため、扉を一つ増やしてもパスワード推測の予算は増えません。2020（403）は「誰であるかを証明した後」にだけ出る唯一の答えです。アカウントは実在し、あなたが本人ですが、それは承認経路を通っていない——処置は「待ち」でも「名前を変える」でもなく「サインインを使う」です。

モードの切替は新しい提出だけを扱い、過去の申請はその場に留まります。Root がモードを `closed` に戻しても `open` に替えても、提出済みの申請について何も決定はしません。既に置かれた行は `pending` のままで、本人は照会でき、通過も削除もされません。同じログイン名での再提出は誰と同じ一意索引に当たる（2019）ことになります。承認待ちも却下済みも名前を占有し続けるため、却下された人は同じ名前でもう一度はできず、他の人がその名前を得ることもできません。

移行 `0009` はアカウント状態に `pending` と `rejected` を追加し、`reviewed_at` という時刻欄を一つ加えます。状態照会がこの欄で「かつて承認され、後に停止された人」と「申請したことがない人」を区別します。決定時刻は待機中・却下済みの行に載ることはなく、新しく作られた行に決定時刻が入ることもありません。提出は Root 域に `account.self_register` を一件追記し、操作者は system 主体です（匿名の請求には記録すべき信頼できる主体がありません）。書き込まれる `status` は実際に確定した状態なので、「申請を受け付けた」と「サインインできる人を作った」は監査上で区別できます。だからといって監査照会の入口は作りません。クロスオリジンの構成ではこの二本のパスのために `cors.allowed_methods` に `POST` を列挙する必要があります。出荷時の既定（`GET`・`HEAD`・`OPTIONS`）は変えていません。ログイン前の入口能力は引き続き二つの真偽値だけで、「今使えるのか待機なのか」という問いもモード名も、書き込みそのものが答えて、匿名の項目を増やして推測させることはありません。

## リリース後の利用方法（予定）

- 誰か一人が自分のマシン（Windows または Linux）でサーバーをホスト
- 他の参加者は同じローカルネットワーク内のブラウザから接続
- 第三者登録は不要。データはホスト機だけに保存

## 対応言語

簡体中文、繁体中文（台湾）、English、日本語。

## ソースからのビルド

Windows 実行ファイルのアイコンは生成されるもので、バージョン管理には含まれません。`cmd/evernight-server/resource_windows_*.syso` は `assets/icons/EvernightRealmBackendRounded.ico` から生成されます。クローン直後はビルドの前に

    python tools/icons/generate_icons.py

を実行してください。実行しないとアイコン無しの実行ファイルができあがりますが、`go build` は何も報告しません。`python tools/icons/generate_icons.py --check` は現状を照合するだけで、何も書き込みません。詳細は `tools/icons/README.md`。

このプロジェクトにはホスト型 CI がありません。コミット前にローカルの品質入口 `go run ./tools/check`（バックエンドのフォーマット・`go vet`・テスト、およびフロントエンドのゲート）を実行してください。
