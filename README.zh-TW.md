# 長夜幻境（EvernightRealm）

> 在自己的機器上，為你的小圈子搭建一座私密的虛擬世界——管理活動、扮演角色、交換虛擬資產。

[English](./README.md) · [簡體中文](./README.zh-CN.md) · [繁體中文（臺灣）](./README.zh-TW.md) · [日本語](./README.ja-JP.md)

## 這是什麼？

長夜幻境是一個自主部署、離線優先的平臺，面向小規模玩家群體：一起推進沉浸式活動、扮演角色、交易虛擬資產——全部在區域網內完成，不需要公網、雲賬號或遙測。

## 功能規劃（開發中）

- **沉浸式活動**：為你的群體編排場景、階段與事件
- **角色與身份**：玩家、NPC 與管理員的角色，共處一個私密世界
- **虛擬資產**：物品有真實歸屬，交易可審計
- **私密聊天**：訊息只留在你自己的伺服器上
- **離線優先**：一切執行在你自己的機器上，不依賴雲服務

## 當前狀態

長夜幻境正在積極開發中，尚未釋出穩定版本。服務端現在可以建置為**單一可執行檔**：同一個連接埠同時提供網頁介面與 API 端點，瀏覽器直接開啟它的位址即可使用，不需要另外部署靜態服務。內嵌的網頁客戶端今天已是身份階段的完整應用——伺服器入口（位址保存、連通性偵測與唯讀的 Root 初始化卡）、登入、三種模式的自助註冊、申請人本人的狀態查詢、訪客進入、本人的工作階段／裝置／改密自助管理，以及 Root 主控台與管理員主控台；它現在也通到**活動管理**（建立、目錄、編輯、開放／停止／歸檔，以及 Root 那側的管理人指派），以及活動內的**陣營管理**（列表、建立、編輯、排序與可用／停用）。現在也通到活動內的**成員名冊**（列出參加者、把一個既有帳戶加入、修改他在本場活動內的暱稱）與**玩家目錄可見性**：管理側多了一欄四態設定卡與名冊裡每一行「只可收緊」的覆蓋開關，玩家側的目錄、單筆直查與本人投影三條讀法已經可用，而且**玩家端的目錄與資料頁面已接上這三條**：名單、按暱稱搜尋、陣營候選與分頁、單筆受權詳情，以及目錄收起時照舊讀得到的本人資料。尚不存在的是活動裡面除陣營與成員名冊以外的東西——把成員分進陣營、資產、聊天、階段與排程——所以剛建好的活動除了您自己建立的陣營與加入的成員外如實是空的。玩家端不再是佔位：它列出這個帳戶所屬的活動，並在那場活動的開關允許時讓玩家自己選陣營；NPC 主控台仍照實顯示「尚未接線」的佔位說明。活動內部，管理側也多了**標籤定義**（建立、列表、編輯、停用，以及一個逐筆標籤各自的旗標，決定該活動的成員能否讀取定義本身），玩家側則能讀取已公開的標籤；把標籤貼在玩家身上這件事尚不存在，也沒有任何畫面把標籤假裝成角色或權限。管理面另也維護**玩家業務狀態**：每位成員一個目前狀態，取值是七個穩定內建值（`normal`、`suspended`、`eliminated`、`dead`、`arrested`、`offline`、`custom`）加上只屬於該活動、只能停用無法刪除的自訂狀態定義，並可為任一狀態依活動覆寫顯示名稱；名冊、玩家目錄與本人投影都以純文字顯示這一格。業務狀態不是連線狀態，本版本也不會因它凍結帳戶、清空資產或把人移出活動。名冊每一行現在也帶著**六項彼此獨立的限制**（登入、聊天、私聊、交易、轉賬、使用物品）：出廠全不限制、逐欄經白名單比較-and-set 編輯。`restrict_login` 只收回**這一場活動**的訪問資格——全域登入、既有會話與其他活動不受影響——被限制的人照舊讀得到自己的六欄。聊天、交易、轉賬與使用物品尚未上線，那五欄今日只是服務端將來的判定依據。

服務端另提供一個維運命令來產出**一致性備份包**：單檔資料庫快照（服務執行中即可產出，不是複製活躍的 WAL 主檔），連同設定檔與媒體／文件／上傳目錄，逐檔記錄大小與 SHA-256 並附一份清單。與之配套的 `restore` 命令能把這份包還原成一個**全新的空資料目錄**：逐檔依清單重算校驗和，落地前後各讀一次快照的資料庫事實並與清單對照，**不覆蓋任何既有目錄**（要覆蓋請先自行備份該目錄），拒絕比目前執行檔更新的資料庫結構版本，並把這次還原本身寫成一筆伺服器端審計記錄。備份包還不能加密，舊包也不會自動清理。

一次性 Root 初始化**只有本機命令這一條入口**：

    evernight-server init-root --password-stdin --data-dir <資料目錄>

它從標準輸入讀口令（前兩行是口令與確認），把 Argon2id 編碼寫進該資料目錄的 `config.yaml`，不輸出任何秘密——不寫明文，也不會自動產生或顯示一個「出廠口令」。交出伺服器最高權限的授權依據是「能在伺服器主機上執行命令」，所以這一步不開任何 HTTP 端點、不佔連接埠；CORS、客戶端自報的位址、介面上隱藏按鈕都不構成授權。服務持有單寫入實例鎖時、`ER_SECURITY_ROOT_PASSWORD_HASH` 蓋著檔案時、或審計表尚未建立時，本命令一律拒絕；寫成功之後也不會再開放第二次——要換口令，走服務內的已認證改密流程（Root 登入後 `POST /auth/password/change`）；只有口令真的遺失了，才用下面那條本機恢復通路。只讀的 `evernight-server root-status` 能回答「現在有沒有 Root」，它不建立也不改動任何檔案，而且只回答這麼多：不給出配置路徑、雜湊或任何引導秘密。成功與拒絕都會寫進 Root 審計表，且不記錄口令。

Root 口令遺失後的恢復同樣只有本機命令這一條入口：

    evernight-server recover-root --password-stdin --confirm --data-dir <資料目錄>

它也只從標準輸入讀新口令（前兩行是口令與確認），不接受命令列上的口令值，並且要求服務已經停止：運作中的服務把憑據讀在記憶體裡，改設定檔不會讓它回頭更新，那樣只會做出「終端說成功了、舊口令其實還登得進去」這種比拒絕更難查的狀態。恢復不問也不驗舊口令——能在這台主機上執行命令、能讀寫那份設定檔，就是這個動作全部的授權依據；因此它也不設後門口令、不產生可下載的恢復檔、不開任何 HTTP 端點。成功時設定檔裡那份憑據被覆寫為新口令的 Argon2id 編碼，Root 名下全部會話在同一筆資料庫交易裡被撤銷（下一個請求即被拒），並留下一筆 `server.root_recover` 審計記錄；一般帳戶的會話一枚都不動。撤銷與審計寫不進去時，設定檔會被換回原本那份憑據、回報失敗，可用狀態與動筆前一致（連回滾都失敗的雙重故障會以 Error 寫進執行日誌檔案，並明確要求人工補記）。`--confirm` 是必須明確給出的旗標：覆蓋的代價是舊口令永久失效加上 Root 全部裝置登出。設定檔裡還沒有憑據時本命令拒絕並指向 `init-root`；已有值即使壞到解不開（那種狀態下誰都登不進去）也照樣能恢復——這正好是 `init-root` 會拒絕的形態，兩條路各自只有一種成功形態。

首次啟動的介面要如實顯示「還沒初始化」，服務端因此另外回答一個唯讀的 `GET /root/init-status`：只有設定檔是否存在、是否已有 Root 憑據、環境變數覆蓋是否處於設定狀態這三個布林值，不回傳路徑、長度或任何憑據片段，也不寫資料庫、不寫審計。它把「有沒有」說出來，不說「怎麼改」——初始化 Root 仍然只有 `init-root` 這一條在伺服器本機上執行的通路（遺失口令後的覆寫是上面那條 `recover-root`，兩者都不提供網路入口）。

## 登入與管理自己的帳戶

身份階段的功能現在已經實作、可以使用：登入、查看目前工作階段、登出、管理自己的裝置、修改自己的口令，以及 Root 建立帳戶、管理管理員目錄、停用與恢復管理員登入、重設管理員登入憑據、軟刪除管理員（見下一節），以及 Root 設定伺服器的帳戶建立策略（再下一節），還有管理員在該策略下建立一般帳戶、翻閱一般帳戶目錄、讀取與維護單筆資料、停用與恢復某個一般帳戶的登入、重設某個一般帳戶的登入口令，以及軟刪除一個一般帳戶或訪客（建號見上一節，目錄、資料、停用、憑證與刪除各看後面五節）。限制同樣如實寫在前面兩點。其一，帳號只從以下幾個入口產生：Root 憑據本身由伺服器本機的 `init-root` 建立，伺服器管理員由 `POST /root/admins` 開設，一般帳戶則要嘛由 `POST /admin/accounts` 建立——這條只在 `admin_create_standard` 開著時成立，而且只認已認證的伺服器級管理員——要嘛由自助註冊 `POST /auth/register` 產生：它匿名可讀、只在 `sign_up_open` 為真時開放，交回一個由本人自設口令的一般帳戶，不簽發任何工作階段，也永遠建不出管理員。自助註冊現在已實作，且開放、審批、邀請碼三種模式都已上線（邀請碼模式由 `POST /auth/register` 把一枚有效碼核銷成一個可立即登入的普通帳戶，`GET /auth/capabilities` 的 `invite_code_required` 告訴共享表單何時顯示邀請碼欄位）。訪客進入也已實作，而且就是它被刻意限制的那條路：`POST /auth/guest` 在同一筆交易裡建出一個**由伺服器命名**、`account_type` 為 `guest` 的帳戶並簽發一枚工作階段，而登入前的介面只有同一個匿名端點回過來的 `guest_open` 才決定要不要露出這扇門。帳戶名由伺服器產生（`guest_<uuid>`），請求裡沒有一格能填它；暱稱只是展示資訊——允許與他人同名、不是憑據，也沒有任何通路能拿它換回一枚工作階段。訪客不攜帶任何伺服器級授予，所以管理端與 Root 端對他一律回 2011，他也枚舉不到全站帳戶。工作階段本身是普通的：到期、閒置、登出撤銷與裝置名額規則和其他帳戶一字不差，而登出或失去這一枚就結束了這一趟。這條通路還要如實寫明的第二件事：只有人主動按下才會建立，頁面載入、重新整理與重連都不寫任何東西，也沒有排程批次清理舊訪客行的工作。其二，服務端自己不做 TLS 終結：預設監聽是 `127.0.0.1:5206` 上的明文 HTTP，只有當請求確實經 TLS 抵達時（也就是你在它前面自行放一層終結 TLS 的反向代理），工作階段 Cookie 才標 `Secure`、才下發 HSTS；程式不含任何憑證處理，HTTPS 是這套程式之外的部署選擇。

身份相關的端點沒有版本前綴——沒有 `/api/v1`：

- `POST /auth/root/login`（只用 Root 口令）與 `POST /auth/login`（登入名加口令）。每次成功都簽發全新工作階段並覆寫舊 Cookie，舊 Cookie 不會被沿用。
- `GET /auth/session`、`POST /auth/logout` 與 `POST /auth/session/rotate`——讀取目前工作階段、撤銷恰好這一枚工作階段（幂等），或換發本工作階段的秘密。
- `GET /auth/devices` 與 `POST /auth/devices/revoke`——只列舉並撤銷目前登入主體名下的工作階段；沒有任何請求能指名別人的裝置。
- `POST /auth/password/change`——必須在請求中當場交出目前口令；成功後該主體名下全部工作階段（含這臺裝置）一起被撤銷。

瀏覽器路徑的工作階段秘密放在 `HttpOnly` Cookie 裡；原生客戶端從回應標頭讀出後以 bearer 秘密攜帶。登入失敗反覆發生後按「來源位址與登入目標」限流（HTTP 429，附 `Retry-After`），Root 入口同樣適用，且被擋的嘗試不會指出撞上的是哪個帳戶。`device_policy` 設為 `single` 或 `limited` 時，會丟掉較舊的工作階段，或在名額用盡後拒絕新的登入。帶有「首次登入必須改密」標記的帳戶，只放行目前工作階段查詢、登出與改密流程，其餘受保護端點一律回 2010，直到改密完成。

兩條維運邊界維持不變：備份與還原仍是 `evernight-server` 子命令，沒有 HTTP 入口；審計記錄只由服務層寫入，仍然沒有審計查詢端點或網頁主控台。執行日誌按自然日切檔，預設不自動刪除（`retention_days=0`）：不讓日誌無限增長是維運者的工作，程式本身不會隨時間給日誌總量設上限。

## Root 管理管理員目錄

Root 的工作階段是第一批人力操作者進來的管道：`POST /root/admins` 帶 `login_name`、`display_name` 與 `password` 開設帳戶；`GET /root/admins` 是分頁的管理員目錄（`page`、`page_size` 上限 100、`status` 可按 `all`／`active`／`disabled`／`deleted` 篩選，依授予時刻由新到舊排序，並回顯 `page`、`page_size` 與 `total`）；`GET /root/admins/{account_id}` 讀取單筆資料；`PUT /root/admins/{account_id}` 編輯它；`DELETE /root/admins/{account_id}` 軟刪除該帳戶，請求本體一個欄位都不帶——多帶任何欄位都會被打成 1004；`PUT /root/admins/{account_id}/status` 停用或恢復該帳戶的登入，請求本體只有 `status` 與 `expected_status` 兩個欄位；`PUT /root/admins/{account_id}/password` 重設該帳戶的登入口令，請求本體只有 `password` 一個欄位。讓新帳戶成為管理員的是端點本身，不是請求內容：這裡沒有 `role`、`account_type` 或 `subject_kind` 可以填，多帶的欄位會被打成 1004。授權的輸入是「這次請求解析出的主體就是 Root」，所以普通帳戶與管理員自己的工作階段都拿到 2011（403）——管理員既不能建立或管理同級管理員，也不能把自己昇格，重新登入一次同樣改變不了這件事。目錄只列管理員帳戶；配置的 Root 不是其中一行，也永遠不會變成一條可被普通帳戶介面編輯的記錄。

初始口令由 Root 親自交出、且只用一次。它走的是與其他任何憑據同一套 Argon2id 服務，帳戶帶著 `must_change_password` 入庫，伺服器在任何回應裡都不回顯該口令，也不存在任何預設口令。於是那個人首次登入拿到的工作階段，只被允許存取查看目前工作階段、登出與改密這一組入口——其餘受保護端點一律回 2010，直到改密完成——而改密成功會讓該帳號的所有裝置退出。這些規則本就適用於任何帳戶，本步補上的是那面旗標的來源。

登入名的唯一性走的是與登入通路同一個正規化鍵（NFKC 加全量大小寫折疊），並由帳戶表上的唯一索引兜住：已被佔用的名字回 2012 且不建立任何東西，所以連點兩次、或在回應丟失後整筆重試都不會多出第二個帳戶，而那一句拒絕也不會回顯既有帳戶的任何資料或任何憑據。建立帳戶、授予 `server_admin`、把 `admin.create` 追加進 Root 審計，全部落在同一個交易裡——任何一處失敗都不會留下半成品管理員，也不會留下無痕的特權變更——而審計記錄裡只有身分欄位，絕沒有口令或其雜湊。

編輯的白名單只有一個欄位：`display_name`，連同它所依據的現值 `expected_display_name` 一起提交。狀態、憑據、首次改密旗標與帳戶類型不在這條通路之內，UPDATE 語句也只碰這一欄——「儲存普通資料順帶覆蓋隱藏欄位」在語句形狀上就不存在。若儲存的值在頁面打開之後已被改動，整個編輯以 2013（409）被拒絕且什麼都不寫入，這與改密使用的同一套 compare-and-set 保護同源。標識格式不對、帳戶不在目錄、帳戶確實不存在，都收到同一個 1001，這個端點因此不是列舉探針。回應只含可展示事實——絕不帶密碼雜湊、工作階段秘密、恢復碼或任何配置——Root 的每次成功編輯都會追加一條 `admin.profile_update` 稽核，僅帶顯示名的前後值；被拒的編輯不寫任何記錄。

停用與恢復走另一條只有一個欄位的端點。停用後新登入會被拒絕（與其他登入失敗同形，伺服器不會說「這個人被鎖了」），該帳戶現有會話在同一筆資料庫交易裡全部撤銷，並追加一條帶前後狀態、`disabled_at` 前後值與 `revoked_sessions` 的 `admin.disable` Root 稽核；主體此刻是否可用依每個請求現讀資料庫，被停用者的既有會話在任何受保護入口都換不出受信主事人。恢復（`admin.enable`）只恢復重新登入的能力：停用時撤銷的會話保持已撤銷、不會復活，尚未完成的首次改密義務仍然有效；Root 與管理員停用其他管理員都不構成合法目標。狀態寫入是對呼叫端所見現狀的一次 compare-and-set——對著過期依據或重複操作都以 2014（409）拒絕且什麼都不發生：不改狀態、不撤會話、不記稽核。已明確完成的操作不倒退，只有停用生效之後發起的新操作被拒絕。UPDATE 語句只碰 `status` 與 `disabled_at` 兩欄，「停用順帶清憑據或旗標」在語句形狀上就沒有發生點；被停用者仍留在目錄裡（授予列保留），這正是他可被恢復的前提。

重設登入憑據是第三條單欄位子資源端點。`PUT /root/admins/{account_id}/password` 只帶 `password` 一個欄位——Root 親自交出的暫時口令，交付語意與開設時同一套批准方案：伺服器不生成口令、任何回應不回顯，口令只在請求本體裡出現一次；日誌、稽核與回應都不含口令材料，線下交付管道在協議之外。一次成功的重設在同一筆交易裡落地三件事：舊口令立即失效、名下全部會話即刻撤銷（`revoked_sessions` 是權威計數）、該帳戶下次登入必須改密（沿用與本人改密同一個 2010 門閂）。它與本人改密是兩個用例而不是同一個：本人改密要交出現行口令作再認證並清掉義務，Root 重設他人恰恰發生在拿不出——也不該拿出——現行口令的場合，成功後義務被重新設為生效。重設因此不帶 compare-and-set 依據值：任何湊出來的錨點驗證的都不是它宣稱的東西；重複提交不是 2013/2014 那種「陳舊依據被拒」，每一次都是完整生效的重設，各留一筆 `admin.password_reset` 稽核（記改密義務旗標前後值與撤銷數量，絕無憑據），所以介面在結果不明時不得自動補發。重設不改的事實同樣真實：UPDATE 語句不碰 `status` 與 `disabled_at`——對停用中的目標重設成功，目標仍停用、新登入仍被拒（與其他登入失敗同形），要恢復登入仍走 status 那條通路；重設也不是撤權、改名或刪除，授予列原樣保留。格式不對的標識、幽靈標識、未持有授予的帳戶與已物理刪除的目標一律回 1001——已軟刪除的目標回 2015，因為那裡的記錄確實還在，拒絕的是它的狀態；非 Root 回 2011，形狀不合格的口令回 1004 並點名 `password` 欄位。

刪除管理員是一種狀態，不是清庫。`DELETE /root/admins/{account_id}` 不帶請求本體，一次成功在同一筆交易裡落地三件事：登入停止、名下全部會話即刻撤銷（回應給出權威計數 `revoked_sessions`）、追加一條 `admin.delete` 的 Root 稽核，內容正是後來者解釋這次刪除所需的身分快照——登入名、改寫前與改寫後的顯示名、狀態前後值、`deleted_at` 前後值、撤銷數量——且絕不含任何憑據材料。帳戶那一列本身留下：它的標識、它的登入名鍵、它的授予列、它的會話列、它的稽核列，全都仍然指向同一個穩定帳戶，因此歷史操作不會變成指向虛無，也不會被悄悄改記到 Root 名下。物理清庫因此不在本步實作，也不是隨手能做的事：被引用的列根本刪不掉。刪除是終態。沒有恢復入口——`PUT /status` 會拒絕，因為停用與刪除是兩種狀態，既有的恢復登入通路不得讓已刪除帳戶復生——而對已刪除的目標發起編輯、重設憑據或再次刪除，都以 2015（409）回覆，這個機器碼的意思就是「這個人存在，但已刪除」。資料庫層面另有一道觸發器讓已刪除的列不可再被改寫，未來任何寫通路都沒辦法悄悄把它撈回來。有一處可展示資料在刪除時被匿名化：`display_name` 改寫為 `DEL_<UTC 日期>_<原名>` 形狀的佔位字串，長度沿用同一份預算，於是目前記錄不再把舊名字呈現為現行名字。而只追加的歷史刻意不動——刪除之前寫下的稽核仍保留它當時記錄的名字，那正是舊操作至今可解釋的理由。登入名的正規化鍵繼續佔用，因此不可復用：已刪除帳戶的名字沒辦法再註冊一次。已刪除的管理員仍列在目錄裡（`status=deleted`，目錄與單筆回應帶 `deleted_at`），其詳情唯讀。不提供批次刪除，請求也不帶原因文字；配置的 Root 憑據不是目錄裡的一列，因此永遠不構成刪除目標。

另有兩個回應欄位按「只增不刪」的演進規則補上：登入與查看目前工作階段的回應現在帶 `roles`，內容是服務端為該主體現讀到的授予（沒有授予時欄位缺席），客戶端據此決定載入哪些入口。它本身不授予任何東西——每個端點仍在每次請求上重讀可信主體。


若部署要讓組態白名單裡的跨來源瀏覽器呼叫這些端點，`cors.allowed_methods` 必須把 `PUT` 與 `POST` 一起列入，刪除端點還要列入 `DELETE`——出廠預設仍是 `GET`／`HEAD`／`OPTIONS`，來源白名單始終是組態決定，本節不為此放寬任何邊界。

## 伺服器的帳戶建立策略

三個值說出這個部署對「新增可登入的一般帳戶」的打算：`admin_create_standard`（管理員能否建立一般帳戶）、`self_register_mode`（`closed`、`open`、`approval` 或 `invite`，四者都已上線：開放建出可用帳戶，審批落成待批申請，邀請碼把一枚有效碼核銷成可用帳戶）與 `guest_enabled`（能否建立臨時的訪客帳戶）。`GET /root/account-policy` 讀取這三個值，`PUT /root/account-policy` 把它們當成一份文件一次寫入。讀寫都只有 Root 可以：管理員自己的會話拿到 2011，沒帶憑據拿到 2002，跨站來源在碰到資料庫之前就被 2005 擋下——「管理員能不能建立一般帳戶」是這個端點會設定的值，而「管理員能不能改伺服器策略」根本不是一個值。三個欄位彼此獨立，而且一個都不能少：漏掉一個開關會被打成 1004 並點名那個欄位，因為沉默是介面漏了欄位，不是「把那個入口關掉」的決定。

這裡刻意沒有 compare-and-set 依據值，因為這是一份只有 Root 會寫的文件：重複保存是同一次狀態的再一次確認，每一次都追加一條 `server.account_policy_update` 的 Root 稽核，內容是每個真的移動過的欄位的前後值（此外沒有任何東西——不含帳戶標識，也不含任何憑據材料）。值持久在遷移 `0008` 建立的那張單行記錄表裡，所以存好的變更對下一條請求立即生效，重開程式後不需要任何重啟動作也會讀回同一份值，而且一律不寫回 `config.yaml`；那一行刪不掉，也不可能多出第二行。

策略值不等於能力。合成的算法仍然是「策略說要開」**而且**「這條通路真的存在」——只是此刻四條通路都已上線，所以那三個布林現在如實跟著開關走：`GET /auth/capabilities` 匿名可讀、`no-store`，回應恰好三個布林——`sign_up_open`、`invite_code_required` 與 `guest_open`。`guest_open` 只是登入前介面關於訪客那扇門的提示，從來不是准入判定：`internal/guestacct` 會在寫入那筆交易裡現讀策略，所以拿到一份過期的 `true` 也進不去。`invite_code_required` 只在生效模式為 `invite` 時點亮，讓共享的註冊表單知道要不要顯示邀請碼欄位；它只是顯示依據，既不是模式名字，也不是准入判定（寫入那一刻的事務會重讀策略）。它不回顯模式名字、不回顯 `updated_at`、不含管理員建號開關、不含任何帳戶清單或閾值。四個模式名字（`closed`、`open`、`approval`、`invite`）現在都寫得進去；寫入一個尚未上線的模式會被打成 2016（400），這句話的意思是「名字認得，流程還沒上線」，與 1004 那句「這個值不存在」是兩句刻意分開了的話，只是本版本已沒有任何被批准的模式處於那種狀態。任何不認識的值永遠不會被往下收成 `closed`，也不會被往上放成最寬的模式。日後某條流程真的上線時，它會登記自己的那一項能力，並在自己那筆交易裡現讀當下生效的策略，而不是快取一份先前讀到的值。

這三個開關也不會伸到 Root 自己身上：開設管理員（`POST /root/admins`）與伺服器本機的憑據命令（`init-root`、`recover-root`）都不讀這張表，所以把 `admin_create_standard` 關掉，不會讓一台伺服器落到「既沒有管理員、也沒有找回來的路」的狀態。與其餘寫入端點相同，開放跨來源呼叫的部署要把 `PUT` 列進 `cors.allowed_methods`，出廠預設仍然只放行 `GET`、`HEAD` 與 `OPTIONS`。

## 管理員建立一般帳戶

已認證的伺服器級管理員透過 `POST /admin/accounts` 一次建立一個一般帳戶。請求本體恰好帶 `login_name`、`display_name` 與一次性 `password` 三個欄位：沒有角色、帳戶類型、審批狀態或活動的格子，因為「新建的是哪一類主體」由端點決定而不是由請求決定——`standard`、啟用中、不帶任何伺服器級授予、`must_change_password` 為真，與 Root 開設管理員使用同一套一次性憑據策略。

通路開不開在寫入那一刻判定：建立交易現讀策略列，`admin_create_standard` 關閉時回 2017（403）——Root 走這條端點也一樣被拒，這個開關不豁免任何主體；沒有伺服器級權限的主體回 2011，登入名（正規化後）已被佔用回 2012。這裡刻意沒有給管理員的「開關預讀」端點：策略現值仍然只有 Root 讀得到，權威答案永遠出自建立交易內現讀的那一刻。新帳戶之後和其他帳戶走同樣的路使用系統：首次登入必須改密（改完之前其餘受保護入口一律 2010）。建出來的帳戶只是一個帳戶——沒有活動檔案、沒有資產、不在任何名冊上——介面如實說明，不冒充已配置好的活動大廳。

一次成功建立會在 Root 域審計追加一條 `account.create_standard`，操作者是真實發起的那位管理員（帳戶級身分，不是 Root，也不是 system）：伺服器級動作不會去借一個它並不擁有的 `activity_id`，那張表的形狀上也沒有這一欄。本功能不新增任何審計查詢入口：能建號的管理員依舊讀不到 Root 域審計，那仍然歸 Root 自己。與其餘寫入端點相同，開放跨來源呼叫的部署要把 `POST` 列進 `cors.allowed_methods`；出廠預設仍只放行 `GET`、`HEAD` 與 `OPTIONS`。

## 管理員打理一般帳戶目錄

已認證的伺服器級管理員除了建號，還能翻閱與修剪這本名冊：`GET /admin/accounts` 是分頁目錄（`page`、`page_size` 上限 100、`status` 依 `all`／`active`／`disabled`／`deleted` 篩選、`type` 依 `all`／`standard`／`guest` 篩選、`q` 依登入名或顯示名做子字串比對），依建立時刻由新到舊排序，並回顯 `page`、`page_size` 與 `total`；`GET /admin/accounts/{account_id}` 讀取單筆詳情；`PUT /admin/accounts/{account_id}` 編輯它，請求本體只有 `display_name` 與它所依據的 `expected_display_name` 兩個欄位；`DELETE /admin/accounts/{account_id}` 軟刪除他，請求本體一個欄位都不帶——`{}` 收得下，帶任何欄位都打成 1004，而且刻意不設依據值欄位：操作者對「現行刪除時刻」拿不出誠實的錨點，作數的是狀態機守衛。成功回 HTTP 200 而不是 204，回應本體是 `{"account": {刪除之後的真相}, "revoked_sessions": <int>, "request_id": "…"}`。

這本目錄的範圍是一條邊界而不是一句偏好：它列的是**不攜帶任何伺服器級授予**的帳戶（普通與訪客都在內，`account_type` 那一欄就是把來源如實講出來），而終態不把人從名冊上抹掉——已 `deleted` 的帳戶與已 `retired` 的訪客（被綁進別人那一行的人）都仍然列出，正因為列得出來，後來的人才查得到過去那筆操作指的是誰。持有 `server_admin` 的人——包括敲這條端點的操作者自己——歸 Root 的管理員目錄；設定 Root 根本不在 `accounts` 表裡，結構上不可能成為一行。兩本目錄因此互斥，誰也不會「順手」把對方的人列進來。沒有伺服器級管理權的主體讀目錄、讀詳情與編輯都拿 2011（403），匿名拿 2002：普通帳戶與訪客因此沒辦法枚舉全站帳戶，這件事成立在服務層的判定上，不靠介面藏起入口。標識格式不合法、帳戶不存在、他是管理員、他還在審批鏈門外，四種輸入都收到同一個 1001，這條端點因此不是「某個人是不是管理員」的探針。已刪除與已退休刻意不在這四種裡：詳情讀得到 200 而且是唯讀的，每一條寫入通路都回 2027 或 2028，而不是假裝這個人查無著落。

顯示名的編輯沿用第一部分與 Root 那側已經規定的規則：登入名自建號起是不可修改的身分錨點（介面也這麼講），而憑證、權限與安全狀態（口令、首次改密旗標、帳戶類型，以及另走一條子資源的狀態）都不在這張資料表單裡——本體多帶任何隱藏欄位都打成 1004，UPDATE 語句裡那些欄位連出現都沒出現。並發保護是同一形的 compare-and-set：依據值已不是資料庫現值時整個編輯不發生並回 2013（409），處置與 Root 那邊逐字相同（重讀服務端現值再決定），所以本步不新增任何機器碼。被拒的編輯不留審計，成功的編輯在 Root 域追加一條 `account.profile_update`，操作者是真實發起的這位管理員（帳戶級身分，不是 Root 也不是 system），前後只有顯示名那一欄的舊值與新值；本功能同樣不新增任何審計查詢入口。

回應只有可展示事實——絕不含口令明文、Argon2id 雜湊、會話材料或登入名的內部正規化鍵。單筆詳情也不放活動、資產與訊息這三塊：那些模組尚未實作，這裡不拿空陣列或 0 冒充一份查得到的真相。改角色在兩側都還沒開放，物理清庫也是；一般帳戶與訪客的軟刪除則已經開放，那一節在憑證重設之後，而登入停用與恢復見下一節、憑證重設見再下一節。已刪除者的目錄列與單筆詳情都帶 `deleted_at`，已退休訪客的單筆帶 `retired_at`，介面因此能說出那個終態落在何時，而不是讓操作者對著一個查不到的標識去猜。跨來源部署的瀏覽器要讀這條目錄得把 `GET` 列進 `cors.allowed_methods`（出廠預設已含 `GET`、`HEAD` 與 `OPTIONS`），要儲存資料則還得列入 `PUT`，要軟刪除則列入 `DELETE`；預設設定未做任何放寬。

## 管理員停用與恢復一般帳戶登入

`PUT /admin/accounts/{account_id}/status` 停用或恢復一個一般帳戶的登入，請求本體只有 `status`（`active` 或 `disabled`）與它所依據的 `expected_status` 兩個欄位。動的是這個帳戶在整台伺服器的登入能力，不是某一場活動裡的玩家限制：停用之後新登入被拒絕，他在每台裝置上的現有會話全部被撤銷、需要重新登入。活動內的禁言、交易凍結與陣營限制不在這裡，也尚未實作。

停用與恢復沿用 Root 那側已經核准的同一條底層機制（狀態寫入與會話撤銷落在同一個交易裡），但目標資格獨立判定：這條通路只認不攜帶任何伺服器級授予、且尚未進入終態的帳戶，所以普通管理員動不了另一位管理員，也動不了自己——那三種情形與「查無此人」同樣收斂成 1001；設定 Root 不在 `accounts` 表裡，結構上就不是一行。已刪除與已退休的帳戶則不再屬於那一句 1001：他列得出、也讀得到，回他的是 2027 或 2028，因為「停用」與「恢復」對一個終態都不是一發得出去的令。授權檔位仍是伺服器級管理權（沒有它回 2011，匿名回 2002），本功能沒有把任何活動作用域的角色放大成伺服器級停用，也沒有新增權限檔位。

恢復只恢復「重新登入」這一件事：停用期間被撤銷的會話保持失效、不會復活（撤銷是不可逆的事實，恢復通路一個會話都不碰），尚未完成的首次改密仍然欠著（重新登入後照舊被 2010 擋住），帳戶的其他限制也不因恢復而解除，已被刪除的帳戶更不能被這樣恢復，那裡回的是 2027（已被綁走的訪客回 2028）而不是 2014：重讀這筆資料也不會讓那顆按鈕為一個終態重新出現。多重限制從來不是一個 Active 布林值：`status` 管能不能登入、`must_change_password` 管登入後要不要先改密、`account_type` 講來源、刪除是終態，四件事各由各自的欄位與通路回答。

併發與重複由同一形的 compare-and-set 處理：`expected_status` 已不是資料庫現值時整個操作不發生——狀態沒改、會話沒撤、審計沒記——並回 2014（409）。這句話與 Root 那側逐字相同，處置也一樣：重讀目標現狀並重新確認，而不是把那顆按鈕再點一次，因此本功能不新增任何機器碼。SQLite 的單寫者把併發串行化，先提交完成的寫入是不倒退的事實，停用生效之後的新操作在會話解析邊界就被拒。一次成功的變更要在 Root 域追加一條 `account.disable` 或 `account.enable`，操作者是真實發起的那位管理員（帳戶級身分，不是 Root 也不是 system），帶前後狀態、前後停用時刻與這次撤銷的會話數量；被拒的變更不留審計，本功能同樣不新增任何審計查詢入口。

回應回顯變更後的服務端現值與 `revoked_sessions`，絕不含口令、憑證雜湊或會話材料；訪客帳戶走同一條通路，因為今日他沒有可登入的憑據通路，那次停用通常撤不到會話（數量為 0），而狀態落庫仍是如實事實。介面在提交前用確認對話框講完目標、影響範圍與「這不是刪除」，成功後重新讀取目錄與詳情的真實狀態。跨來源部署要儲存這條狀態得把 `PUT` 列進 `cors.allowed_methods`；出廠預設未做任何放寬。

## 管理員重設一般帳戶憑證

`PUT /admin/accounts/{account_id}/password` 把某個一般帳戶的登入口令換成管理員親自交出的那一個一次性口令，請求本體只有 `password` 一個欄位。它複用 Root 重設管理員憑證時建立的那套元件——同一個口令派生實作點、同一條強制替換雜湊的倉儲寫法、同一把定向撤銷會話的刀——但操作者、目標類型與管理範圍各自校驗：授權檔位仍是伺服器級管理權（沒有它回 2011，匿名回 2002），目標範圍仍是「不攜帶任何伺服器級授予」那一本目錄，而這條邊界多了一道：終態的列在名冊上，卻不再可處置。所以普通管理員重設不了另一位管理員，也重設不了自己，更碰不到配置 Root——那幾種形態與「查無此人」同樣收斂成 1001，這條通路不回答「差哪一半」；而一個已刪除或已退休的目標，這本目錄列得著他，回的是 2027 或 2028。

一次成功的重設落地三件事，缺一件都是半套：現行口令立即失效（雜湊整欄換掉，拿舊明文永遠過不了校驗）、該帳戶名下全部現有會話在同一交易裡被撤銷（`revoked_sessions` 就是這次落庫的數量）、首次改密義務被重新設為生效（他下次登入照舊被 2010 擋住，直到自己改掉為止）。交付方案沿用已批准的形態：口令由操作者親自交、伺服器不生成、不在任何回應裡回顯、不設預設口令，線下的交付管道在協定之外。界面上那串字只活在輸入框到請求之間那一小段：發出請求前就清空，之後任何一處都不再顯示，也不寫進日誌、審計、可讀偏好或自動複製的剪貼簿。

重設不改的事實同樣要如實列出：停用狀態原樣保持（那條 UPDATE 語句裡沒有 `status` 與 `disabled_at` 兩欄，重設之後他仍然登不進去，要恢復登入仍走 `/status` 那條通路），刪除終態不能被這樣復活，而且這一次重設連那句判斷都到不了——寫入先以 2027（已被綁走的訪客是 2028）被擋下，一個欄位都不落地，還欠首次改密的人不會因為被重設就免掉義務。待審批與已拒絕的申請不在這本目錄的範圍裡：拿這兩種狀態的帳戶標識來重設口令，得到的是與「查無此人」同一句 1001。所以這條通路既不會替誰放行，也碰不到一個還沒獲准的人——批准不是這三道寫入點的任何副作用。

訪客帳戶（`account_type` 為 `guest`）不在這條通路的職責裡：他的口令格在資料庫裡就被凍結成空值，替他寫一個進去等於把身分從訪客升級成普通帳戶，而那該由另一條明確的訪客升級通路決定（`PUT /admin/accounts/{account_id}/upgrade`），不是一欄口令的 PUT 該決定的事。他因此拿到本功能唯一的新機器碼 2018（403）。那句話與 1004「改改口令寫法」、1001「換個目標」、2011「換個身分」都不是同一種處置——權限夠、寫法也沒錯，該走的是那條升級通路；而目錄按定義把訪客列得進去，這裡也不講「他在這本名冊外」。

併發與重複：這條端點刻意沒有依據值——操作者拿不出「現行雜湊」這類誠實的錨點，任何湊出來的依據值驗證的不是它宣稱的東西。SQLite 的單寫者把每次重設串行化，每一次成功都是完整的「換雜湊＋撤會話＋審計」；重複提交是如實地再做一次重設（再撤一輪可能新簽發的會話、再留一筆審計），不是 2014 那種「陳舊依據被拒」。介面據此不在結果不明時自動補發，把那顆按鈕再按一次不是重試。一次成功的重設在 Root 域追加一條 `account.password_reset`，操作者是真實發起的那位管理員（帳戶級身分，不是 Root 也不是 system），帶首次改密旗標的前後值與這次撤銷的會話數量；被拒的重設不留審計，本功能同樣不新增任何審計查詢入口。

回應回顯重設後的服務端現值與 `revoked_sessions`，絕不回顯口令的任何影子（連前綴與長度都不給）。跨來源部署要儲存這條憑證得把 `PUT` 列進 `cors.allowed_methods`；出廠預設（`GET`、`HEAD`、`OPTIONS`）未做任何放寬。郵件找回、Root 的網路恢復入口與獨立的一次性恢復碼體系都不在這裡，也不因這一步而存在。

## 管理員軟刪除一般帳戶與訪客

在這本目錄裡刪除一個人是一種狀態，不是清庫，而且落地的是 Root 管理員那側早已落地的同三件事——差的是誰來動、動的是哪本名冊。`DELETE /admin/accounts/{account_id}` 不帶請求本體：`{}` 收得下，帶任何欄位都打成 1004，而且刻意不設依據值欄位——操作者對「現行刪除時刻」拿不出誠實的錨點，作數的是狀態機守衛（`deleted_at IS NULL`），於是第二次刪除寫不中任何一列，回的是拒絕而不是「又刪成功一次」。一次成功在同一筆交易裡落地三件事：新的登入被拒絕（狀態落為 `deleted`，而所有既有的閘本來就拒絕任何非 active 狀態，哪一處都不必為此新增特例）、名下全部現有會話在同一筆交易裡撤銷（`revoked_sessions` 就是權威計數——訪客名下是真的有會話，因此這個數字常常大於 0）、`display_name` 在同一條 UPDATE 裡被改寫為 `DEL_<UTC 日期>_<原名>` 形狀的佔位字串。成功是 HTTP 200 而不是 204，回應本體是 `{"account": {刪除之後的真相}, "revoked_sessions": <int>, "request_id": "…"}`，介面因此拿服務端回的事實改寫那張卡，而不是對著一個空回應猜結果；Root 稽核追加一條 `account.delete`，操作者是真實發起的那位管理員（帳戶級身分，不是 Root 也不是 system）。

刪除留下的東西才是重點：帳戶那一列、它的標識、它的登入名鍵、它的會話、它的授予與它的稽核列全部留下，歷史因此繼續指向同一個穩定身分，而那個名字也沒辦法再被別人註冊一次。刪除之前寫下的稽核仍保留它當時記錄的名字，只追加的歷史刻意不動。刪除是終態：沒有恢復入口，而對一個終態目標發起編輯、改狀態、重設憑據、升級訪客或再次刪除，一律被拒。物理清庫在兩側仍然都不開放。

兩枚新的機器碼各自帶著四語言的服務端句子，承住這些拒絕。2027（HTTP 409）說這名一般帳戶或訪客已經被軟刪除：本次什麼都沒發生，重試也不會讓它變成成功。它是已發布的 2015 在一般帳戶這本名冊裡的對應版本，而 2015 保持原樣、仍然只指 Root 的管理員目錄——兩本名冊的範圍規則本來不同，措辭因此不共用。2028（HTTP 409）說這名訪客已經被綁定併入另一個一般帳戶，進入的是 `retired` 終態：他不能被刪除、不能被復活，而那條綁定留痕保留著。這句話與 2027 刻意不同形——面對一個被刪掉的人，操作者什麼都不必再做；面對一個已退休的人，該讀的是那條綁定歷史記錄。

刪除後的展示策略刻意與 Root 管理員那側已有的形狀相同：已刪除的一般帳戶與訪客仍然列在 `GET /admin/accounts` 裡，`?status=deleted` 現在是可接受的篩選值（過去它被打成 1004），目錄列與單筆回應都帶 `deleted_at`。已刪除或已退休者的詳情讀得到（200）但唯讀：每一條寫入通路都回 2027 或 2028，而不是假裝這個人查無著落。`pending` 與 `rejected` 的申請人仍然不在這本書裡——他們照舊被篩選擋下（1004），也照舊在這條端點夠不著的地方（1001），因為審批名冊是另一本書，而那本書唯一的寫入就是批准與否那一個決定。

範圍邊界要說在明處。普通管理員不能經這條端點刪除另一位管理員或 Root：那些標識、格式不對的標識、幽靈標識與 Root 保留的主體標識全部收斂到同一句 1001，這條端點因此不是標識探針，而設定的 Root 根本不是一列 `accounts`。也正因為這是一件伺服器範圍的能力變更，一次成功的刪除收走的是整台伺服器的登入能力（所有裝置、所有往後的活動），不是某一場活動裡的玩家限制。刪除一段既有綁定的目標是允許的，而且不做級聯：那個已退休的源頭列、那條不可變的綁定記錄、以及源頭佔用的登入名全部原樣留著；而往一個已被刪除的目標身上發起新的綁定，由預檢擋下。跨來源部署的瀏覽器要打到這條通路，得把 `DELETE` 列進 `cors.allowed_methods`；出廠預設（`GET`、`HEAD`、`OPTIONS`）不變。

## 待審批的自助註冊與本人的狀態查詢

`self_register_mode` 設為 `approval` 時，`POST /auth/register` 不再建立一個馬上能登入的帳戶，而是收下一份申請。白名單仍是那三個欄位，口令仍由本人自選，建的仍是不帶任何伺服器級授予的普通帳戶——唯一的差別落在狀態上：`pending` 而不是 `active`。穩定的帳戶標識從提交那一刻就存在，因為在統一帳戶模型下，申請人不該在被人批准的那天變成另一個人。登入名從那一刻起被佔用，`must_change_password` 保持關閉：申請人等的是批准，不是一份口令。

「等待」不是半個可用狀態，而且這不靠措辭維持。登入判定問的是帳戶是否 `active`，而 `pending`（以及 `rejected`）在這一問上與「口令打錯」完全同形——同樣回 2001，不透露哪個名字存在。會話儲存拒絕為非可用帳戶簽發或解析主體，因此沒有 Cookie、沒有 bearer 祕密，也沒有一枚「受限會話」能讓待審批的人去碰普通業務。管理員的普通帳戶目錄把這兩種狀態都排在範圍之外，而按標識直打那五條通路（詳情、改顯示名、停用／恢復、重設口令、刪除）都得到 1001——「這本名冊沒這個人」。批准與拒絕走的是另一組入口（見下一節「註冊申請的審批」），那道閘門認的是伺服器級管理權；這四條目錄通路從來不能替任何人做出批准，也沒有一條能把已做過的決定改回來。

申請人若想知道自己的申請怎麼樣了，可以走 `POST /auth/registration-status`，而答案只有重新證明憑據才拿得到：本體只有 `login_name` 與 `password`，用與登入同一個 Argon2id 憑據校驗。成功的回應只給結局（`pending`、`approved` 或 `rejected`）、提交時刻，以及在已有決定時的決定時刻——沒有別的。沒有審核人是誰、沒有拒絕理由、沒有排隊位次、沒有別人的申請，也沒有任何會話材料：這條通路不寫 `Set-Cookie`、不產生會話行，因此也就不需要一枚要有壽命與撤銷邊界的「臨時狀態證明」。它只有 POST，理由相同：祕密不進 URL、不進查詢字串、不被預取、不會被貼進位址欄。查無此名、訪客帳戶與口令不符一律收成同一句 2001，這條通路對「誰的名字存在」不新增信號；限流用的是登入守衛那一份帳——多開一扇門不多發一份猜口令的預算。此後已被軟刪除的帳戶拿到的也是同一形的 2001，並且照舊記一次憑據失敗，而不是永遠回「已批准」：那句拒絕只在口令驗證通過之後才說，因此這條通路不新增任何枚舉面，也沒有為它另發一枚碼——2027／2028 那兩句是讀得到這本目錄的管理端才需要的分辨。2020（403）是唯一一種必須在「已經證明你是誰」之後才會出現的回答：這個帳戶存在、你就是它的主人，但它根本沒走審批通路，所以處置是「改用登入入口」，而不是「等一等」或「換個名字」。

切換模式只管新的提交，歷史申請原地保留。Root 把模式改回 `closed` 或轉成 `open`，都不替任何一份已經交上來的申請說話：已落的行仍是 `pending`，仍能被本人查到，既不被放行也不被刪除。這也意味著用同一個登入名重複提交會撞上與所有人同一個唯一索引（2019）——待審批與已拒絕的行都繼續佔用那個名字，被拒絕的人不能拿同一個名字再來一次，別人也拿不走。

遷移 `0009` 給帳戶狀態集合加上 `pending` 與 `rejected`，並新增一欄 `reviewed_at`：狀態查詢通路就是靠它把「曾被批准、後來被停用」與「從沒申請過」分開——決定時刻不可能掛在還在等待或已被拒絕的行上，新建的行也不可能被塞進一個決定時刻。提交仍在 Root 域追加一條 `account.self_register` 稽核，操作者是系統主體（匿名請求本來就沒有可信主體可記），而記錄裡的 `status` 就是實際落成的那個狀態，所以「我們收了一份申請」與「我們建了一個能登入的人」在稽核上可分，而不需要新造一個稽核查詢入口。跨來源部署要把 `POST` 列進 `cors.allowed_methods` 才存得了這兩條路徑；出廠預設（`GET`、`HEAD`、`OPTIONS`）一字未動。登入前的入口能力現在帶三個布林——`sign_up_open`、`guest_open` 與 `invite_code_required`——但模式名字本身仍不從匿名入口出去：「立即能用還是要等」這個問題由寫入自己的 status 回答，而 `invite_code_required` 只說「這一趟要不要帶碼」（只在 invite 模式點亮），不說當前是哪一種模式。

## 註冊申請的審批

`GET /admin/registrations` 列的是走審批通路進來的申請：查詢參數只有 `page`、`page_size`、`all`／`pending`／`rejected` 的狀態篩選與一段可選的名稱關鍵字；每一行帶帳戶標識、兩個名字、狀態、提交時刻，以及在已有決定時的決定時刻。投影裡沒有別的：沒有口令、沒有憑據雜湊、沒有登入名的正規化鍵、也沒有角色欄，更沒有審核人欄與理由欄——帳戶表本來就沒有那兩格。被批准的人離開這本書：那一行此後屬於普通帳戶目錄，停用、重設憑據與改名都在那一側處理。持有授予者、訪戶與已進入刪除終態的行都在範圍之外，得到的答案與查無此標識完全同形（1001），因此這條通路永遠不會變成「誰存在但他不是申請人」的探測器。

`PUT /admin/registrations/{account_id}/decision` 做那個決定，而本體只有一欄：`decision`，取值 `approve` 或 `reject`。刻意不帶依據值，因為審核者手上沒有誠實的依據值——一筆還沒被決定的申請，其現值就是 `pending` 這個詞本身，放一格 `expected_status` 只會多出一個「填錯就注定落敗」的表單欄位；真正的併發控制是資料庫那道 `WHERE status = 'pending'`（與刪除、重設憑據那兩條同一取向）。本體裡沒有角色欄、沒有狀態欄、沒有口令欄，也沒有理由欄：那條 UPDATE 連 `account_server_roles` 都不在語句裡，「批准順手多造一位管理員」沒有可以發生的形狀；批准也不簽發任何會話——申請人仍要自己帶著当初選的口令走 `/auth/login`，他拿到的是不帶任何伺服器級授予的普通帳戶。批准同樣不解除任何獨立限制：`must_change_password`、`disabled_at` 與 `deleted_at` 都不在那條語句裡，所以一個曾被批准、此後被停用的人早已不是 `pending` 行，審批通路對他無事可做。

決定是單向的，而併發的兩位審核者只形成一個有效結果。只有 `pending` 的行可以被決定；一旦有人批准或拒絕過，沒有任何通路能改判、能覆蓋，也不能讓同一個人把那份申請重開。併發裡後到的那一位，或對著已決定過的申請再按一次的那一位，拿到的是機器碼 2021（409）「這份申請已經有過決定」——它刻意不是 2014 那句「你依據的現值已過期，重讀之後同一顆按鈕還可以再按」。2021 的處置是重讀名冊：對那一行而言，那顆按鈕已經不存在。被拒絕的行保留、登入名繼續被佔用，而「要不要讓他重新申請」不是這一步做出的產品決定。審批也從不查帳戶建立策略：Root 把模式改成 `closed` 或 `open`，既不會讓誰的待審批申請消失，也不會擋住審核者處理眼前這一筆——策略只管新的提交。

兩個入口都由 `NeedServerAdmin` 把關，與建立、列舉、停用及重設普通帳戶同一道閘：具備普通帳戶管理權的管理者審批普通帳戶的申請，Root 也走得通。普通帳戶、訪戶與系統主體在任何一次讀取之前就拿到 2011，匿名請求碰不到資料庫就拿到 2002。一次成功的決定恰好追加一筆 Root 域審計（`account.approve` 或 `account.reject`），actor 是经受信主體換得的真實審核者——不是 system，也不是冒充 Root——帶 `status` 與 `reviewed_at` 的前後值，以及服務端固定措辭的原因句；被拒的決定不寫審計，本步也不新增任何審計查閱入口或網頁控制台。審核者是誰與任何理由文本永遠不會回傳給申請人：他能知道的只有自己那筆申請的結局與決定時刻，也就是上一節那條 `POST /auth/registration-status`。

## 伺服器註冊邀請碼管理

邀請碼是允許新普通帳戶進入本伺服器的准入憑證：它不攜帶 Root／管理員權限，也不代表加入任何活動。只有 Root 管理它——`POST`／`GET`／`HEAD /root/invite-codes`（簽發與分頁名冊）與 `DELETE /root/invite-codes/{code_id}`（撤銷），全部由 `NeedRoot` 判定，與帳戶建立策略同側，因為「誰能發這張路條」本身就是伺服器級的准入決定；能打理普通帳戶的管理員仍然不能簽發或撤銷。

每枚碼有自己的額度與期限。`max_uses` 是可被核銷幾次（至少 1；1 即單次碼——不另開一個「是否單次」旗標，那只是 `max_uses = 1` 的第二份副本）；`used_count` 每次核銷只加一，名冊顯示 `remaining = max_uses - used_count`。`expires_at` 可選：`0` 表示永不過期，否則是一個必須晚於簽發時刻的絕對到期。狀態從來不是儲存欄——`active`／`expired`／`exhausted`／`revoked` 由這些事實加注入時鐘在讀用時算出，所以沒有排程去清理或翻動行，也不會有兩次時鐘讀數互相矛盾。撤銷是單向終態：落下時刻即立刻擋住之後的核銷並凍結該行（已用次數作為歷史留住），重複撤銷回 `2022`（409）「這枚邀請碼已經被撤銷」，處置是重讀名冊，而不是再按一次那顆按鈕。

完整邀請碼只在簽發成功的 `201` 回應裡出現一次，伺服器只存它的 SHA-256——邀請碼是高熵隨機值，所以（與會話秘密同理，而异於用人想出來的口令、後者留在 `internal/credential` 走 Argon2id）用快雜湊作為驗證材料就夠，整庫匯出也造不出可用的碼。名冊與撤銷回顯只帶標籤、狀態、額度與時刻——絕不帶明文碼，也不帶雜湊。碼丟了就重新簽發一枚，而不是從庫裡翻回秘密。簽發與撤銷各追加一筆 Root 域審計（`invite.issue`／`invite.revoke`），actor 是取自受信主體的 Root，明文碼與雜湊都不進審計、日誌或錯誤。

把一枚有效碼換成帳戶的核銷通路，現在已接進開放模式所走的同一條匿名 `POST /auth/register`，作為它的 `invite` 分支：請求本體能帶一個可選的 `invite_code` 欄位，只有當寫入那一刻生效的模式確為 `invite` 時才讀取並核銷它（開放／核准模式根本不看這格，於是一支碼絕不會在不需它的另一側被順手吃掉）。核銷與建號共用同一筆 `BEGIN IMMEDIATE` 交易，經 `internal/invitecode` 的 `Store.Redeem`（`used_count` 上釘著「未撤銷、未過期、額度未滿」四重 WHERE 的單向 UPDATE）：同名衝突、非法口令或任何寫入失敗都整筆回滾、不誤耗名額；一次性碼在併發提交下恰好一次成功，其餘拿到同一句不洩露細節的拒絕；重複請求或回應丟失都不多建帳戶、不多扣額度。建出的按定義是普通帳戶——邀請碼不攜帶任何權限——並且可立即登入，走與開放模式相同的通路（註冊這一步仍不簽發會話）。登入前的 `GET /auth/capabilities` 多出第三個布林 `invite_code_required`，只在 `invite` 模式點亮，讓共享表單知道要顯示邀請碼欄位；它從不洩露模式名字本身。任何換不出帳戶的碼——缺、形狀不合、本機從未簽過、已撤銷、已過期、額度用盡、或併發下被另一次註冊搶先——一律收斂成同一個不區分的機器碼 2023（403），刻意不分辨原因，好讓這條通路不成為逐枚探測碼有效性的探測器；吞吐與開放模式同受來源級限流約束。把 `self_register_mode` 切成 `invite` 仍是 Root 在 `/root/account-policy` 上單獨做的決定，該端點現在四個名字都收。

## 受限的訪客進入

`POST /auth/guest` 是門外的人把自己換成一個**臨時、受限主體**的那條匿名通路。它只在帳戶建立策略允許時存在，而它的放行答案和其他入口算法相同：`guest_enabled` **而且**「這個執行檔真的把這條路做出來了」（`internal/acctpolicy` 的 `AllowsGuest`，而且是在寫入那筆交易裡現讀）。開關關著時回的是既有的 2017（403）——「這條帳戶建立通路此刻被伺服器策略關閉」——那句話本來就是為帳戶建立通路寫的，為訪客另開一枚碼只會讓同一個決定有兩種說法。

主體由伺服器命名，這正是重點。`login_name` 產生為 `guest_<uuid>`，請求裡沒有一格能交它，所以訪客既不能替自己佔住某個真人將來想用的名字，這個匿名入口也就不會變成登入名的存在性探測器（那恰恰是 `POST /auth/register` 結構上免不了的性質，所以那側寧可回可判別的 2019）。穩定的身分是伺服器鑄造的 Account ID；暱稱只是展示資訊——可選、按顯示名的同一套領域規則校驗、允許和別人同名，而且從來不是憑據。留空時由伺服器給出一個語言中立的臨時編號（`guest-<6 位十六進位>`），因為伺服器產生的字串不該把任何一種語言的用詞寫進資料裡。

這個帳戶按構造就沒有憑據：`password_hash` 為 NULL、`must_change_password` 為 0，由資料庫 CHECK 凍結、領域層再核一遍，所以這裡沒有一枚可以被猜、被重設或被交出的口令。這也正是這條通路與其他註冊路徑相反、**要**簽發工作階段的原因：訪客沒有之後用口令登入的路可走，不給工作階段這扇門只是一堵牆。工作階段來自 `internal/session` 那唯一的簽發點，經傳輸層唯一的那條 Cookie 分發通路送出：絕對的到期時刻、閒置線、登出與改密時的撤銷、裝置名額、輪換，全都和其他帳戶一樣。沒有一枚「不受這些約束的訪客 Cookie」，而秘密只會經 `Set-Cookie` 到達客戶端（Web 由瀏覽器代管，原生寫入平台的安全儲存），絕不出現在回應本體裡。

進來了不等於有管理權。訪客主體構造時交的是空的授予集合，而 `identity.NewAccountPrincipal` 會當場拒絕「訪客卻持有角色」，所以這是型別層的牆，不靠約定。於是每一條 `NeedServerAdmin` 與 `NeedRoot` 的路徑對他回 2011（403）（匿名者則是 2002），他既讀不到也無法透過這些端點寫帳戶目錄；而 `/auth/session`、`/auth/logout`、`/auth/session/rotate`、`/auth/devices` 這些只處理自己工作階段的路對他照常可用——撤銷自己的工作階段從來的一項特權。同樣刻意的還有「不告訴他什麼」：活動、資產、聊天與 NPC 這些還沒做的模組不會裝成可用，介面的玩家面會如實寫著這個身分还不屬於任何活動。

兩件事是被明確決定下來的，而不是悄悄發生。第一，**沒有自助找回**：工作階段到期、主動登出、換裝置或清掉本機憑據之後，這一趟就結束了。一條「憑暱稱把我找回來」的通路等於一把可以被任何人替別人出示的可猜測憑據，本步刻意不發明它——要處置這個人，由管理員在一般帳戶目錄（這本目錄按定義就把訪客列進去）核實之後另行決定。第二，**訪客建立按「嘗試」計量而不是按「失敗」**：`security.register_guard` 的那組閾值被第三份獨立的記憶體守衛複用，計量主軸是「來源位址 × 這條通路」，而成功的那一趟和被拒的一樣要銷預算。自註冊靠登入名唯一性天然自限，但每一趟成功的訪客進入都實實在在多出一筆帳戶、一枚工作階段、一條稽核，只記失敗等於留下「開關亮著就能無限建號」這條路——既然也不提供排程批次刪除訪客，天花板就必須設在門口。

落庫的痕跡是一條 Root 域稽核 `account.guest_enter`，操作者是系統主體（匿名請求本來就沒有可信主體可記），帶產生的登入名、顯示名、`account_type` 為 `guest` 與 `must_change_password` 為 false——不帶來源位址、不帶任何工作階段材料，暱稱除了顯示名本身也沒有第二處落點。回應回顯帳戶標識、顯示名、裝置標識與到期時刻；同時在 `/auth/login` 與 `/auth/session` 的回應裡新增的 `account_type` 欄位，是讓重新整理或重開之後的介面還能說「訪客（臨時身分）」而不會把所有人都唸成「帳戶」的依據。

## 訪客帳戶就地升級

`PUT /admin/accounts/{account_id}/upgrade` 是只有伺服器級管理員走得通的「就地轉正」通路：一般帳戶目錄裡那些訪客行不必被重建，也不必併到別人身上。請求本體的白名單只有 `login_name` 與 `password` 兩欄：升級給他一個正式登入名和操作者親自交付的一次性憑證，升級出來的形態恆為 `standard`＋`active`＋首次登入必須改密——本體沒有 `account_type`、`roles`、`status` 或旗標的格子可填，所以「把訪客升成管理員」在協定層根本沒有地方可寫，而既有的身分判定本來也會拒絕為不存在的授予放行。

被保留的才是這一節的重點。那條更新只改同一行帳戶的五個欄位（登入名、它的正規化鍵、帳戶類型、口令雜湊與首改旗標），而帳戶標識、建立時刻、顯示名、所有已經指向這個穩定標識的實際存在參照——連同記下他怎麼出生的 `account.guest_enter` 審計——全部逐字不動。審計只追加：升級另記一筆 Root 域的 `account.guest_upgrade`（操作者是那位真實管理員，內容是新登入名與帳戶類型的前後值、首改義務與這次撤銷的會話數量），沒有任何歷史被改寫，因為歷史事件描述的就是發生時那個訪客的身分。這正是「就地升級」與「把他綁定到另一個既有正式帳戶」的分別：第二個動詞既有唯讀的預檢，也已經有了執行通路（下一節）；介面在同一張卡上把兩句話分開講。

舊會話活不過升級。會話解析每請求現讀帳戶列，留著訪客 Cookie 不等他做任何事，就等於讓撿到舊臨時憑證的人安安靜靜拿到正式帳戶；所以撤銷他名下全部會話與升級落在同一筆交易——用的就是停用與重設已經在用的那個原語——回應如實帶回 `revoked_sessions`，回到門內的唯一方式是用新憑證真實登入一次，而首次登入立刻受首改門閂（2010）約束。任何一步失敗就一個都不落地：不會留下沒有口令的半升級身分，也不會留下查不到誰的撤銷。

三個建立開關不約束這條通路：它們管的是「準不準再多出一筆帳戶」，而升級動的是一筆已存在帳戶的形態——關掉訪客入口不該剝奪管理員處置既有訪客的手段。結論各說各話：1004 點名寫壞的 `login_name` 或 `password` 欄位；2012 說那個名字是別人的，而訪客那一行一個字都沒被改；2011 是敲這條端點的人不是管理員——訪客本人也在內，這條路存在的意義之一就是答不了他；1001 是這本目錄按定義不列的目標（管理員、申請人），而已進入終態的人是列得到卻動不了——已刪除回 2027、已被綁走的訪戶回 2028，那既不是 1001 那句「換個目標」，也不是 2024 那句「重讀現值之後那顆按鈕還在」：對那兩種人，那顆按鈕永遠不會再出現；升級帶來的新碼 2024（409）回答「他此刻不是可升級的訪客」——要嘛已經升過（重複提交），要嘛此刻被停用，前者的處置是「無事可做」、後者是「先恢復他的登入」，兩句都指向重讀伺服器端現值，而都不是 1001 那句「換個目標」：這本目錄列得到他。口令交付沿用建號與重設同一套規則：伺服器不生成、不回顯，線下交付在協定之外。

## 訪客綁定預檢（唯讀預覽）

「把訪戶併入另一個既有正式帳戶」這個動詞從唯讀的預檢與衝突預覽開始：`POST /admin/accounts/{account_id}/bind-preflight` 由伺服器級管理員發起（NeedServerAdmin），請求本體的白名單恰好一格 `target_account_id`——一次只評估「這個訪戶 × 這個目標」的一對，不存在替訪戶羅列可綁定目標的讀法；請求形態本身就是反枚舉的邊界。目標標識放在本體而不是查詢串：它是一段待驗證的輸入，不該成為可書籤、可快取的尋人請求。

這一條通路零寫入：不改帳戶、不撤會話、不動授予，連一筆安全審計都不記（用戶批准的 R2-018 決定：純唯讀，介面顯著標示「尚未綁定」由結果面板首句承擔）。「此刻不可綁定」是 200 預覽本體裡的穩定原因記號而不是錯誤：`executable` 為假時 `blockers` 逐條點名——同源自同一對（`same_source_target`）、來源已轉正或已退休（`source_not_guest`）、來源已經登不進來了（`source_not_active`——停用、已刪除，或已被綁走而退休）、來源帶著授予（`source_has_grants`，形態缺陷方向）、目標也是訪戶（`target_not_standard`）、目標停用中連以自己的會話確認綁定都做不到（`target_not_active`）、以及 `unknown_references`。回應同時如實帶出這份快照運行的 `schema_version`、該訪戶名下尚未撤銷的會話數 `source_open_sessions`，以及恆為 `target_self_initiated` 的 `consent_mode`：綁定只能由目標帳戶持有人以自己的已認證會話發起，管理員永遠拿不到代他完成綁定的按鈕——登入名相同或管理員輸入目標標識都不構成目標的同意。

未知引用整體阻止是這一節最要緊的規矩。預檢每次執行都現掃實庫的外鍵邊：只要出現一張引用帳戶而處置登記表尚未接入的表（未來活動、帳本、NPC 模組新加的表），一切綁定都被阻止，絕不靜默合併評估不了的權限或資產；那個模組把自己的引用接入預檢之後才重新放行。未接入的表名只進伺服器日誌，不進回應。這一步沒有發布任何新機器碼：請求級拒絕全用既有碼——來源或目標不在普通帳戶目錄（不存在、管理員、已刪除、待審批）與詳情端點逐字同句收斂 1001，預檢不是比詳情更亮的探照燈；2011 是主體不夠（訪戶本人敲它也一樣）；1004 點名 `target_account_id`；GET 方法 1002。

預覽裡的影響就是執行時必須遵守的那一份清單：該訪戶名下尚未撤銷的會話同交易登出、訪戶帳戶進入不可登入、不可複用的退休終態、指向他的歷史參照逐字保留、未來的身份歸屬落在目標標識上，而目標的憑據、狀態、顯示名與權限一概不動。

## 訪戶綁定由目標帳戶本人執行

預檢不是綁定，簽發憑證也不是綁定。`POST /admin/accounts/{account_id}/bind-ticket`（仍由 NeedServerAdmin 判定，本體白名單仍恰好一格 `target_account_id`）在**寫交易之內**把整份預檢重做一遍，可行才簽發一枚操作憑證——這就是用戶批准的 R2-019 那座橋：把「管理員准了這一對」交給「目標本人的會話按下執行」。它只落兩行：`guest_bind_tickets` 裡的一枚憑證，和 Root 域一筆 `account.guest_bind_ticket_issue` 審計（操作者是那位真實管理員，內容含憑證標識與被准的目標，絕不含明文）。訪戶沒被退休、會話沒被撤銷、留痕沒被追加。那一刻這一對不可行，就根本沒有憑證存在，答案是 2026 並帶著原因記號。

憑證是刻意做小的：15 分鐘，寫在碼內而不是配置欄位（一枚能調到一週的綁定憑證就不叫短期憑據了）、只准核銷一次、限定這一對來源與目標、限定這一個用途。明文只在簽發回應裡出現那一次；庫裡存的是它的 SHA-256，此後任何讀法——包括管理員那本目錄——都拿不回來。把它交出去是線下動作，與建號、重置的口令交付同口徑；它不是目標的口令，伺服器也從不要求管理員去收集任何人的口令。

執行屬於 `target_account_id` 那一個人，不屬於任何人。三條通路都在 `/auth` 之下：`POST /auth/guest-bindings/preview` 以唯讀方式、不核銷任何東西地展示這枚憑證按**今天的事實**會做什麼；`POST /auth/guest-bindings` 核銷憑證並完成綁定；`GET`/`HEAD /auth/guest-bindings` 列出「目標是我」的已完成綁定。主體判定先於任何查詢，所以訪戶、Root、管理員與匿名分別拿到 2011 與 2002——沒有半開的門。本體恰好一格 `ticket`：沒有任何「我要以誰的身分」可填，目標範圍只來自這次會話換出的主體。憑證放本體而不是路徑或查詢串，它才不會進訪問日誌、書籤與快取。

一次成功的確認在同一筆交易裡落地四件事：憑證被一條 `WHERE` 釘住「尚未核銷且尚未到期」的條件式 `UPDATE` 標記核銷；訪戶那一行連同 `retired_at` 一起進入新終態 `retired`（遷移 0011；行與登入名鍵保留，因此名字不可被複用、歷史也仍指得回來，但與刪除通路不同，顯示名**不做**匿名化——那個名字是記錄的一部分）；他名下仍有效的每一枚會話都用停用與重置那同一個原語撤銷；`guest_account_bindings` 追加一行只追加的留痕。目標那一行沒有任何一處被重寫：那條 UPDATE 連目標都沒點名，他的口令雜湊不被複製到任何地方，不繼承任何授予，狀態、顯示名與首改旗標逐字不動——「訪戶經綁定獲得權限」在形狀上就沒有落點。源令牌不會被換成能開目標家門的令牌，它只是從此解析不出主體，而目標繼續以他自己的正常認證進門。任何一步失敗都整體回滾，連那個核銷標記也不留下，原先可用關係完整保留。把一枚已用掉或不屬於你的憑證再打一次，得到的是 2025——五種內部原因刻意收成同一句話，因為分辨「過期」「已用掉」「不是你的」會讓這條通路變成憑證探測器。

執行時重做檢查，才讓一份舊預覽沒辦法被執行：任一側形態變了、資料庫版本推進了、或庫裡此刻多了一張尚未接入綁定預檢的帳戶引用表，請求就以 2026（「重新預檢」）被拒，並且憑證不會被核銷。因此「預檢通過」從來不是永久有權執行，而憑證那一行同時釘著計劃摘要與它被釘住時的那個版本。已被綁走的訪戶不可能再領到第二枚憑證——退休讓他在源頭就離開可綁形態，而留痕表的 `source_account_id` 帶 `UNIQUE`，是「一個訪戶至多被併入一次」的最後一道結構保證。

審計邊界沿用既有規則：普通帳戶本人的動作今日不寫 Root 域審計表，因為「帳戶本人作為審計主體」這一分類尚未批准（與登入、登出、輪換、本人改密同一口徑）。可追溯性並沒有變薄——誰准了這一對、誰同意了、什麼時候、撤了幾枚會話，全在 `guest_bind_tickets` 與 `guest_account_bindings` 兩行不可變的資料裡。

本步覆蓋範圍說清楚：只有帳戶層——帳戶、會話、憑證、綁定留痕與 Root 域審計。活動、成員身分、資料卡與帳本尚未開發，所以「未來的身份歸屬」以合約形式表達（`transfer_future_attribution` 那條影響），不宣稱已驗證。那些模組落地時必須先把自己的帳戶引用登記進 `internal/stdacct/bindpreflight.go` 的處置表，綁定才可能被再次簽發或執行；在那之前 `unknown_references` 把整條通路拒絕掉，任何沒人評估過的東西都不會被靜默合併。


## 活動生命週期管理

**活動**是後續功能（成員、資產、聊天、排程）將要棲身的容器；它裡面的**陣營**——活動內的分組——已隨本步交付（見下一節）。這部分交付的是容器、它的生命週期與陣營管理：`internal/activity` 加六條端點——`POST`／`GET`／`HEAD /admin/activities`（建立、分頁目錄）、`GET`／`HEAD`／`PUT /admin/activities/{activity_id}`（詳情、白名單資料編輯）、`PUT /admin/activities/{activity_id}/status`（狀態轉換）、`GET`／`HEAD /admin/activities/{activity_id}/managers`（該活動管理人名冊），以及 Root 那側的 `POST /root/activities/{activity_id}/managers`／`DELETE /root/activities/{activity_id}/managers/{account_id}`（指派與撤銷）。

身份是 `activity_id` 那枚 UUIDv7，從來不是名稱。名稱可改、可重複，任何層級都沒有唯一約束：兩個活動都叫《秋夜長談》是完全正常的部署形態而不是缺陷，而「用名稱當查詢鍵」這條路被結構本身拒絕。建立通路只吃兩個欄位（`name`、`description`）：狀態不在其中，因為新建一律是 `draft`；建立者不在其中，因為他來自那枚會話憑據；也沒有 `id`、`created_at`、`archived_at` 可以填——所以「我建的時候就把它寫成已開放，再把責任推給後來的編輯」在協議層沒有一個形狀，其餘類似企圖（在資料編輯裡帶上 `status`、帶上 `activity_id` 想把活動挪進另一個活動、在指派裡帶上 `role`）一律以 1004 擋下並點名是哪一欄。

生命週期四態是本步批准的：`draft` → `active`（開放）、`active` → `closed`（停止）、`closed` → `active`（重新開放）、`draft`／`active`／`closed` → `archived`。停止可逆，歸檔是終態：歸檔後的行仍列、仍可讀，但一概拒寫——不能改名、不能改狀態、也不能增減它的管理人——且沒有回去的路（2029，409）。`closed` 拒絕的是活動**內部**的業務寫入，而這條判定今天是刻意做成一個可複用的呼叫（`EnsureBusinessWritesAllowed`，在呼叫端自己的交易內現讀狀態），不是做成一條端點：誰擁有業務通路，誰在寫之前呼叫它。陣營通路是這條門禁的第一個呼叫端，停止態的拒絕因此才有了它的機器碼——2033（409）「活動已停止，重新開放後才能再寫」，與 2029 的終態句「這件事已經結束」刻意分開。三種拒絕各留一枚碼，因為用戶的下一步不同：2029「這件事已經結束」、2030「你依據的現值已過期，重讀之後再決定」（同態重複也收斂到這裡，而不是謊報第二次成功）、2031「這條路不存在，重讀也沒有用」。資料編輯沿用 2013（對 `expected_name` 與 `expected_description` 兩欄一起做比較-and-set）；狀態轉換不帶依據值，因為正當性錨在 `WHERE status = ?` 的單向更新上——落敗者拿到的是 `RowsAffected = 0`，什麼都沒寫。

伺服器級管理員**不是**所有活動的管理員。`identity.AuthorizeActivityScope`——身份層為這一天預留的唯一改點——現在讀的是 `activity_manager_grants`（R1-006 留著沒接的落庫來源），而且兩道閘都要過：`NeedServerAdmin` 證明他屬於伺服器的管理面，那一行指派證明這個活動認得他。一個失去伺服器級角色的管理人會立刻被拒，即使指派行還留在表裡。對任何不是 Root 的主體，「這個活動不存在」與「它存在但輪不到你」在讀寫兩條路人都收斂成同一句不可分辨的 1001，於是這條端點不是存在性探測器；目錄反映的也正是同一份指派集合（絕不會因為漏帶授權資料就變成「全都看得見」），而 Root——不屬於任何活動的伺服器級主體——仍然進得了任何活動，這與審計層既有的規則同說一套。

指派管理人是一次權限授予，所以它待在 Root 那一側（`NeedRoot`），與簽發邀請碼、開設管理員同邊：活動自己的管理人讀得到名冊，卻不能自行加人，因為一個被駭的管理員會話不該能在沒有任何獨立准入核查的情況下把權限散出去。指派只會落在已經持有 `server_admin` 的帳戶上——本步交付的是活動**管理**權，不是活動**內身份**（一個人在活動裡扮演哪個玩家檔案或 NPC 操作者仍未落地，審計主體類別也仍然拒絕猜測），這也是訪戶根本不可能持有一枚指派的原因：域層、服務層與 0012 裡一支觸發器各擋一次。`activities.created_by_account_id` 與 `activity_manager_grants.account_id` 刻意是不帶外鍵的軟參照，與審計表同一口徑：歷史指向原標識，不搬也不改寫，所以軟刪除一位管理員之後名冊那一行依然解析得到，並如實標出（`account_status: "deleted"`——仍列、可讀、拒寫）。`internal/stdacct` 裡一支定向測試釘住這個取捨的另一半：訪戶繫結預檢在這些行存在時依然回答「可執行」，而一旦有人把這兩欄改成真正的 `REFERENCES accounts`，它會立刻整體 fail-closed——這條邊界由實時掃描守住，不靠這段話自我宣告。

每一次被接受的寫入都在同一個交易裡追加恰好一筆 `activity_audit`（`activity.create`／`activity.profile_update`／`activity.status_change`／`activity.manager_assign`／`activity.manager_revoke`，以及下一節的陣營動作），帶著活動標識、來自可信主體的真實操作者（Root 或該管理員，絕不降級成 `system`）、被改動欄位的前後值，以及一句服務端固定敘述：請求裡沒有任何欄位能往審計寫自由文字。被拒的企圖不記審計也不動任何欄位；而如果審計寫不進去，活動那筆寫入就跟著一起回滾——「資料庫裡存在一處改動，卻查不出是誰改的」正是這一對繫結要防的事。

## 活動陣營管理

**陣營**是一場活動裡的分組——它是後續功能要指向玩家的形態，但「把玩家分進陣營」刻意不屬於本步。`internal/activity` 負責陣營域，`activity_factions`（遷移 0013）負責持久化：身分是 `faction_id` 那枚 UUIDv7，繫結唯一一個 `activity_id`，兩者由資料庫觸發器釘成不可就地改寫——白名單編輯改不了陣營 ID，也挪不動歸屬活動，因為請求本體裡沒有一個 `id`／`activity_id` 的格子（多帶以 1004 點名），`UPDATE` 語句裡也沒有那兩欄。本步沒有任何刪除通路（用戶批准）：`available: false` 是旗標而不是移除——停用的行仍列、仍可讀、仍可編輯，與帳戶和活動終態「仍列、可讀、拒寫」同一姿態；物理刪除陣營留給真需要它的那一步單獨決定。

三條端點，只在陣營用例被装配時掛載：`GET`／`HEAD`／`POST /admin/activities/{activity_id}/factions`（列表、建立）與 `PUT /admin/activities/{activity_id}/factions/{faction_id}`（編輯）。准入與活動資料編輯同一道閘——`NeedServerAdmin` **加上**該活動的一行指派，判定只經 `identity.AuthorizeActivityScope`——所以帶著有效會話的普通成員敲哪一條都拿到 2011；對活動之外的人，「查無此陣營」與「輪不到你碰」收斂成同一句不可分辨的 1001；連 Root 也必須指著一個真實活動說話，因為把「從未存在的活動」讀成一份空列表會講出另一套謊。

陣營是活動內的業務資料，兩條寫通路都先過生命週期門禁：`draft` 與 `active` 接受（開放前把組備好正是它的用途）、`closed` 以 2033 拒絕（「重新開放後才能再寫」——可逆）、`archived` 以 2029 拒絕（終態）。列表在任何狀態都可讀。

停用一個陣營現在是一份批准過的規則，而不是言外之意。`available: false` 只讓這個陣營不再接收新的成員分配，其餘一切留在原處：既有成員保留原歸屬（顯示為所屬陣營已停用），這些人之間仍按同陣營互見；沒有人被移出活動，沒有帳戶被凍結，沒有人被批次遷到別的陣營，這一行也不刪除——照樣列出、可讀、可編輯。這個旗標雙向可逆：重新啟用只翻那一欄，不會自動改寫任何人的歸屬。刪除通路依舊不存在，物理移除屬於將來真需要它的那一步的單獨決定。

有兩樣東西的存在是為了讓將來的分配步驟不能自己發明語意。`activity.Service.EnsureFactionAcceptsNewMembers` 是唯一那處可複用判定：它收呼叫端自己的**寫入**交易——簽名接 `*database.Tx`，唯讀交易直接被拒——於是「在一個交易裡查可用，再到另一個無保護的交易裡寫」這種寫法在程式碼層面就不成立；它在同一交易內現讀活動的寫入門禁與那一列陣營，停用的陣營答 `ErrFactionNotAcceptingMembers`，屬於別的活動的陣營答同一句不可分辨的 `ErrFactionNotFound`，停止或歸檔的活動答它各自那句門禁話。後來交付的玩家自選那一步是它第一位 HTTP 呼叫端，因此「該陣營已停用」那句話有了自己的機器碼 2036；管理側的分配通路至今仍未存在。每一列陣營回應還帶著 `accepts_new_members`，那是服務端依「旗標**且**活動此刻接受業務寫入」派生的值，所以停止中的活動即使列出行內仍是可用的陣營，也會如實顯示「此刻不接收新分配」。這一格在請求本體裡沒有位置：帶著它來就是 1004 並點名該欄位。

指向一個陣營的引用只有 `faction_id`，所以改名與旗標都不會讓引用失效：改名、換色、停用、重新啟用都留著標識、歸屬活動與建立時刻不動，任何狀態下那一列都讀得到。成員與歷史交易還不存在，因此這一步不建快照表、也不回填任何東西；帳本或歷史記錄落地時，必須把陣營標識連同當時的展示值一起存下，不得用陣營現在的名字重新解釋過去。管理介面的兩句話分開放：列表列顯示的是讀回來的狀態，確認框在送出任何東西之前把影響摘要念完——成員尚未接入這件事照實說，而不是端出一個偽造的成員數——結果那句取服務端寫回來的值，不取請求裡的意圖。

名稱規則走活動結構明確留給本步的那一句：`name` 在**同一個活動內**唯一（`UNIQUE (activity_id, name)`，剔除首尾空白後逐字比對——大小寫摺疊未被批准），撞名拿到自己的碼 2034（409）「這個活動裡已有另一個陣營用這個名字」——處置是換一個名字，不是重讀也不是換目標。別的活動用同名是完全正常的部署形態：這裡什麼都不把兩者關聯。`description` 沿用活動上界（1..64／0..500 碼位，控制與格式字元拒絕）。展示欄就留在展示：`icon` 是一封閉的內建識別鍵集合，客戶端用自己隨附的 Material 圖標渲染（`""` 表示未選，介面以中性佔位呈現），`color` 是 `#RRGGBB` 且正規化成小寫（或 `""`），其餘寫法一律 1004 點名欄位——沒有媒體上傳、沒有遠端圖片、沒有 CDN，這些這個伺服器都不執行。`sort_order` 是 0..99999 的整數、允許同值，同值按建立時刻與標識穩定破平；建立時不帶排序值的，由服務層在同一交易內現算「目前最大值加一」排到最後。

兩條寫都是本倉庫其餘資料編輯同形的比較-and-set：更新帶六欄新值與它們各自依據的六欄現值，落敗者拿 2013（「重讀這份列表再決定」），什麼都沒寫、審計不記——介面因此在服務端回讀的那一列回來之前絕不顯示「已儲存」，在過期畫面上也只留重讀這一個出口。每一次被接受的寫入在同一交易裡向 `activity_audit` 追加一筆 `faction.create`／`faction.update`，帶著活動標識、真實操作的管理員、白名單欄位的前後值與一句服務端固定敘述——可用性那一欄被翻轉時，敘述句會明說停用或重新啟用，讓查審計的人不必再猜「這一次動的是收不收新成員」還是「只是改了資料」；而沒有翻轉的重複儲存，記的就是它本來的這一句編輯。`activity_factions` 沒有任何一欄引用帳戶——它唯一的外鍵指向 `activities`——所以訪戶繫結、帳戶軟刪除與歷史保留都不受這張表影響；遷移測試釘住這條邊的形狀，stdacct 的繫結預檢在陣營列在場時依然回答「可執行」。

## 活動成員名冊與唯一玩家檔案

**成員列**就是一個帳戶在一場活動裡的身分：`internal/activity` 持有這塊領域，`activity_members`（遷移 0014）把它作為**單一權威關係**落庫。這一列的 `id` 是玩家在該活動裡的穩定身分（日後的帳本、聊天與資產指向的是它，不是名稱，也不是帳戶），`activity_id` 說是哪場活動，`account_id` 說是哪一個人，`nickname` 是他在活動裡面的展示名，而 `faction_id` 就是他此刻的陣營。因為歸屬只是這一列上的一欄，分配就沒有第二個可以各說一套的地方：庫裡不存在「成員 → 陣營」的映射表，檔案欄位與獨立映射因此不可能互相矛盾。`UNIQUE (activity_id, account_id)` 是「一個帳戶在一場活動裡只有一份檔案」的結構形態，而觸發器把 `id`、`activity_id` 與 `account_id` 釘成不可就地改寫——改這三欄裡的任何一個不是編輯，而是換了一個主詞，任何指向舊值的東西都會被留在原處。

`account_id` 是**不帶外鍵的軟參照**，姿態與 `activities.created_by_account_id`、`activity_manager_grants.account_id` 相同（遷移 0012）：歷史指向原來的標識，既不搬也不改寫。已被軟刪除（0007）或被訪客綁定退休（0011）的帳戶仍然解析得到那一列，所以名冊可以老實說「這一列指向一個已被刪除的帳戶」，而不是把列藏起來或把它改名成別人。選擇軟參照也讓綁定通路保持走得通：`internal/stdacct` 的綁定預檢掃的是實庫的外鍵邊，一張對 `accounts` 沒有邊的表對它根本不可見，所以這張新表既不阻止綁定，也不會被靜默合併進去。寫在該檔案裡的規則是：成員列與指派同屬歷史那一側，不是待搬遷的歸屬；定向測試也確實在是一對（來源、目標）兩側都種有成員列時照样回「可執行」，而且事後每一列仍指向它原本那一個帳戶。相較之下，`faction_id` 是指向 `activity_factions` 的硬外鍵，另外再加兩條外鍵表達不了的觸發器：非空的陣營必須屬於**同一場**活動，建立與更新各一條，所以把一個玩家縫到另一場活動的陣營上會在資料庫層當場失敗，而不是依賴呼叫端還記得先查一次。

誰能參加由服務端現讀，絕不由請求宣稱。普通帳戶與訪戶都能成為成員——參加不是一種特權，而訪戶正是區域網路活動現場最常見的身分；待審批、已被拒絕、已被軟刪除、已綁定退休這四種帳戶則與一個從未存在的標識、以及零值標識一樣，收斂成同一句不可分辨的 1001。這個收斂是刻意的：活動管理人並不是帳戶目錄的操作者，多一句「他被刪了」等於交給任何敲得動這條路徑的人一枚列舉帳戶狀態的信號。被停用的帳戶可以被加入，因為停用是可逆的暫停，在活動開放前把名單備好是正常工務；名冊隨後帶著從 `internal/account` 讀回的狀態。持有 `server_admin` 的帳戶也可以是成員：成員身分從不授予任何伺服器級權限，這兩個問題問的是兩個不同的來源。建立、加入或改名一名成員都不會寫帳戶列——狀態不變、憑據不變、首改旗標不變、授予行不多、會話不撤、任何東西都不凍結——而有測試正是釘住這一句。

三條端點，只在成員用例被注入時掛載：`GET`／`HEAD`／`POST /admin/activities/{activity_id}/members`（名冊、加入）與 `PUT /admin/activities/{activity_id}/members/{member_id}`（改暱稱）。准入與活動資料編輯、陣營管理同一道閘——`NeedServerAdmin` **加上**該活動的一行指派，且只經 `identity.AuthorizeActivityScope` 判定——所以帶著有效會話的普通帳戶在每一條上都拿 2011，外人管理員與幽靈活動拿到同一個 1001，而 Root 也必須指向一個真實活動。成員是活動內的業務資料，因此兩條寫入都先過生命週期那道門：`draft` 與 `active` 接受，`closed` 回 2033，`archived` 回 2029，而名冊在任何狀態下仍列、可讀。建立的本體恰好兩格：`account_id` 與 `nickname`；編輯的本體恰好是 `nickname` 加上它所依據的 `expected_nickname`。`member_id`、`activity_id`、任何時刻、任何角色、任何操作者宣稱都沒有格子——而這一點在本步特別值得說明：`faction_id` 也沒有格子。把玩家分進陣營是下一步的命令，所以「順手改名又把挪他進另一組」在這裡不是被拒，而是無處可寫。於是這一列的 `faction_id` 讀回來是空字串，那是如實的現值（「尚未分組」）而不是欄位缺席；回應始終帶著這個鍵，客戶端因此分得開「沒有分組」與「我讀不到這一格」。

兩個業務結論各有各的一句話，因為操作者要做的事完全不同。同一帳戶在同一場活動裡的第二份檔案是 2035（409）：唯一索引才是寫不进第二次的根據，既有那一列不被覆蓋，也不會把沒發生過的事記成成功；要改一個人就去改他已有的那份檔案——不是再按一次按鈕，也不是像 2013 那樣重讀現值。拿著過期現值改名是 2013，與本倉庫其餘每一份資料編輯共用同一枚：落敗者一個字都不寫、審計也不追加，介面只留下「重新讀取這份名冊」這一個出口。暱稱是展示值（剔首尾空白後 1..64 個碼位，控制與格式字元一律拒絕，由 1004 點名該欄），而且**不施加唯一約束**：同一場活動兩個成員重名完全合法，那正是幾十人的活動所需要的，介面靠標識與帳戶登入名分辨他們。

每一次被接受的寫入都在同一個交易裡向 `activity_audit` 追加一筆 `member.create`／`member.update`，帶著活動標識、經 `principal.AuditActor()` 換得的真實操作管理員（換不出操作者的主體會讓整次寫入失敗，而不是被記成伺服器自作自為）、暱稱的前後值，以及一句服務端固定的原因；這一族沒有任何一格接受呼叫端的自由文字。審計寫不進去時，成員列跟著一起消失——「改了卻在活动審計裡查不到」與「審計說有過而這一列不存在」是同一個缺陷。這裡刻意**沒有**的東西：把成員移出活動（這一族沒有 DELETE，也不能改寫一列指向誰）、自助申請與審批、活動層級的邀請碼核銷、活動內的任何角色或權限、以及把成員分進陣營。最後那件事的門已經先建好了：`activity.Service.EnsureFactionAcceptsNewMembers` 必須在分配所在的那個交易內被呼叫，而它返回的「該陣營已停用」那一句会在做出分配端點的那一步拿到自己的機器碼（2035 隨重複檔案結論發出，而 2036～2039 已隨玩家自選陣營那一步發出——因此那一步要從 2040 起另發新碼）。

## 玩家自選陣營與活動開關

**開關屬活動，不屬陣營。**`activities.faction_select_mode`（遷移 0015）每場活動一欄，取值是封閉集合：`disabled`（出廠預設）、`first_only`（每位玩家只能自己選第一次）、`free`（可在還開著的陣營之間來回換）。這一欄用 `ALTER TABLE ... DEFAULT 'disabled'` 加上 `CHECK` 追加，所以既有每一行、以及此後新建的每一場活動都讀成 `disabled`：沒有任何活動會未經明確決定就被開放；而把開關收回也絕不清空、不搬動任何人已經擁有的歸屬。開關是一欄配置，不是生命週期狀態——它不進 `status`，也不是權限。本步沒有發明人數配額、付費切換、冷卻或審批佇列，因為那些都不曾被批准。

**兩道准入，不是一道。**設定由管理側寫：`PUT /admin/activities/{activity_id}/faction-select`，閘與活動資料編輯同一道（`NeedServerAdmin` **加上**該活動的一行指派，判定只經 `identity.AuthorizeActivityScope`），本體恰好 `mode` 與 `expected_mode` 兩格。玩家打不開自己那場活動的開關——他拿到 2011，與任何不屬於管理員身份面的帳戶同一句話。自選是另一條通路，絕不複用管理端那條通用編輯面：把管理端點開放給玩家不叫授權，那叫「誰都可以改誰的行」。玩家這一家掛在新首段 `/player` 之下：`GET`／`HEAD /player/activities`（只列本次交談的帳戶有成員行的活動）、`GET`／`HEAD /player/activities/{activity_id}/faction`（那場活動的現值、他自己的歸屬，以及該活動全部陣營各帶服務端派生的 `selectable`）、同一路徑上的 `PUT` 則恰好帶 `faction_id` 與 `expected_faction_id`。**路徑與本體裡沒有一個格子在說「哪個玩家」**：被寫的那份檔案由服務端按（本次交談的帳戶, 這場活動）讀出來，所以「偽造別人的 Profile」不是被拒，而是無處可寫。

**每條規則都在同一個寫入交易內重新問一遍**，順序是：活動生命週期（歸檔答 2029、停止答 2033、草稿答 2038——玩家自選不是草稿期活動該發生的事，正因為「僅首次」會在還沒開始時就把人鎖死），然後那一欄開關（`disabled` 時 2037），然後是他自己的成員行（讀不到就與幽靈活動同一句不可分辨的 1001），然後是次數規則（`first_only` 下他已選過就是 2039），然後是 `EnsureFactionAcceptsNewMembers`——這條通路是它的第一位呼叫端，所以「該陣營已停用」那句話終於有了自己的機器碼 2036——最後是一個只碰 `faction_id` 一欄的比較-and-set 更新。SQLite 只有一個寫入者，而判定在呼叫端自己的交易內現讀，因此「管理人同時關掉開關或停用那個陣營」這段並發視窗繞不過去：落敗的那一個一個字都不寫、不追加審計，拿到 2013 或對應那句原因。丟掉回應後拿同一份過期依據值重發，也不會產生第二次切換與第二條審計。

**刻意沒有的東西：**沒有自助離開陣營的通路（把歸屬改回「尚未分組」屬管理側的分配通路，而它仍然不存在，所以這一族沒有 `DELETE`，本體裡也沒有一格能表達「目標為空」——解析不出的或空的 `faction_id` 與幽靈同樣是 1001，而「目標等於依據值」是點名欄位的 1004）；沒有管理側的分配與遷出；沒有自助申請與審批、活動層級邀請碼核銷、活動內角色或權限、資產與聊天。派生值（`faction_select_mode`、`can_select_now`、每一項的 `selectable`）恆在回應裡而絕不在請求裡——帶上來就是 1004——於是介面能把「此刻是什麼狀態」與「這次寫入做成了什麼」分成兩句話顯示，而藏按鈕從不被當成那道閘。

**審計沿用同一條規則，只多一句話。**每次被接受的寫入都在同一筆交易裡向 `activity_audit` 追加一筆 `member.faction_select`（設定那一跳是 `activity.faction_select_update`），帶恰好一欄的前後值與一句服務端固定的原因。玩家那一次的動作主是他在這一場活動裡的身份：`identity.AuditActorAsActivityMember` 把「已通過認證的帳戶主體」加上服務層剛在同一交易內讀到的成員標識，換成 `actor.kind = \"player\"` 的記錄。`AuditActor` 本身沒有放寬——它照舊拒絕為沒有伺服器級授予的帳戶憑空造出活動內身份——所以這是另加的一句更窄的話，而不是把規則放開；而恰好持有 `server_admin` 的人在這裡也記成玩家身份，因為那次動的是他自己的歸屬，而成員行仍能解析回那一個帳戶。被拒的寫入什麼都不追加。前端：活動頁多了那張開關卡（三個選項各把自己的後果寫清楚、必經確認框、2013 只留重讀），玩家端不再是佔位——它列出這個帳戶所屬的活動，並為每場活動給出一張自選卡。

## 玩家目錄可見性與資料投影

**誰能在這場活動的玩家目錄裡看見誰，是活動的一欄設定，外加每個人只能往更看不見方向的一層覆蓋。**`activities.member_directory_mode`（遷移 0016）取值是封閉集合：`hidden`（出廠預設）、`same_faction_only`（只列與觀看者同一陣營的成員）、`all_players_except_admin`（列所有玩家，但把管理員身分收起來）、`all_members`（列出這場活動的全部成員）。同一支遷移在 `activity_members` 上加 `directory_visibility`，只有 `inherit`（出廠預設，服從活動規則）與 `hidden`（在活動規則之外再多收一層）兩個值。兩欄都用 `ALTER TABLE ... DEFAULT` 加上 `CHECK` 追加，因此既有每一行、以及此後新建的每一行都讀成預設值：**升級不會讓任何一個原本沒有人能搜尋到的人突然變得可見**，管理人要開放必須明確選一個非 `hidden` 的值。集合裡刻意沒有 `visible`／`public` 這類取值——一格能繞過整個活動規則的開關就不是覆蓋，而是第二套規則。停用陣營的成員仍按同陣營互見（判定看歸屬本身，不看可用旗標），與陣營停用那一步批准的姿態一致。

**無陣營不是一個群體。**`faction_id` 為空的語意是「尚未分組」，不是一組的名字：在 `same_faction_only` 下，兩個都還沒分組的人彼此看不見，每個人只看得見自己。把它讀成同一組會出現兩個後果——出廠形態（所有人都還沒分組）等於一個全開放的目錄，而把某人的陣營收回反而擴大他的可見範圍——兩句都不是批准過的規則。

**同一策略只有一處，先授權篩選、再分頁計數。**列表、搜尋、單筆詳情、計數、篩選候選、分頁與日後指向某個玩家的解析都消費同一個判定函式的輸出：服務端把這場活動的候選行湊齊、逐行問一次可見性，然後才統計總數、切出本頁、按同一個已篩選集合分組出陣營候選。於是「列得出來卻點不進去」「計數比列表多幾筆」「候選裡顯示 12 人而點進去只有 3 行」這類形態在結構上不成立。候選清單與計數取的都是已授權篩選之後的行，因此目錄本身不會變成一枚探測「別人那邊有幾個人」的儀器。這一族的讀取是每請求現讀，背後沒有查詢快取，也不採信請求交來的任何一格：管理人改完設定、玩家換完陣營、覆蓋被落地或指派被撤銷之後的**下一筆請求**就按新規則回答（目前倉庫沒有即時層，因此這裡聲稱的只有請求級失效，不假造推送成功）。

**管理員在自己獲准管理的活動內看全部成員，而這不是參數。**算不算管理視角，只由服務端現讀的兩道閘決定：`NeedServerAdmin` **加上**該活動的一行指派（判定仍只經 `identity.AuthorizeActivityScope`）。兩道都過的人在同一份目錄讀法裡看到全部成員，模式與覆蓋都不改變這一句；持有 `server_admin` 卻沒被指派到這個活動的人，讀到的與普通成員一字不差——「伺服器級管理員不等於所有活動的管理員」這句在目錄上的落點就在這裡，而它也不允許普通玩家借任何請求參數冒充管理視角：玩家那一族的路徑、查詢串與本體裡都沒有那一格，帶上來就撞 1004。

**「管理員身分」只有一個來源。**`all_players_except_admin` 收起來的是「此刻在 `account_server_roles` 裡那一行存在」的帳戶，判據是 `internal/grant` 的現讀，絕不是暱稱、顯示名或任何前端標籤。測試正是釘住這一句：把那個人的活動內暱稱改成聽起來像平民的名字，他依然不在列表裡；把授予撤下，同一行在下一筆請求裡就只是普通玩家。這一格最要緊的方向也寫死在程式碼上——授予讀取失敗時如實報錯，而不降級成「他不是管理員」，否則一次故障就會把該收起來的人放大成可見。

**完全隱藏時，本人仍讀得到自己。**`hidden` 態下目錄對任何人都不列舉任何人，包括他自己——那本來就是這一態的答案，所以它是空的一頁加上 `member_directory_mode: "hidden"`，而不是一種錯誤；介面據此能說「這場活動沒開放目錄」，不會把它唸成「還沒有人加入」。另一條獨立通路是 `GET`／`HEAD /player/activities/{activity_id}/profile`：只按（本次工作階段的帳戶, 這場活動）讀回他自己那一行的活動內投影（成員標識、活動內暱稱、陣營歸屬與展示值、加入時刻、他自己那格覆蓋、活動的模式），不經目錄判定。也就是說隱藏與覆蓋收的都是「別人能不能看見他」，從來不是「他能不能看見自己」。

**目錄輸出是角色對應的欄位白名單。**一行目錄項只有 `member_id`、`nickname`、`faction_id` 與陣營的展示三值（名稱、圖標、顏色）、`joined_at`。登入名、口令形態、帳戶狀態、帳戶標識、任何內部標籤與「他為什麼不可見」那種後台原因一律不出去；「他是不是管理員身分」這一格也只在管理名冊出現——否則普通玩家就多得到一枚「誰是背後的人」的可列舉訊號。管理名冊因此新增兩格投影：`directory_visibility`（服務端現讀的覆蓋）與 `admin_identity`（`internal/grant` 的現讀）。防枚舉沿用既有那一句：查無這個活動、他不是這場活動的成員、那一行屬於另一場活動、以及那一行此刻按規則不給他看，四種原因對外都是同一個 1001。

**端點與既有約定。**管理側兩條：`PUT /admin/activities/{activity_id}/member-directory`（本體恰好 `mode` 與 `expected_mode`）與 `PUT /admin/activities/{activity_id}/members/{member_id}/directory-visibility`（本體恰好 `visibility` 與 `expected_visibility`）。玩家側三條：`GET`／`HEAD /player/activities/{activity_id}/members`（分頁目錄，查詢參數只有 `page`／`page_size`／`q`／`faction`）、`GET`／`HEAD .../members/{member_id}`（同一策略的直查）、`GET`／`HEAD .../profile`（本人投影）。設定那一條與活動資料編輯同一道閘，因此停止態仍可準備「重開之後目錄開多大」，而歸檔一律拒寫（2029）；覆蓋那一格改的是某一行成員的資料，因此先過業務寫入門禁（停止態 2033）。被接受的兩次寫入各自在同一交易裡向 `activity_audit` 追加一筆 `activity.member_directory_update`／`member.directory_visibility_update`，帶一欄前後值、經 `principal.AuditActor()` 換得的管理員身分與一句服務端固定的原因；被拒的寫入一個字不落、一條痕不加。**本步沒有發布任何新機器碼**——結論全部復用既有的 1001、1004、2011、2013、2029、2033，下一枚未發碼仍是 2040。

**刻意沒有的東西：**NPC 目錄與它那套獨立授權（屬 NPC 模組）；把覆蓋做成能放寬活動規則的開關；跨活動一口氣查看全部成員；按暱稱以外的欄位搜尋；把成員移出活動；以及任何「推送失效」的能力。

**目錄那一行還帶出陣營的停用旗標。**`directoryMemberItem` 與本人投影各多一欄 `faction_available`（只增不刪），值是 `activity_factions.available` 的現值本身，刻意**不**折進活動狀態——活動停止時目錄照舊可讀，而介面那句「該玩家所屬陣營已停用」講的就是那一欄。它是三處讀法（目錄、單筆直查、本人投影）共用的同一個現讀，所以列表裡那一行與點進去那一份不可能各說一套。這一欄不構成新的可列舉信號：同一個現值在 `GET`／`HEAD /player/activities/{activity_id}/faction` 的選項清單裡對任何成員本來就是逐陣營敞開的；也沒有為它發任何新機器碼。無歸屬、以及歸屬讀不到展示值這兩種情形它同樣為假，而介面靠 `faction_id` 與 `faction_name` 那兩格把三種假分開念，不拿一個假值冒充「已停用」。合同至今沒有簡介與頭像這類欄位，因此玩家介面對它們只有佔位與一句「這一欄還不存在」。

## 活動標籤定義與其公開範圍

**標籤是一個活動內部一枚有自己穩定身分的標記。**`activity_tags`（遷移 0017）保存標識、所屬活動、名稱、描述、內建圖標鍵、顏色、排序值、可用性旗標與逐列的 `public` 旗標。標識才是身分，名稱不是：改名、換色、停用或設成公開都不會讓任何引用失效，也沒有一條通路能用名稱找到一枚標籤。跨活動同名完全互不相干，而同一個活動裡的重名會被擋下（2040），那是給操作者的防呆——真正讓它成立的是 `UNIQUE (activity_id, name)`，先查一步只決定您聽到哪一句。每一欄的約定都沿用陣營那套而不是另發明一次：名稱剔首尾空白後 1..64 碼位、描述 0..500、同一份內建圖標鍵封閉集合、顏色是 `#RRGGBB` 或空（正規化成小寫）、`sort_order` 0..99999 且同值時按建立時刻再按標識破平、未帶排序值時在交易內現算「當前最大值加一」。`id` 與 `activity_id` 由觸發器釘住，所以「儲存這枚標籤順手把它挪去另一場活動」不是被拒絕，而是無處可寫。**這一族沒有刪除通路**（本步經用戶批准）：停用是唯一能表達「不想再被使用」的地方，行仍列、可讀，而且一個字都不級聯清空——因為真正要緊的引用（將來的通知、文件、批量資產操作、自動化）指向的是標識。

**標籤預設是管理員的內部資訊，而且公開要一枚一枚決定。**`public` 出廠是 0（`DEFAULT 0 CHECK (public IN (0,1))`），升級過的資料庫與新建的活動，都不會在沒有明確決定的情況下被這功能開放。它是逐列的欄位，不是活動級開關：「這場活動全部對外翻開」那種格子會讓「曾經說過哪些標籤」沒有逐筆留痕。建立的本體裡根本沒有 `public` 這一格——新標籤出生即是內部的，所以「保存按鈕預設勾選公開」這種行為在界面上無從發生；對外必須是建好之後那一跳明確的編輯，而那一次編輯自帶一筆審計。**公開的意思只有這一件事：**這份定義本身變得可由該活動的成員讀取。**它不意味著的其他事：**它不是角色，不授予任何權限，也不讓任何一個本來不在玩家目錄裡的人變得可見——誰能被誰看見仍然只由 `activities.member_directory_mode` 與每一行成員自己的覆蓋（遷移 0016）決定，標籤從不參與那個判定。把 `public` 收回成 0 同樣不改寫任何東西：行、標識與任何既有引用都在，只是下一次玩家側查詢不再列出它。這一族讀法背後沒有快取層，這個倉庫也沒有實時層，所以「請求級失效」就是全部能宣稱的範圍。

**兩族端點、兩套准入、兩份 DTO。**管理側：`GET`/`HEAD`/`POST /admin/activities/{activity_id}/tags` 與 `PUT /admin/activities/{activity_id}/tags/{tag_id}`，准入與活動資料編輯、陣營管理同一道閘（`NeedServerAdmin` **加上**該活動的一行指派，判定只有 `identity.AuthorizeActivityScope` 這一處），本體在建立時是四欄加可選的排序值，在編輯時是七欄白名單新值加它們各自的七個 `expected_*` 依據值。玩家側：`GET`/`HEAD /player/activities/{activity_id}/tags`（這場活動的公開定義）與 `GET`/`HEAD .../tags/{tag_id}`（按標識直查一枚），准入只有「這次請求的會話帳戶在這裡有沒有成員行」。玩家投影帶的是 `tag_id`、`name`、`description`、`icon`、`color`、`sort_order`——結構上沒有別的：可用性、`public` 旗標本身、所屬活動、兩個時刻、逐枚標籤的成員名單與任何內部計數都不在那份回應裡，也不是拿 0 或空字串佔位，因為今日的倉儲根本填不出它們。篩選也不是某一處記得寫 `if`：玩家那一族的兩條讀法是各自的 SQL，`WHERE` 裡就帶著 `public = 1`，要把內部定義遞給玩家就必須繞開倉儲方法本身。「查無這枚標籤」「它屬於另一場活動」「它還沒被設成公開」「觀看者不是這活動的成員」四件事都是同一句不可分辨的 1001——玩家這條路徑刻意不是內部定義的存在性探測器——而普通帳戶去敲管理那一族拿到 2011，匿名拿到 2002。兩族讀法都不受生命週期門禁約束：停止與歸檔的活動照樣列出標籤（仍列、可讀；拒的是寫），兩條寫入通路在停止態答 2033、歸檔態答 2029。`accepts_new_assignments` 是服務端派生欄，恆在回應、絕在請求之外（帶著它就是 1004），於是界面能把「此刻的狀態是什麼」與「這一次寫入做了什麼」分成兩句講。

**本步只發布一枚新的機器碼。**2040 是重名那一句；其餘全部復用 1001、1004、2011、2013、2029 與 2033，下一枚未發布的碼是 2041。特別地，「那枚標籤已停用」這個結論刻意**還沒有**對外發布：今日沒有端點會走到它，所以那個判定只活在服務層，先例是同樣的態度——「陣營已停用」那枚碼是在玩家自選成為它第一位呼叫端之後才出現的。

**下一步要呼叫的可用性判定已備妥。**`activity.Service.EnsureTagAcceptsNewAssignments` 必須由貼標那筆寫入自己的交易呼叫，簽名收 `*database.Tx`，於是「先在一個交易查可用、再到另一個無保護的交易寫入」在編譯層就不成立：它在那一個交易內重新問業務寫入門禁、重新讀回這一行、核實它確實屬於這個活動（否則與幽靈同一句 1001），並在標籤已停用時回報 `ErrTagNotAcceptingAssignments`。SQLite 只有一個寫入者，判定時讀到的現值與同一交易內隨後那筆寫入看見的是同一個快照，所以「把人貼進一枚剛被停用的標籤」那段視窗不存在。兩個旗標刻意互不相干：已公開但停用的標籤照樣被拒於新貼標之外，而未公開的標籤照常被管理面使用——`public` 決定誰讀得到這份定義，`available` 決定它還能不能被使用。`activity_tags` 沒有任何欄位指向 `accounts`，因此它不進入訪戶綁定的引用登記表（與 `activity_factions` 同一姿態）；貼標關係表落地的那一天，那一步必須自行補登記與定向測試，否則綁定預檢整體 fail-closed。

**審計說出是誰做的、動了什麼。**每一筆被接受的寫入都在同一個交易內追加一筆 `tag.create` 或 `tag.update` 到 `activity_audit`，操作者是經 `principal.AuditActor()` 換得的管理員身分（換不出主體的那筆寫入整筆回滾，而不是被記成「伺服器自己做的」），並帶七欄白名單的前後值與一句服務端固定的原因。原因句按翻動的是哪一個旗標分岔，讓讀審計的人分得清「這一次是停用」「這一次是對外」與「這一次只是改資料」，而公開那幾句同時寫明**沒有**做的事：沒有放大任何人的可見範圍，也沒有授予任何權限。被拒的寫入一筆都不記，所以留痕筆數等於實際提交數。前端：活動頁面多了標籤定義卡，每一行用**文字**標出內部還是公開（顏色從來不是唯一提示），建立表單沒有公開那一格並如實說明，而把 `public` 翻動之前有一顆確認框會點名這條標籤與它的影響；玩家端多了一張唯讀卡，列出已公開的定義並寫明「給玩家貼標這件事還沒有實作」。

**刻意沒有的東西：**把標籤貼在玩家身上（那是下一步的通路，今日沒有一個端點能吃「某一個人＋某一枚標籤」，界面也不拿空名單或 0 冒充人數）、活動級的一鍵公開、刪除一枚標籤、以標籤為準的權限或角色、配額與審批，以及由通知、文件、批量資產操作或自動化去引用標籤標識——那些將來指向的是穩定標識，而本步不建任何條件運算式語言。

## 玩家業務狀態與顯示名稱

**玩家的業務狀態是那份活動內身份上的一欄，由該活動管理人維護。** `activity_members` 新增 `business_status`（遷移 0018），取值是七個穩定內部值之一——`normal`（出廠預設）、`suspended`、`eliminated`、`dead`、`arrested`、`offline`、`custom`；當且僅當它是 `custom` 時另帶一個 `business_status_custom_id`，指向同一場活動的自訂狀態定義。成對關係（custom 必須恰好一個定義、其餘六個必須為空）與同活動限制都由資料庫觸發器釘住，跨活動拼接不是「呼叫端記得檢查一下」的事。新欄以 `ALTER TABLE ... DEFAULT 'normal'` 落地，因此**升級既不重置任何人的資料，也不需要回填**：每一筆舊資料本來就讀成 `normal`，那是一個不含任何意義的值。

**狀態不是連線狀態，本版本也不帶任何行為。** 這裡的 `offline` 是管理人維護的一個標籤：請求抵達、頁面開啟、時間流逝或日後的心跳都不會改寫這一欄，倉庫裡今日也根本沒有任何「上線」欄位可與之比較。將來若真做上線指示，它會獨立維護並分開顯示——介面把這句話直接寫出來，而不是讓 offline 這個詞暗示存在一套上線系統。同樣重要：規格裡 `dead`、`arrested`、`eliminated` 的狀態行為範例不完整，因此**不從名字推出任何隱含權限**。改狀態只是記錄並顯示它：不凍結帳戶、不清空資產、不把人移出活動，也沒有任何程式碼路徑拿狀態名去決定這些。

**顯示名稱只是展示值。** 每場活動可以覆寫任一內部狀態的顯示名稱（`activity_player_status_labels` 表；空值代表「使用客戶端四語言預設文案」），自訂狀態自己的名稱同樣只是文字。改名不改變內部值、穩定標識或任何人的目前狀態，也不改寫任何歷史引用——四個內部文案以 `zh-CN`、`zh-TW`、`en-US`、`ja-JP` 隨附，而被覆寫或自訂的名稱依原樣以純文字顯示：介面用一般文字元件渲染，絕不交給任何 HTML 或富文字通路。兩張新表的 `id` 與 `activity_id` 由觸發器釘住；把顯示名稱恢復成預設只是清空一欄，不是刪除一個狀態。

**自訂狀態屬於單一活動、只能停用、以穩定標識被引用。** `activity_player_statuses`（遷移 0018）儲存標識、所屬活動、活動內唯一的名稱（重名以 2042 拒絕，跨活動同名互不相干）與出廠為可用的可用性旗標。沿用陣營與標籤的已批准口徑，**這裡沒有刪除通路**：停用只讓新的選用被拒（分配通路給 2041），已經帶著它的人保留並仍看得到名稱，介面標出「該定義此刻已停用」；重新啟用可逆且不搬動任何人。選取一個自訂定義寫入的就是 `custom` 加那個定義的標識；選任一內部值會把標識清回空。

**端點與寫入門禁的位置。** 管理族（准入同活動資料編輯：`NeedServerAdmin` **加上**該活動的一行指派，判定只走 `identity.AuthorizeActivityScope`）：`GET`/`HEAD /admin/activities/{activity_id}/player-statuses`（七個內部顯示值加全部自訂定義，停止與歸檔的活動照舊可讀）、`POST` 同路徑（本體只有 `name`）、`PUT .../player-statuses/{status_id}`（本體恰好 `name` 與 `available` 加兩個 `expected_*`）與 `PUT .../player-status-labels/{status_key}`（本體恰好 `display_name` 加 `expected_display_name`）。狀態定義與顯示名稱屬活動配置，所以停止態仍可準備它們，只有歸檔拒寫（2029）。改某位玩家目前的狀態是業務寫入：`PUT /admin/activities/{activity_id}/members/{member_id}/business-status`（本體恰好 `business_status`、`custom_status_id` 加兩個 `expected_*`）先過業務寫入門禁，因此停止態拿 2033、歸檔態拿 2029。併發保護是對狀態兩欄一起做 NULL 安全的比較-and-set：依據值過期的一方以 2013 落敗且一個字都不寫，而重送「目前就是這個值」是一次誠實的冪等成功，不產生第二條稽核。客戶端能影響的結論仍然不存在：除了上面點名的四格，請求本體沒有任何格子能填狀態或派生值，多塞一格就是 1004。

**普通玩家看得到哪些狀態，沿用目錄規則，不是第二個可見性來源。** 目錄行、單笔直查與本人投影各新增 `business_status`、`custom_status_id`、`custom_status_name`、`status_display_name` 與 `status_available`（全部只增不刪）：看得见的人顯示他目前的狀態，看不見的人什麼都顯示不出來，因為那一行根本進不去結果集。改狀態從不放大或收窄誰能看見誰——那個判定只由 `activities.member_directory_mode` 與單人覆蓋兩處決定——玩家回應裡也不含任何內部備註或原因。**本步發布兩枚機器碼**：2041（那個自訂狀態已停用，不能再用於新的選用）與 2042（這場活動裡已有一個同名的自訂狀態）；其餘複用 1001、1004、2011、2013、2029 與 2033，下一枚未發碼是 2043。兩張新表都不引用 `accounts`，訪戶綁定的引用登記表因此不受影響。

**稽核，以及刻意沒有的東西。** 每筆被接受的寫入在同一交易地向 `activity_audit` 追加 `member.business_status_update`、`player_status.create`、`player_status.update` 或 `player_status.label_update`，帶著前後值（狀態變更那一筆是內部值、自訂定義標識與當時的顯示名稱），操作者必須由 `principal.AuditActor()` 換得，換不出就整筆回滾。被拒的寫入一條痕都不留。**這裡沒有做的：**依規則自動指派狀態、狀態級權限或凍結、由活躍度或心跳自動設為離線、可查詢的狀態歷史表（歷史就是稽核日誌，正因如此冪等重送不得寫第二筆）、任何由狀態驅動的資產或成員變動，以及規則編輯器或工作流引擎。

## 玩家分項限制與活動訪問控制

**六項限制是成員行上的六欄獨立事實，不是一枚總凍結開關。** `activity_members` 新增 `restrict_login`、`restrict_chat`、`restrict_private_chat`、`restrict_trade`、`restrict_transfer` 與 `restrict_item_use`（遷移 0019），每一欄都是 `INTEGER NOT NULL DEFAULT 0 CHECK (… IN (0,1))`。出廠值是「不限制」：升級不凍結任何人，也不需要回填，舊的行直接讀成未限制——這是新增旗標唯一能走的相容方向。倉庫裡刻意沒有總 `frozen` 布爾：一枚總開關會抹掉六項之間被批准的區別，而每一項都各存各欄、各改各的、各取消各的。編輯通路 `PUT /admin/activities/{activity_id}/members/{member_id}/restrictions` 只收被選中的欄對——最多六對 `restrict_*` 加上它們各自的 `expected_*` 依據值；沒提交的欄位在倉儲那筆 `UPDATE` 裡連格子都沒有，所以「取消聊天順手取消私聊或登入」不是被拒，是無處發生。任一提交欄的依據值過期即 2013，整個編輯一個字都不落；新值與現值相同的重送是冪等成功——不寫入，也不追加第二條留痕。

**`restrict_login` 收回的是「進入並繼續使用這一場活動」的資格——只到這裡（用戶批准）。** 它不是帳戶開關：不碰 `accounts`、不停全域登入、不吊銷既有會話，也不動這個帳戶在其他活動裡的行。普通登入照舊能建立全域會話；被擋的是拿那條會話在受限活動裡繼續活動。判定是服務層每請求現讀——玩家族通路（本人活動清單，其行帶著派生值 `access_restricted`；陣營現況與自選；目錄；單笔直查；本人資料；標籤清單與單筆）每一次都要問成員行的現值，既有會話不能靠著登錄那一刻的結論繼續走；旗標收回後的下一筆請求就按新值回答。本倉庫沒有實時層，這句話就是全部的失效形態。**被禁止登入的成員唯一還讀得動的活動通路是 `GET`/`HEAD /player/activities/{activity_id}/restrictions`**——那就是批准的「本人獲准查看有效結果」：六個布林加上成員與活動標識，別的一律沒有（原因句、操作者、時刻都不在外傳那一側；它們活在 `activity_audit`，而本專案不發審計查詢的 HTTP 入口）。一項連被限制的人都問不出內容的限制，就是無法核實的指控，所以這一讀刻意留在門外；其餘活動內通路在旗標生效期間一律 403／**2043**。

**其餘五項今日是判定介面，不是已接線的業務。** 聊天、私聊、交易、轉賬與使用物品在本倉庫沒有端點，因此也沒有對外機器碼——沒有人收得到的結論不發碼（既有口徑）。`activity.Service.EnsureMemberCapability` 逐鍵回答「這個成員此刻被不被擋在這項能力上」，由領域測試取證；將來的聊天或資產通路必須在自己的寫入交易內呼叫它（login 那一鍵已有真實呼叫端；其餘五枚如實記為「尚無業務接入證據」）。管理對話框與玩家卡片都把這件事寫成文字，也不擺任何半成品的業務按鈕。

**管理者憑伺服器級准入行事；六枚旗標綁的是成員身份——所以凍結一個玩家不會把管理者一起鎖在解除的門外。** 編輯與管理讀法走 `requireActivityScope`（`NeedServerAdmin` 加上這個活動的一行指派），那道閘從不問成員行，設定限制的人總能解除它，哪怕目標也持有 `server_admin`。兩個方向都沒有發明的豁免：同時持有 `server_admin` 的成員在 `/player` 族照樣被擋（旗標作用在他的成員身份上），他的 `/admin` 通路憑授予與指派照常走得動——兩個身份兩個答案，不是一個身份可以靜默壓過另一個。Root 與系統主體在玩家族沒有可指向的成員行，與「不是成員」同收 1001。

**端點、門禁與審計。** 編輯屬業務寫入：先過 `EnsureBusinessWritesAllowed`（停止 2033、歸檔 2029），坐落活動作用域准入之下；被接受的寫入向 `activity_audit` 追加一條 `member.restrictions_update`，操作者經 `principal.AuditActor()` 現換，changes 只帶實際翻動欄位的前後值。原因句按翻動的鍵分岔——翻動 `restrict_login` 那一句寫明批准邊界（活動級、下一筆請求即生效、不停全域會話、不動其他活動），單獨解除那一句說門重新按現值回答，其餘五項則被點名為「尚未上線業務的判定依據」。名冊行新增六欄（只增不刪；恆在回應、絕在請求——六對白名單欄以外送出派生值就是 1004）。**本步只發布一枚機器碼：** 2043（403——你在這一場活動的訪問資格已被限制；這不是帳戶停用）。其餘復用 1001、1004、2011、2013、2029 與 2033，下一枚未發碼是 2044。遷移 0019 不新增表、也不新增任何指向 `accounts` 的引用，訪戶綁定登記表不受影響；0014 的身份觸發器繼續釘死 `id`／`activity_id`／`account_id`，六欄新旗標照常可改。

**刻意沒有的：** 由這些旗標驅動的全域封禁、吊銷會話或停用帳戶；按時間自動解除；限制改變誰能看見誰（那仍由遷移 0016 那兩欄決定）；給未接入業務發機器碼；把審計原因外傳給玩家；以及推送通路——失效是請求級的，這是本倉庫今日能如實宣稱的全部。

## 釋出後的使用方式（規劃）

- 一人在這臺機器（Windows 或 Linux）上託管服務端
- 其他人在同一區域網內用瀏覽器加入
- 無需第三方註冊；資料只儲存在主機上

## 從原始碼建置

Windows 執行檔的圖示是產生出來的、不納入版本控制：`cmd/evernight-server/resource_windows_*.syso` 由 `assets/icons/EvernightRealmBackendRounded.ico` 推導。全新複製的倉庫在編譯前先執行

    python tools/icons/generate_icons.py

否則產生的執行檔沒有圖示，而 `go build` 不會報錯。`python tools/icons/generate_icons.py --check` 只核對現況，不寫入任何檔案；詳見 `tools/icons/README.md`。

本專案沒有託管 CI：提交前請在本機跑品質入口 `go run ./tools/check`（後端格式、`go vet` 與測試，並連帶前端閘門）。
