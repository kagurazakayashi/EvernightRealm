# 長夜幻境（EvernightRealm）

> 在自己的機器上，為你的小圈子搭建一座私密的虛擬世界——管理活動、扮演角色、交換虛擬資產。

[English](./README.md) · [簡體中文](./README.zh-CN.md) · [繁體中文（臺灣）](./README.zh-TW.md) · [日本語](./README.ja-JP.md)

## 這是什麼？

長夜幻境是一個自主部署、離線優先的平臺，面向小規模玩家群體：一起推進沉浸式活動、扮演角色、交易虛擬資產——全部在區域網內完成，不需要公網、雲賬號或遙測。

## 功能規劃（開發中）

- **沉浸式活動**：為你的群體編排場景、階段與事件
- **角色與身份**：玩家、NPC 與管理員的角色，共處一個私密世界
- **虛擬資產**：物品有真實歸屬，交易可審計
- **私密聊天**：訊息只留在你自己的伺服器上
- **離線優先**：一切執行在你自己的機器上，不依賴雲服務

## 當前狀態

長夜幻境正在積極開發中，尚未釋出穩定版本。服務端現在可以建置為**單一可執行檔**：同一個連接埠同時提供網頁介面（目前是可切換語言、可偵測伺服器連通性的應用殼，業務功能仍在開發）與 API 端點，瀏覽器直接開啟它的位址即可使用，不需要另外部署靜態服務。

服務端另提供一個維運命令來產出**一致性備份包**：單檔資料庫快照（服務執行中即可產出，不是複製活躍的 WAL 主檔），連同設定檔與媒體／文件／上傳目錄，逐檔記錄大小與 SHA-256 並附一份清單。與之配套的 `restore` 命令能把這份包還原成一個**全新的空資料目錄**：逐檔依清單重算校驗和，落地前後各讀一次快照的資料庫事實並與清單對照，**不覆蓋任何既有目錄**（要覆蓋請先自行備份該目錄），拒絕比目前執行檔更新的資料庫結構版本，並把這次還原本身寫成一筆伺服器端審計記錄。備份包還不能加密，舊包也不會自動清理。

一次性 Root 初始化**只有本機命令這一條入口**：

    evernight-server init-root --password-stdin --data-dir <資料目錄>

它從標準輸入讀口令（前兩行是口令與確認），把 Argon2id 編碼寫進該資料目錄的 `config.yaml`，不輸出任何秘密——不寫明文，也不會自動產生或顯示一個「出廠口令」。交出伺服器最高權限的授權依據是「能在伺服器主機上執行命令」，所以這一步不開任何 HTTP 端點、不佔連接埠；CORS、客戶端自報的位址、介面上隱藏按鈕都不構成授權。服務持有單寫入實例鎖時、`ER_SECURITY_ROOT_PASSWORD_HASH` 蓋著檔案時、或審計表尚未建立時，本命令一律拒絕；寫成功之後也不會再開放第二次——要換口令，走服務內的已認證改密流程（Root 登入後 `POST /auth/password/change`）；只有口令真的遺失了，才用下面那條本機恢復通路。只讀的 `evernight-server root-status` 能回答「現在有沒有 Root」，它不建立也不改動任何檔案，而且只回答這麼多：不給出配置路徑、雜湊或任何引導秘密。成功與拒絕都會寫進 Root 審計表，且不記錄口令。

Root 口令遺失後的恢復同樣只有本機命令這一條入口：

    evernight-server recover-root --password-stdin --confirm --data-dir <資料目錄>

它也只從標準輸入讀新口令（前兩行是口令與確認），不接受命令列上的口令值，並且要求服務已經停止：運作中的服務把憑據讀在記憶體裡，改設定檔不會讓它回頭更新，那樣只會做出「終端說成功了、舊口令其實還登得進去」這種比拒絕更難查的狀態。恢復不問也不驗舊口令——能在這台主機上執行命令、能讀寫那份設定檔，就是這個動作全部的授權依據；因此它也不設後門口令、不產生可下載的恢復檔、不開任何 HTTP 端點。成功時設定檔裡那份憑據被覆寫為新口令的 Argon2id 編碼，Root 名下全部會話在同一筆資料庫交易裡被撤銷（下一個請求即被拒），並留下一筆 `server.root_recover` 審計記錄；一般帳戶的會話一枚都不動。撤銷與審計寫不進去時，設定檔會被換回原本那份憑據、回報失敗，可用狀態與動筆前一致（連回滾都失敗的雙重故障會以 Error 寫進執行日誌檔案，並明確要求人工補記）。`--confirm` 是必須明確給出的旗標：覆蓋的代價是舊口令永久失效加上 Root 全部裝置登出。設定檔裡還沒有憑據時本命令拒絕並指向 `init-root`；已有值即使壞到解不開（那種狀態下誰都登不進去）也照樣能恢復——這正好是 `init-root` 會拒絕的形態，兩條路各自只有一種成功形態。

首次啟動的介面要如實顯示「還沒初始化」，服務端因此另外回答一個唯讀的 `GET /root/init-status`：只有設定檔是否存在、是否已有 Root 憑據、環境變數覆蓋是否處於設定狀態這三個布林值，不回傳路徑、長度或任何憑據片段，也不寫資料庫、不寫審計。它把「有沒有」說出來，不說「怎麼改」——初始化 Root 仍然只有 `init-root` 這一條在伺服器本機上執行的通路（遺失口令後的覆寫是上面那條 `recover-root`，兩者都不提供網路入口）。

## 登入與管理自己的帳戶

身份階段的功能現在已經實作、可以使用：登入、查看目前工作階段、登出、管理自己的裝置、修改自己的口令，以及 Root 建立帳戶、管理管理員目錄、停用與恢復管理員登入、重設管理員登入憑據、軟刪除管理員（見下一節），以及 Root 設定伺服器的帳戶建立策略（再下一節），還有管理員在該策略下建立一般帳戶、翻閱一般帳戶目錄、讀取與維護單筆資料、停用與恢復某個一般帳戶的登入、重設某個一般帳戶的登入口令（建號見上一節，目錄、資料、停用與憑證各看後面四節）。限制同樣如實寫在前面兩點。其一，帳號只從以下幾個入口產生：Root 憑據本身由伺服器本機的 `init-root` 建立，伺服器管理員由 `POST /root/admins` 開設，一般帳戶則要嘛由 `POST /admin/accounts` 建立——這條只在 `admin_create_standard` 開著時成立，而且只認已認證的伺服器級管理員——要嘛由自助註冊 `POST /auth/register` 產生：它匿名可讀、只在 `sign_up_open` 為真時開放，交回一個由本人自設口令的一般帳戶，不簽發任何工作階段，也永遠建不出管理員。自助註冊現在已實作，且開放、審批、邀請碼三種模式都已上線（邀請碼模式由 `POST /auth/register` 把一枚有效碼核銷成一個可立即登入的普通帳戶，`GET /auth/capabilities` 的 `invite_code_required` 告訴共享表單何時顯示邀請碼欄位）。訪客進入也已實作，而且就是它被刻意限制的那條路：`POST /auth/guest` 在同一筆交易裡建出一個**由伺服器命名**、`account_type` 為 `guest` 的帳戶並簽發一枚工作階段，而登入前的介面只有同一個匿名端點回過來的 `guest_open` 才決定要不要露出這扇門。帳戶名由伺服器產生（`guest_<uuid>`），請求裡沒有一格能填它；暱稱只是展示資訊——允許與他人同名、不是憑據，也沒有任何通路能拿它換回一枚工作階段。訪客不攜帶任何伺服器級授予，所以管理端與 Root 端對他一律回 2011，他也枚舉不到全站帳戶。工作階段本身是普通的：到期、閒置、登出撤銷與裝置名額規則和其他帳戶一字不差，而登出或失去這一枚就結束了這一趟。這條通路還要如實寫明的第二件事：只有人主動按下才會建立，頁面載入、重新整理與重連都不寫任何東西，也沒有排程批次清理舊訪客行的工作。其二，服務端自己不做 TLS 終結：預設監聽是 `127.0.0.1:5206` 上的明文 HTTP，只有當請求確實經 TLS 抵達時（也就是你在它前面自行放一層終結 TLS 的反向代理），工作階段 Cookie 才標 `Secure`、才下發 HSTS；程式不含任何憑證處理，HTTPS 是這套程式之外的部署選擇。

身份相關的端點沒有版本前綴——沒有 `/api/v1`：

- `POST /auth/root/login`（只用 Root 口令）與 `POST /auth/login`（登入名加口令）。每次成功都簽發全新工作階段並覆寫舊 Cookie，舊 Cookie 不會被沿用。
- `GET /auth/session`、`POST /auth/logout` 與 `POST /auth/session/rotate`——讀取目前工作階段、撤銷恰好這一枚工作階段（幂等），或換發本工作階段的秘密。
- `GET /auth/devices` 與 `POST /auth/devices/revoke`——只列舉並撤銷目前登入主體名下的工作階段；沒有任何請求能指名別人的裝置。
- `POST /auth/password/change`——必須在請求中當場交出目前口令；成功後該主體名下全部工作階段（含這臺裝置）一起被撤銷。

瀏覽器路徑的工作階段秘密放在 `HttpOnly` Cookie 裡；原生客戶端從回應標頭讀出後以 bearer 秘密攜帶。登入失敗反覆發生後按「來源位址與登入目標」限流（HTTP 429，附 `Retry-After`），Root 入口同樣適用，且被擋的嘗試不會指出撞上的是哪個帳戶。`device_policy` 設為 `single` 或 `limited` 時，會丟掉較舊的工作階段，或在名額用盡後拒絕新的登入。帶有「首次登入必須改密」標記的帳戶，只放行目前工作階段查詢、登出與改密流程，其餘受保護端點一律回 2010，直到改密完成。

兩條維運邊界維持不變：備份與還原仍是 `evernight-server` 子命令，沒有 HTTP 入口；審計記錄只由服務層寫入，仍然沒有審計查詢端點或網頁主控台。執行日誌按自然日切檔，預設不自動刪除（`retention_days=0`）：不讓日誌無限增長是維運者的工作，程式本身不會隨時間給日誌總量設上限。

## Root 管理管理員目錄

Root 的工作階段是第一批人力操作者進來的管道：`POST /root/admins` 帶 `login_name`、`display_name` 與 `password` 開設帳戶；`GET /root/admins` 是分頁的管理員目錄（`page`、`page_size` 上限 100、`status` 可按 `all`／`active`／`disabled`／`deleted` 篩選，依授予時刻由新到舊排序，並回顯 `page`、`page_size` 與 `total`）；`GET /root/admins/{account_id}` 讀取單筆資料；`PUT /root/admins/{account_id}` 編輯它；`DELETE /root/admins/{account_id}` 軟刪除該帳戶，請求本體一個欄位都不帶——多帶任何欄位都會被打成 1004；`PUT /root/admins/{account_id}/status` 停用或恢復該帳戶的登入，請求本體只有 `status` 與 `expected_status` 兩個欄位；`PUT /root/admins/{account_id}/password` 重設該帳戶的登入口令，請求本體只有 `password` 一個欄位。讓新帳戶成為管理員的是端點本身，不是請求內容：這裡沒有 `role`、`account_type` 或 `subject_kind` 可以填，多帶的欄位會被打成 1004。授權的輸入是「這次請求解析出的主體就是 Root」，所以普通帳戶與管理員自己的工作階段都拿到 2011（403）——管理員既不能建立或管理同級管理員，也不能把自己昇格，重新登入一次同樣改變不了這件事。目錄只列管理員帳戶；配置的 Root 不是其中一行，也永遠不會變成一條可被普通帳戶介面編輯的記錄。

初始口令由 Root 親自交出、且只用一次。它走的是與其他任何憑據同一套 Argon2id 服務，帳戶帶著 `must_change_password` 入庫，伺服器在任何回應裡都不回顯該口令，也不存在任何預設口令。於是那個人首次登入拿到的工作階段，只被允許存取查看目前工作階段、登出與改密這一組入口——其餘受保護端點一律回 2010，直到改密完成——而改密成功會讓該帳號的所有裝置退出。這些規則本就適用於任何帳戶，本步補上的是那面旗標的來源。

登入名的唯一性走的是與登入通路同一個正規化鍵（NFKC 加全量大小寫折疊），並由帳戶表上的唯一索引兜住：已被佔用的名字回 2012 且不建立任何東西，所以連點兩次、或在回應丟失後整筆重試都不會多出第二個帳戶，而那一句拒絕也不會回顯既有帳戶的任何資料或任何憑據。建立帳戶、授予 `server_admin`、把 `admin.create` 追加進 Root 審計，全部落在同一個交易裡——任何一處失敗都不會留下半成品管理員，也不會留下無痕的特權變更——而審計記錄裡只有身分欄位，絕沒有口令或其雜湊。

編輯的白名單只有一個欄位：`display_name`，連同它所依據的現值 `expected_display_name` 一起提交。狀態、憑據、首次改密旗標與帳戶類型不在這條通路之內，UPDATE 語句也只碰這一欄——「儲存普通資料順帶覆蓋隱藏欄位」在語句形狀上就不存在。若儲存的值在頁面打開之後已被改動，整個編輯以 2013（409）被拒絕且什麼都不寫入，這與改密使用的同一套 compare-and-set 保護同源。標識格式不對、帳戶不在目錄、帳戶確實不存在，都收到同一個 1001，這個端點因此不是列舉探針。回應只含可展示事實——絕不帶密碼雜湊、工作階段秘密、恢復碼或任何配置——Root 的每次成功編輯都會追加一條 `admin.profile_update` 稽核，僅帶顯示名的前後值；被拒的編輯不寫任何記錄。

停用與恢復走另一條只有一個欄位的端點。停用後新登入會被拒絕（與其他登入失敗同形，伺服器不會說「這個人被鎖了」），該帳戶現有會話在同一筆資料庫交易裡全部撤銷，並追加一條帶前後狀態、`disabled_at` 前後值與 `revoked_sessions` 的 `admin.disable` Root 稽核；主體此刻是否可用依每個請求現讀資料庫，被停用者的既有會話在任何受保護入口都換不出受信主事人。恢復（`admin.enable`）只恢復重新登入的能力：停用時撤銷的會話保持已撤銷、不會復活，尚未完成的首次改密義務仍然有效；Root 與管理員停用其他管理員都不構成合法目標。狀態寫入是對呼叫端所見現狀的一次 compare-and-set——對著過期依據或重複操作都以 2014（409）拒絕且什麼都不發生：不改狀態、不撤會話、不記稽核。已明確完成的操作不倒退，只有停用生效之後發起的新操作被拒絕。UPDATE 語句只碰 `status` 與 `disabled_at` 兩欄，「停用順帶清憑據或旗標」在語句形狀上就沒有發生點；被停用者仍留在目錄裡（授予列保留），這正是他可被恢復的前提。

重設登入憑據是第三條單欄位子資源端點。`PUT /root/admins/{account_id}/password` 只帶 `password` 一個欄位——Root 親自交出的暫時口令，交付語意與開設時同一套批准方案：伺服器不生成口令、任何回應不回顯，口令只在請求本體裡出現一次；日誌、稽核與回應都不含口令材料，線下交付管道在協議之外。一次成功的重設在同一筆交易裡落地三件事：舊口令立即失效、名下全部會話即刻撤銷（`revoked_sessions` 是權威計數）、該帳戶下次登入必須改密（沿用與本人改密同一個 2010 門閂）。它與本人改密是兩個用例而不是同一個：本人改密要交出現行口令作再認證並清掉義務，Root 重設他人恰恰發生在拿不出——也不該拿出——現行口令的場合，成功後義務被重新設為生效。重設因此不帶 compare-and-set 依據值：任何湊出來的錨點驗證的都不是它宣稱的東西；重複提交不是 2013/2014 那種「陳舊依據被拒」，每一次都是完整生效的重設，各留一筆 `admin.password_reset` 稽核（記改密義務旗標前後值與撤銷數量，絕無憑據），所以介面在結果不明時不得自動補發。重設不改的事實同樣真實：UPDATE 語句不碰 `status` 與 `disabled_at`——對停用中的目標重設成功，目標仍停用、新登入仍被拒（與其他登入失敗同形），要恢復登入仍走 status 那條通路；重設也不是撤權、改名或刪除，授予列原樣保留。格式不對的標識、幽靈標識、未持有授予的帳戶與已物理刪除的目標一律回 1001——已軟刪除的目標回 2015，因為那裡的記錄確實還在，拒絕的是它的狀態；非 Root 回 2011，形狀不合格的口令回 1004 並點名 `password` 欄位。

刪除管理員是一種狀態，不是清庫。`DELETE /root/admins/{account_id}` 不帶請求本體，一次成功在同一筆交易裡落地三件事：登入停止、名下全部會話即刻撤銷（回應給出權威計數 `revoked_sessions`）、追加一條 `admin.delete` 的 Root 稽核，內容正是後來者解釋這次刪除所需的身分快照——登入名、改寫前與改寫後的顯示名、狀態前後值、`deleted_at` 前後值、撤銷數量——且絕不含任何憑據材料。帳戶那一列本身留下：它的標識、它的登入名鍵、它的授予列、它的會話列、它的稽核列，全都仍然指向同一個穩定帳戶，因此歷史操作不會變成指向虛無，也不會被悄悄改記到 Root 名下。物理清庫因此不在本步實作，也不是隨手能做的事：被引用的列根本刪不掉。刪除是終態。沒有恢復入口——`PUT /status` 會拒絕，因為停用與刪除是兩種狀態，既有的恢復登入通路不得讓已刪除帳戶復生——而對已刪除的目標發起編輯、重設憑據或再次刪除，都以 2015（409）回覆，這個機器碼的意思就是「這個人存在，但已刪除」。資料庫層面另有一道觸發器讓已刪除的列不可再被改寫，未來任何寫通路都沒辦法悄悄把它撈回來。有一處可展示資料在刪除時被匿名化：`display_name` 改寫為 `DEL_<UTC 日期>_<原名>` 形狀的佔位字串，長度沿用同一份預算，於是目前記錄不再把舊名字呈現為現行名字。而只追加的歷史刻意不動——刪除之前寫下的稽核仍保留它當時記錄的名字，那正是舊操作至今可解釋的理由。登入名的正規化鍵繼續佔用，因此不可復用：已刪除帳戶的名字沒辦法再註冊一次。已刪除的管理員仍列在目錄裡（`status=deleted`，目錄與單筆回應帶 `deleted_at`），其詳情唯讀。不提供批次刪除，請求也不帶原因文字；配置的 Root 憑據不是目錄裡的一列，因此永遠不構成刪除目標。

另有兩個回應欄位按「只增不刪」的演進規則補上：登入與查看目前工作階段的回應現在帶 `roles`，內容是服務端為該主體現讀到的授予（沒有授予時欄位缺席），客戶端據此決定載入哪些入口。它本身不授予任何東西——每個端點仍在每次請求上重讀可信主體。


若部署要讓組態白名單裡的跨來源瀏覽器呼叫這些端點，`cors.allowed_methods` 必須把 `PUT` 與 `POST` 一起列入，刪除端點還要列入 `DELETE`——出廠預設仍是 `GET`／`HEAD`／`OPTIONS`，來源白名單始終是組態決定，本節不為此放寬任何邊界。

## 伺服器的帳戶建立策略

三個值說出這個部署對「新增可登入的一般帳戶」的打算：`admin_create_standard`（管理員能否建立一般帳戶）、`self_register_mode`（`closed`、`open`、`approval` 或 `invite`，四者都已上線：開放建出可用帳戶，審批落成待批申請，邀請碼把一枚有效碼核銷成可用帳戶）與 `guest_enabled`（能否建立臨時的訪客帳戶）。`GET /root/account-policy` 讀取這三個值，`PUT /root/account-policy` 把它們當成一份文件一次寫入。讀寫都只有 Root 可以：管理員自己的會話拿到 2011，沒帶憑據拿到 2002，跨站來源在碰到資料庫之前就被 2005 擋下——「管理員能不能建立一般帳戶」是這個端點會設定的值，而「管理員能不能改伺服器策略」根本不是一個值。三個欄位彼此獨立，而且一個都不能少：漏掉一個開關會被打成 1004 並點名那個欄位，因為沉默是介面漏了欄位，不是「把那個入口關掉」的決定。

這裡刻意沒有 compare-and-set 依據值，因為這是一份只有 Root 會寫的文件：重複保存是同一次狀態的再一次確認，每一次都追加一條 `server.account_policy_update` 的 Root 稽核，內容是每個真的移動過的欄位的前後值（此外沒有任何東西——不含帳戶標識，也不含任何憑據材料）。值持久在遷移 `0008` 建立的那張單行記錄表裡，所以存好的變更對下一條請求立即生效，重開程式後不需要任何重啟動作也會讀回同一份值，而且一律不寫回 `config.yaml`；那一行刪不掉，也不可能多出第二行。

策略值不等於能力。合成的算法仍然是「策略說要開」**而且**「這條通路真的存在」——只是此刻四條通路都已上線，所以那三個布林現在如實跟著開關走：`GET /auth/capabilities` 匿名可讀、`no-store`，回應恰好三個布林——`sign_up_open`、`invite_code_required` 與 `guest_open`。`guest_open` 只是登入前介面關於訪客那扇門的提示，從來不是准入判定：`internal/guestacct` 會在寫入那筆交易裡現讀策略，所以拿到一份過期的 `true` 也進不去。`invite_code_required` 只在生效模式為 `invite` 時點亮，讓共享的註冊表單知道要不要顯示邀請碼欄位；它只是顯示依據，既不是模式名字，也不是准入判定（寫入那一刻的事務會重讀策略）。它不回顯模式名字、不回顯 `updated_at`、不含管理員建號開關、不含任何帳戶清單或閾值。四個模式名字（`closed`、`open`、`approval`、`invite`）現在都寫得進去；寫入一個尚未上線的模式會被打成 2016（400），這句話的意思是「名字認得，流程還沒上線」，與 1004 那句「這個值不存在」是兩句刻意分開了的話，只是本版本已沒有任何被批准的模式處於那種狀態。任何不認識的值永遠不會被往下收成 `closed`，也不會被往上放成最寬的模式。日後某條流程真的上線時，它會登記自己的那一項能力，並在自己那筆交易裡現讀當下生效的策略，而不是快取一份先前讀到的值。

這三個開關也不會伸到 Root 自己身上：開設管理員（`POST /root/admins`）與伺服器本機的憑據命令（`init-root`、`recover-root`）都不讀這張表，所以把 `admin_create_standard` 關掉，不會讓一台伺服器落到「既沒有管理員、也沒有找回來的路」的狀態。與其餘寫入端點相同，開放跨來源呼叫的部署要把 `PUT` 列進 `cors.allowed_methods`，出廠預設仍然只放行 `GET`、`HEAD` 與 `OPTIONS`。

## 管理員建立一般帳戶

已認證的伺服器級管理員透過 `POST /admin/accounts` 一次建立一個一般帳戶。請求本體恰好帶 `login_name`、`display_name` 與一次性 `password` 三個欄位：沒有角色、帳戶類型、審批狀態或活動的格子，因為「新建的是哪一類主體」由端點決定而不是由請求決定——`standard`、啟用中、不帶任何伺服器級授予、`must_change_password` 為真，與 Root 開設管理員使用同一套一次性憑據策略。

通路開不開在寫入那一刻判定：建立交易現讀策略列，`admin_create_standard` 關閉時回 2017（403）——Root 走這條端點也一樣被拒，這個開關不豁免任何主體；沒有伺服器級權限的主體回 2011，登入名（正規化後）已被佔用回 2012。這裡刻意沒有給管理員的「開關預讀」端點：策略現值仍然只有 Root 讀得到，權威答案永遠出自建立交易內現讀的那一刻。新帳戶之後和其他帳戶走同樣的路使用系統：首次登入必須改密（改完之前其餘受保護入口一律 2010）。建出來的帳戶只是一個帳戶——沒有活動檔案、沒有資產、不在任何名冊上——介面如實說明，不冒充已配置好的活動大廳。

一次成功建立會在 Root 域審計追加一條 `account.create_standard`，操作者是真實發起的那位管理員（帳戶級身分，不是 Root，也不是 system）：伺服器級動作不會去借一個它並不擁有的 `activity_id`，那張表的形狀上也沒有這一欄。本功能不新增任何審計查詢入口：能建號的管理員依舊讀不到 Root 域審計，那仍然歸 Root 自己。與其餘寫入端點相同，開放跨來源呼叫的部署要把 `POST` 列進 `cors.allowed_methods`；出廠預設仍只放行 `GET`、`HEAD` 與 `OPTIONS`。

## 管理員打理一般帳戶目錄

已認證的伺服器級管理員除了建號，還能翻閱與修剪這本名冊：`GET /admin/accounts` 是分頁目錄（`page`、`page_size` 上限 100、`status` 依 `all`／`active`／`disabled` 篩選、`type` 依 `all`／`standard`／`guest` 篩選、`q` 依登入名或顯示名做子字串比對），依建立時刻由新到舊排序，並回顯 `page`、`page_size` 與 `total`；`GET /admin/accounts/{account_id}` 讀取單筆詳情；`PUT /admin/accounts/{account_id}` 編輯它，請求本體只有 `display_name` 與它所依據的 `expected_display_name` 兩個欄位。

這本目錄的範圍是一條邊界而不是一句偏好：它列的是**不攜帶任何伺服器級授予**、且未進入刪除終態的帳戶（普通與訪客都在內，`account_type` 那一欄就是把來源如實講出來）。持有 `server_admin` 的人——包括敲這條端點的操作者自己——歸 Root 的管理員目錄；設定 Root 根本不在 `accounts` 表裡，結構上不可能成為一行。兩本目錄因此互斥，誰也不會「順手」把對方的人列進來。沒有伺服器級管理權的主體讀目錄、讀詳情與編輯都拿 2011（403），匿名拿 2002：普通帳戶與訪客因此沒辦法枚舉全站帳戶，這件事成立在服務層的判定上，不靠介面藏起入口。標識格式不合法、帳戶不存在、他是管理員、他已被刪除，四種輸入都收到同一個 1001，這條端點因此不是「某個人是不是管理員」的探針。

顯示名的編輯沿用第一部分與 Root 那側已經規定的規則：登入名自建號起是不可修改的身分錨點（介面也這麼講），而憑證、權限與安全狀態（口令、首次改密旗標、帳戶類型，以及另走一條子資源的狀態）都不在這張資料表單裡——本體多帶任何隱藏欄位都打成 1004，UPDATE 語句裡那些欄位連出現都沒出現。並發保護是同一形的 compare-and-set：依據值已不是資料庫現值時整個編輯不發生並回 2013（409），處置與 Root 那邊逐字相同（重讀服務端現值再決定），所以本步不新增任何機器碼。被拒的編輯不留審計，成功的編輯在 Root 域追加一條 `account.profile_update`，操作者是真實發起的這位管理員（帳戶級身分，不是 Root 也不是 system），前後只有顯示名那一欄的舊值與新值；本功能同樣不新增任何審計查詢入口。

回應只有可展示事實——絕不含口令明文、Argon2id 雜湊、會話材料或登入名的內部正規化鍵。單筆詳情也不放活動、資產與訊息這三塊：那些模組尚未實作，這裡不拿空陣列或 0 冒充一份查得到的真相。一般帳戶的刪除與改角色同樣還沒開放——那兩樣能力今天只有 Root 對管理員的一側；一般帳戶的登入停用與恢復見下一節，憑證重設見再下一節。跨來源部署的瀏覽器要讀這條目錄得把 `GET` 列進 `cors.allowed_methods`（出廠預設已含 `GET`、`HEAD` 與 `OPTIONS`），要儲存資料則還得列入 `PUT`；預設設定未做任何放寬。

## 管理員停用與恢復一般帳戶登入

`PUT /admin/accounts/{account_id}/status` 停用或恢復一個一般帳戶的登入，請求本體只有 `status`（`active` 或 `disabled`）與它所依據的 `expected_status` 兩個欄位。動的是這個帳戶在整台伺服器的登入能力，不是某一場活動裡的玩家限制：停用之後新登入被拒絕，他在每台裝置上的現有會話全部被撤銷、需要重新登入。活動內的禁言、交易凍結與陣營限制不在這裡，也尚未實作。

停用與恢復沿用 Root 那側已經核准的同一條底層機制（狀態寫入與會話撤銷落在同一個交易裡），但目標資格獨立判定：這條通路只認不攜帶任何伺服器級授予、且未進入刪除終態的帳戶，所以普通管理員動不了另一位管理員，也動不了自己——那三種情形與「查無此人」同樣收斂成 1001；設定 Root 不在 `accounts` 表裡，結構上就不是一行。授權檔位仍是伺服器級管理權（沒有它回 2011，匿名回 2002），本功能沒有把任何活動作用域的角色放大成伺服器級停用，也沒有新增權限檔位。

恢復只恢復「重新登入」這一件事：停用期間被撤銷的會話保持失效、不會復活（撤銷是不可逆的事實，恢復通路一個會話都不碰），尚未完成的首次改密仍然欠著（重新登入後照舊被 2010 擋住），帳戶的其他限制也不因恢復而解除，已被刪除的帳戶更不能被這樣恢復。多重限制從來不是一個 Active 布林值：`status` 管能不能登入、`must_change_password` 管登入後要不要先改密、`account_type` 講來源、刪除是終態，四件事各由各自的欄位與通路回答。

併發與重複由同一形的 compare-and-set 處理：`expected_status` 已不是資料庫現值時整個操作不發生——狀態沒改、會話沒撤、審計沒記——並回 2014（409）。這句話與 Root 那側逐字相同，處置也一樣：重讀目標現狀並重新確認，而不是把那顆按鈕再點一次，因此本功能不新增任何機器碼。SQLite 的單寫者把併發串行化，先提交完成的寫入是不倒退的事實，停用生效之後的新操作在會話解析邊界就被拒。一次成功的變更要在 Root 域追加一條 `account.disable` 或 `account.enable`，操作者是真實發起的那位管理員（帳戶級身分，不是 Root 也不是 system），帶前後狀態、前後停用時刻與這次撤銷的會話數量；被拒的變更不留審計，本功能同樣不新增任何審計查詢入口。

回應回顯變更後的服務端現值與 `revoked_sessions`，絕不含口令、憑證雜湊或會話材料；訪客帳戶走同一條通路，因為今日他沒有可登入的憑據通路，那次停用通常撤不到會話（數量為 0），而狀態落庫仍是如實事實。介面在提交前用確認對話框講完目標、影響範圍與「這不是刪除」，成功後重新讀取目錄與詳情的真實狀態。跨來源部署要儲存這條狀態得把 `PUT` 列進 `cors.allowed_methods`；出廠預設未做任何放寬。

## 管理員重設一般帳戶憑證

`PUT /admin/accounts/{account_id}/password` 把某個一般帳戶的登入口令換成管理員親自交出的那一個一次性口令，請求本體只有 `password` 一個欄位。它複用 Root 重設管理員憑證時建立的那套元件——同一個口令派生實作點、同一條強制替換雜湊的倉儲寫法、同一把定向撤銷會話的刀——但操作者、目標類型與管理範圍各自校驗：授權檔位仍是伺服器級管理權（沒有它回 2011，匿名回 2002），目標範圍仍是「不攜帶任何伺服器級授予、且未進入刪除終態」那一本目錄。所以普通管理員重設不了另一位管理員，也重設不了自己，更碰不到配置 Root——那幾種形態與「查無此人」同樣收斂成 1001，這條通路不回答「差哪一半」。

一次成功的重設落地三件事，缺一件都是半套：現行口令立即失效（雜湊整欄換掉，拿舊明文永遠過不了校驗）、該帳戶名下全部現有會話在同一交易裡被撤銷（`revoked_sessions` 就是這次落庫的數量）、首次改密義務被重新設為生效（他下次登入照舊被 2010 擋住，直到自己改掉為止）。交付方案沿用已批准的形態：口令由操作者親自交、伺服器不生成、不在任何回應裡回顯、不設預設口令，線下的交付管道在協定之外。界面上那串字只活在輸入框到請求之間那一小段：發出請求前就清空，之後任何一處都不再顯示，也不寫進日誌、審計、可讀偏好或自動複製的剪貼簿。

重設不改的事實同樣要如實列出：停用狀態原樣保持（那條 UPDATE 語句裡沒有 `status` 與 `disabled_at` 兩欄，重設之後他仍然登不進去，要恢復登入仍走 `/status` 那條通路），刪除終態不能被這樣復活，還欠首次改密的人不會因為被重設就免掉義務。待審批與已拒絕的申請不在這本目錄的範圍裡：拿這兩種狀態的帳戶標識來重設口令，得到的是與「查無此人」同一句 1001。所以這條通路既不會替誰放行，也碰不到一個還沒獲准的人——批准不是這三道寫入點的任何副作用。

訪客帳戶（`account_type` 為 `guest`）不在這條通路的職責裡：他的口令格在資料庫裡就被凍結成空值，替他寫一個進去等於把身分從訪客升級成普通帳戶，而那該由另一條明確的訪客升級通路決定（`PUT /admin/accounts/{account_id}/upgrade`），不是一欄口令的 PUT 該決定的事。他因此拿到本功能唯一的新機器碼 2018（403）。那句話與 1004「改改口令寫法」、1001「換個目標」、2011「換個身分」都不是同一種處置——權限夠、寫法也沒錯，該走的是那條升級通路；而目錄按定義把訪客列得進去，這裡也不講「他在這本名冊外」。

併發與重複：這條端點刻意沒有依據值——操作者拿不出「現行雜湊」這類誠實的錨點，任何湊出來的依據值驗證的不是它宣稱的東西。SQLite 的單寫者把每次重設串行化，每一次成功都是完整的「換雜湊＋撤會話＋審計」；重複提交是如實地再做一次重設（再撤一輪可能新簽發的會話、再留一筆審計），不是 2014 那種「陳舊依據被拒」。介面據此不在結果不明時自動補發，把那顆按鈕再按一次不是重試。一次成功的重設在 Root 域追加一條 `account.password_reset`，操作者是真實發起的那位管理員（帳戶級身分，不是 Root 也不是 system），帶首次改密旗標的前後值與這次撤銷的會話數量；被拒的重設不留審計，本功能同樣不新增任何審計查詢入口。

回應回顯重設後的服務端現值與 `revoked_sessions`，絕不回顯口令的任何影子（連前綴與長度都不給）。跨來源部署要儲存這條憑證得把 `PUT` 列進 `cors.allowed_methods`；出廠預設（`GET`、`HEAD`、`OPTIONS`）未做任何放寬。郵件找回、Root 的網路恢復入口與獨立的一次性恢復碼體系都不在這裡，也不因這一步而存在。

## 待審批的自助註冊與本人的狀態查詢

`self_register_mode` 設為 `approval` 時，`POST /auth/register` 不再建立一個馬上能登入的帳戶，而是收下一份申請。白名單仍是那三個欄位，口令仍由本人自選，建的仍是不帶任何伺服器級授予的普通帳戶——唯一的差別落在狀態上：`pending` 而不是 `active`。穩定的帳戶標識從提交那一刻就存在，因為在統一帳戶模型下，申請人不該在被人批准的那天變成另一個人。登入名從那一刻起被佔用，`must_change_password` 保持關閉：申請人等的是批准，不是一份口令。

「等待」不是半個可用狀態，而且這不靠措辭維持。登入判定問的是帳戶是否 `active`，而 `pending`（以及 `rejected`）在這一問上與「口令打錯」完全同形——同樣回 2001，不透露哪個名字存在。會話儲存拒絕為非可用帳戶簽發或解析主體，因此沒有 Cookie、沒有 bearer 祕密，也沒有一枚「受限會話」能讓待審批的人去碰普通業務。管理員的普通帳戶目錄把這兩種狀態都排在範圍之外，而按標識直打那四條通路（詳情、改顯示名、停用／恢復、重設口令）都得到 1001——「這本名冊沒這個人」。批准與拒絕走的是另一組入口（見下一節「註冊申請的審批」），那道閘門認的是伺服器級管理權；這四條目錄通路從來不能替任何人做出批准，也沒有一條能把已做過的決定改回來。

申請人若想知道自己的申請怎麼樣了，可以走 `POST /auth/registration-status`，而答案只有重新證明憑據才拿得到：本體只有 `login_name` 與 `password`，用與登入同一個 Argon2id 憑據校驗。成功的回應只給結局（`pending`、`approved` 或 `rejected`）、提交時刻，以及在已有決定時的決定時刻——沒有別的。沒有審核人是誰、沒有拒絕理由、沒有排隊位次、沒有別人的申請，也沒有任何會話材料：這條通路不寫 `Set-Cookie`、不產生會話行，因此也就不需要一枚要有壽命與撤銷邊界的「臨時狀態證明」。它只有 POST，理由相同：祕密不進 URL、不進查詢字串、不被預取、不會被貼進位址欄。查無此名、訪客帳戶與口令不符一律收成同一句 2001，這條通路對「誰的名字存在」不新增信號；限流用的是登入守衛那一份帳——多開一扇門不多發一份猜口令的預算。2020（403）是唯一一種必須在「已經證明你是誰」之後才會出現的回答：這個帳戶存在、你就是它的主人，但它根本沒走審批通路，所以處置是「改用登入入口」，而不是「等一等」或「換個名字」。

切換模式只管新的提交，歷史申請原地保留。Root 把模式改回 `closed` 或轉成 `open`，都不替任何一份已經交上來的申請說話：已落的行仍是 `pending`，仍能被本人查到，既不被放行也不被刪除。這也意味著用同一個登入名重複提交會撞上與所有人同一個唯一索引（2019）——待審批與已拒絕的行都繼續佔用那個名字，被拒絕的人不能拿同一個名字再來一次，別人也拿不走。

遷移 `0009` 給帳戶狀態集合加上 `pending` 與 `rejected`，並新增一欄 `reviewed_at`：狀態查詢通路就是靠它把「曾被批准、後來被停用」與「從沒申請過」分開——決定時刻不可能掛在還在等待或已被拒絕的行上，新建的行也不可能被塞進一個決定時刻。提交仍在 Root 域追加一條 `account.self_register` 稽核，操作者是系統主體（匿名請求本來就沒有可信主體可記），而記錄裡的 `status` 就是實際落成的那個狀態，所以「我們收了一份申請」與「我們建了一個能登入的人」在稽核上可分，而不需要新造一個稽核查詢入口。跨來源部署要把 `POST` 列進 `cors.allowed_methods` 才存得了這兩條路徑；出廠預設（`GET`、`HEAD`、`OPTIONS`）一字未動。登入前的入口能力現在帶三個布林——`sign_up_open`、`guest_open` 與 `invite_code_required`——但模式名字本身仍不從匿名入口出去：「立即能用還是要等」這個問題由寫入自己的 status 回答，而 `invite_code_required` 只說「這一趟要不要帶碼」（只在 invite 模式點亮），不說當前是哪一種模式。

## 註冊申請的審批

`GET /admin/registrations` 列的是走審批通路進來的申請：查詢參數只有 `page`、`page_size`、`all`／`pending`／`rejected` 的狀態篩選與一段可選的名稱關鍵字；每一行帶帳戶標識、兩個名字、狀態、提交時刻，以及在已有決定時的決定時刻。投影裡沒有別的：沒有口令、沒有憑據雜湊、沒有登入名的正規化鍵、也沒有角色欄，更沒有審核人欄與理由欄——帳戶表本來就沒有那兩格。被批准的人離開這本書：那一行此後屬於普通帳戶目錄，停用、重設憑據與改名都在那一側處理。持有授予者、訪戶與已進入刪除終態的行都在範圍之外，得到的答案與查無此標識完全同形（1001），因此這條通路永遠不會變成「誰存在但他不是申請人」的探測器。

`PUT /admin/registrations/{account_id}/decision` 做那個決定，而本體只有一欄：`decision`，取值 `approve` 或 `reject`。刻意不帶依據值，因為審核者手上沒有誠實的依據值——一筆還沒被決定的申請，其現值就是 `pending` 這個詞本身，放一格 `expected_status` 只會多出一個「填錯就注定落敗」的表單欄位；真正的併發控制是資料庫那道 `WHERE status = 'pending'`（與刪除、重設憑據那兩條同一取向）。本體裡沒有角色欄、沒有狀態欄、沒有口令欄，也沒有理由欄：那條 UPDATE 連 `account_server_roles` 都不在語句裡，「批准順手多造一位管理員」沒有可以發生的形狀；批准也不簽發任何會話——申請人仍要自己帶著当初選的口令走 `/auth/login`，他拿到的是不帶任何伺服器級授予的普通帳戶。批准同樣不解除任何獨立限制：`must_change_password`、`disabled_at` 與 `deleted_at` 都不在那條語句裡，所以一個曾被批准、此後被停用的人早已不是 `pending` 行，審批通路對他無事可做。

決定是單向的，而併發的兩位審核者只形成一個有效結果。只有 `pending` 的行可以被決定；一旦有人批准或拒絕過，沒有任何通路能改判、能覆蓋，也不能讓同一個人把那份申請重開。併發裡後到的那一位，或對著已決定過的申請再按一次的那一位，拿到的是機器碼 2021（409）「這份申請已經有過決定」——它刻意不是 2014 那句「你依據的現值已過期，重讀之後同一顆按鈕還可以再按」。2021 的處置是重讀名冊：對那一行而言，那顆按鈕已經不存在。被拒絕的行保留、登入名繼續被佔用，而「要不要讓他重新申請」不是這一步做出的產品決定。審批也從不查帳戶建立策略：Root 把模式改成 `closed` 或 `open`，既不會讓誰的待審批申請消失，也不會擋住審核者處理眼前這一筆——策略只管新的提交。

兩個入口都由 `NeedServerAdmin` 把關，與建立、列舉、停用及重設普通帳戶同一道閘：具備普通帳戶管理權的管理者審批普通帳戶的申請，Root 也走得通。普通帳戶、訪戶與系統主體在任何一次讀取之前就拿到 2011，匿名請求碰不到資料庫就拿到 2002。一次成功的決定恰好追加一筆 Root 域審計（`account.approve` 或 `account.reject`），actor 是经受信主體換得的真實審核者——不是 system，也不是冒充 Root——帶 `status` 與 `reviewed_at` 的前後值，以及服務端固定措辭的原因句；被拒的決定不寫審計，本步也不新增任何審計查閱入口或網頁控制台。審核者是誰與任何理由文本永遠不會回傳給申請人：他能知道的只有自己那筆申請的結局與決定時刻，也就是上一節那條 `POST /auth/registration-status`。

## 伺服器註冊邀請碼管理

邀請碼是允許新普通帳戶進入本伺服器的准入憑證：它不攜帶 Root／管理員權限，也不代表加入任何活動。只有 Root 管理它——`POST`／`GET`／`HEAD /root/invite-codes`（簽發與分頁名冊）與 `DELETE /root/invite-codes/{code_id}`（撤銷），全部由 `NeedRoot` 判定，與帳戶建立策略同側，因為「誰能發這張路條」本身就是伺服器級的准入決定；能打理普通帳戶的管理員仍然不能簽發或撤銷。

每枚碼有自己的額度與期限。`max_uses` 是可被核銷幾次（至少 1；1 即單次碼——不另開一個「是否單次」旗標，那只是 `max_uses = 1` 的第二份副本）；`used_count` 每次核銷只加一，名冊顯示 `remaining = max_uses - used_count`。`expires_at` 可選：`0` 表示永不過期，否則是一個必須晚於簽發時刻的絕對到期。狀態從來不是儲存欄——`active`／`expired`／`exhausted`／`revoked` 由這些事實加注入時鐘在讀用時算出，所以沒有排程去清理或翻動行，也不會有兩次時鐘讀數互相矛盾。撤銷是單向終態：落下時刻即立刻擋住之後的核銷並凍結該行（已用次數作為歷史留住），重複撤銷回 `2022`（409）「這枚邀請碼已經被撤銷」，處置是重讀名冊，而不是再按一次那顆按鈕。

完整邀請碼只在簽發成功的 `201` 回應裡出現一次，伺服器只存它的 SHA-256——邀請碼是高熵隨機值，所以（與會話秘密同理，而异於用人想出來的口令、後者留在 `internal/credential` 走 Argon2id）用快雜湊作為驗證材料就夠，整庫匯出也造不出可用的碼。名冊與撤銷回顯只帶標籤、狀態、額度與時刻——絕不帶明文碼，也不帶雜湊。碼丟了就重新簽發一枚，而不是從庫裡翻回秘密。簽發與撤銷各追加一筆 Root 域審計（`invite.issue`／`invite.revoke`），actor 是取自受信主體的 Root，明文碼與雜湊都不進審計、日誌或錯誤。

把一枚有效碼換成帳戶的核銷通路，現在已接進開放模式所走的同一條匿名 `POST /auth/register`，作為它的 `invite` 分支：請求本體能帶一個可選的 `invite_code` 欄位，只有當寫入那一刻生效的模式確為 `invite` 時才讀取並核銷它（開放／核准模式根本不看這格，於是一支碼絕不會在不需它的另一側被順手吃掉）。核銷與建號共用同一筆 `BEGIN IMMEDIATE` 交易，經 `internal/invitecode` 的 `Store.Redeem`（`used_count` 上釘著「未撤銷、未過期、額度未滿」四重 WHERE 的單向 UPDATE）：同名衝突、非法口令或任何寫入失敗都整筆回滾、不誤耗名額；一次性碼在併發提交下恰好一次成功，其餘拿到同一句不洩露細節的拒絕；重複請求或回應丟失都不多建帳戶、不多扣額度。建出的按定義是普通帳戶——邀請碼不攜帶任何權限——並且可立即登入，走與開放模式相同的通路（註冊這一步仍不簽發會話）。登入前的 `GET /auth/capabilities` 多出第三個布林 `invite_code_required`，只在 `invite` 模式點亮，讓共享表單知道要顯示邀請碼欄位；它從不洩露模式名字本身。任何換不出帳戶的碼——缺、形狀不合、本機從未簽過、已撤銷、已過期、額度用盡、或併發下被另一次註冊搶先——一律收斂成同一個不區分的機器碼 2023（403），刻意不分辨原因，好讓這條通路不成為逐枚探測碼有效性的探測器；吞吐與開放模式同受來源級限流約束。把 `self_register_mode` 切成 `invite` 仍是 Root 在 `/root/account-policy` 上單獨做的決定，該端點現在四個名字都收。

## 受限的訪客進入

`POST /auth/guest` 是門外的人把自己換成一個**臨時、受限主體**的那條匿名通路。它只在帳戶建立策略允許時存在，而它的放行答案和其他入口算法相同：`guest_enabled` **而且**「這個執行檔真的把這條路做出來了」（`internal/acctpolicy` 的 `AllowsGuest`，而且是在寫入那筆交易裡現讀）。開關關著時回的是既有的 2017（403）——「這條帳戶建立通路此刻被伺服器策略關閉」——那句話本來就是為帳戶建立通路寫的，為訪客另開一枚碼只會讓同一個決定有兩種說法。

主體由伺服器命名，這正是重點。`login_name` 產生為 `guest_<uuid>`，請求裡沒有一格能交它，所以訪客既不能替自己佔住某個真人將來想用的名字，這個匿名入口也就不會變成登入名的存在性探測器（那恰恰是 `POST /auth/register` 結構上免不了的性質，所以那側寧可回可判別的 2019）。穩定的身分是伺服器鑄造的 Account ID；暱稱只是展示資訊——可選、按顯示名的同一套領域規則校驗、允許和別人同名，而且從來不是憑據。留空時由伺服器給出一個語言中立的臨時編號（`guest-<6 位十六進位>`），因為伺服器產生的字串不該把任何一種語言的用詞寫進資料裡。

這個帳戶按構造就沒有憑據：`password_hash` 為 NULL、`must_change_password` 為 0，由資料庫 CHECK 凍結、領域層再核一遍，所以這裡沒有一枚可以被猜、被重設或被交出的口令。這也正是這條通路與其他註冊路徑相反、**要**簽發工作階段的原因：訪客沒有之後用口令登入的路可走，不給工作階段這扇門只是一堵牆。工作階段來自 `internal/session` 那唯一的簽發點，經傳輸層唯一的那條 Cookie 分發通路送出：絕對的到期時刻、閒置線、登出與改密時的撤銷、裝置名額、輪換，全都和其他帳戶一樣。沒有一枚「不受這些約束的訪客 Cookie」，而秘密只會經 `Set-Cookie` 到達客戶端（Web 由瀏覽器代管，原生寫入平台的安全儲存），絕不出現在回應本體裡。

進來了不等於有管理權。訪客主體構造時交的是空的授予集合，而 `identity.NewAccountPrincipal` 會當場拒絕「訪客卻持有角色」，所以這是型別層的牆，不靠約定。於是每一條 `NeedServerAdmin` 與 `NeedRoot` 的路徑對他回 2011（403）（匿名者則是 2002），他既讀不到也無法透過這些端點寫帳戶目錄；而 `/auth/session`、`/auth/logout`、`/auth/session/rotate`、`/auth/devices` 這些只處理自己工作階段的路對他照常可用——撤銷自己的工作階段從來的一項特權。同樣刻意的還有「不告訴他什麼」：活動、資產、聊天與 NPC 這些還沒做的模組不會裝成可用，介面的玩家面會如實寫著這個身分还不屬於任何活動。

兩件事是被明確決定下來的，而不是悄悄發生。第一，**沒有自助找回**：工作階段到期、主動登出、換裝置或清掉本機憑據之後，這一趟就結束了。一條「憑暱稱把我找回來」的通路等於一把可以被任何人替別人出示的可猜測憑據，本步刻意不發明它——要處置這個人，由管理員在一般帳戶目錄（這本目錄按定義就把訪客列進去）核實之後另行決定。第二，**訪客建立按「嘗試」計量而不是按「失敗」**：`security.register_guard` 的那組閾值被第三份獨立的記憶體守衛複用，計量主軸是「來源位址 × 這條通路」，而成功的那一趟和被拒的一樣要銷預算。自註冊靠登入名唯一性天然自限，但每一趟成功的訪客進入都實實在在多出一筆帳戶、一枚工作階段、一條稽核，只記失敗等於留下「開關亮著就能無限建號」這條路——既然也不提供排程批次刪除訪客，天花板就必須設在門口。

落庫的痕跡是一條 Root 域稽核 `account.guest_enter`，操作者是系統主體（匿名請求本來就沒有可信主體可記），帶產生的登入名、顯示名、`account_type` 為 `guest` 與 `must_change_password` 為 false——不帶來源位址、不帶任何工作階段材料，暱稱除了顯示名本身也沒有第二處落點。回應回顯帳戶標識、顯示名、裝置標識與到期時刻；同時在 `/auth/login` 與 `/auth/session` 的回應裡新增的 `account_type` 欄位，是讓重新整理或重開之後的介面還能說「訪客（臨時身分）」而不會把所有人都唸成「帳戶」的依據。

## 訪客帳戶就地升級

`PUT /admin/accounts/{account_id}/upgrade` 是只有伺服器級管理員走得通的「就地轉正」通路：一般帳戶目錄裡那些訪客行不必被重建，也不必併到別人身上。請求本體的白名單只有 `login_name` 與 `password` 兩欄：升級給他一個正式登入名和操作者親自交付的一次性憑證，升級出來的形態恆為 `standard`＋`active`＋首次登入必須改密——本體沒有 `account_type`、`roles`、`status` 或旗標的格子可填，所以「把訪客升成管理員」在協定層根本沒有地方可寫，而既有的身分判定本來也會拒絕為不存在的授予放行。

被保留的才是這一節的重點。那條更新只改同一行帳戶的五個欄位（登入名、它的正規化鍵、帳戶類型、口令雜湊與首改旗標），而帳戶標識、建立時刻、顯示名、所有已經指向這個穩定標識的實際存在參照——連同記下他怎麼出生的 `account.guest_enter` 審計——全部逐字不動。審計只追加：升級另記一筆 Root 域的 `account.guest_upgrade`（操作者是那位真實管理員，內容是新登入名與帳戶類型的前後值、首改義務與這次撤銷的會話數量），沒有任何歷史被改寫，因為歷史事件描述的就是發生時那個訪客的身分。這正是「就地升級」與「把他綁定到另一個既有正式帳戶」的分別：第二個動詞既有唯讀的預檢，也已經有了執行通路（下一節）；介面在同一張卡上把兩句話分開講。

舊會話活不過升級。會話解析每請求現讀帳戶列，留著訪客 Cookie 不等他做任何事，就等於讓撿到舊臨時憑證的人安安靜靜拿到正式帳戶；所以撤銷他名下全部會話與升級落在同一筆交易——用的就是停用與重設已經在用的那個原語——回應如實帶回 `revoked_sessions`，回到門內的唯一方式是用新憑證真實登入一次，而首次登入立刻受首改門閂（2010）約束。任何一步失敗就一個都不落地：不會留下沒有口令的半升級身分，也不會留下查不到誰的撤銷。

三個建立開關不約束這條通路：它們管的是「準不準再多出一筆帳戶」，而升級動的是一筆已存在帳戶的形態——關掉訪客入口不該剝奪管理員處置既有訪客的手段。結論各說各話：1004 點名寫壞的 `login_name` 或 `password` 欄位；2012 說那個名字是別人的，而訪客那一行一個字都沒被改；2011 是敲這條端點的人不是管理員——訪客本人也在內，這條路存在的意義之一就是答不了他；1001 是這本目錄按定義不列的目標（管理員、已刪除、申請人）；升級帶來的新碼 2024（409）回答「他此刻不是可升級的訪客」——要嘛已經升過（重複提交），要嘛此刻被停用，前者的處置是「無事可做」、後者是「先恢復他的登入」，兩句都指向重讀伺服器端現值，而都不是 1001 那句「換個目標」：這本目錄列得到他。口令交付沿用建號與重設同一套規則：伺服器不生成、不回顯，線下交付在協定之外。

## 訪客綁定預檢（唯讀預覽）

「把訪戶併入另一個既有正式帳戶」這個動詞從唯讀的預檢與衝突預覽開始：`POST /admin/accounts/{account_id}/bind-preflight` 由伺服器級管理員發起（NeedServerAdmin），請求本體的白名單恰好一格 `target_account_id`——一次只評估「這個訪戶 × 這個目標」的一對，不存在替訪戶羅列可綁定目標的讀法；請求形態本身就是反枚舉的邊界。目標標識放在本體而不是查詢串：它是一段待驗證的輸入，不該成為可書籤、可快取的尋人請求。

這一條通路零寫入：不改帳戶、不撤會話、不動授予，連一筆安全審計都不記（用戶批准的 R2-018 決定：純唯讀，介面顯著標示「尚未綁定」由結果面板首句承擔）。「此刻不可綁定」是 200 預覽本體裡的穩定原因記號而不是錯誤：`executable` 為假時 `blockers` 逐條點名——同源自同一對（`same_source_target`）、來源已轉正或已退休（`source_not_guest`）、來源停用中（`source_not_active`）、來源帶著授予（`source_has_grants`，形態缺陷方向）、目標也是訪戶（`target_not_standard`）、目標停用中連以自己的會話確認綁定都做不到（`target_not_active`）、以及 `unknown_references`。回應同時如實帶出這份快照運行的 `schema_version`、該訪戶名下尚未撤銷的會話數 `source_open_sessions`，以及恆為 `target_self_initiated` 的 `consent_mode`：綁定只能由目標帳戶持有人以自己的已認證會話發起，管理員永遠拿不到代他完成綁定的按鈕——登入名相同或管理員輸入目標標識都不構成目標的同意。

未知引用整體阻止是這一節最要緊的規矩。預檢每次執行都現掃實庫的外鍵邊：只要出現一張引用帳戶而處置登記表尚未接入的表（未來活動、帳本、NPC 模組新加的表），一切綁定都被阻止，絕不靜默合併評估不了的權限或資產；那個模組把自己的引用接入預檢之後才重新放行。未接入的表名只進伺服器日誌，不進回應。這一步沒有發布任何新機器碼：請求級拒絕全用既有碼——來源或目標不在普通帳戶目錄（不存在、管理員、已刪除、待審批）與詳情端點逐字同句收斂 1001，預檢不是比詳情更亮的探照燈；2011 是主體不夠（訪戶本人敲它也一樣）；1004 點名 `target_account_id`；GET 方法 1002。

預覽裡的影響就是執行時必須遵守的那一份清單：該訪戶名下尚未撤銷的會話同交易登出、訪戶帳戶進入不可登入、不可複用的退休終態、指向他的歷史參照逐字保留、未來的身份歸屬落在目標標識上，而目標的憑據、狀態、顯示名與權限一概不動。

## 訪戶綁定由目標帳戶本人執行

預檢不是綁定，簽發憑證也不是綁定。`POST /admin/accounts/{account_id}/bind-ticket`（仍由 NeedServerAdmin 判定，本體白名單仍恰好一格 `target_account_id`）在**寫交易之內**把整份預檢重做一遍，可行才簽發一枚操作憑證——這就是用戶批准的 R2-019 那座橋：把「管理員准了這一對」交給「目標本人的會話按下執行」。它只落兩行：`guest_bind_tickets` 裡的一枚憑證，和 Root 域一筆 `account.guest_bind_ticket_issue` 審計（操作者是那位真實管理員，內容含憑證標識與被准的目標，絕不含明文）。訪戶沒被退休、會話沒被撤銷、留痕沒被追加。那一刻這一對不可行，就根本沒有憑證存在，答案是 2026 並帶著原因記號。

憑證是刻意做小的：15 分鐘，寫在碼內而不是配置欄位（一枚能調到一週的綁定憑證就不叫短期憑據了）、只准核銷一次、限定這一對來源與目標、限定這一個用途。明文只在簽發回應裡出現那一次；庫裡存的是它的 SHA-256，此後任何讀法——包括管理員那本目錄——都拿不回來。把它交出去是線下動作，與建號、重置的口令交付同口徑；它不是目標的口令，伺服器也從不要求管理員去收集任何人的口令。

執行屬於 `target_account_id` 那一個人，不屬於任何人。三條通路都在 `/auth` 之下：`POST /auth/guest-bindings/preview` 以唯讀方式、不核銷任何東西地展示這枚憑證按**今天的事實**會做什麼；`POST /auth/guest-bindings` 核銷憑證並完成綁定；`GET`/`HEAD /auth/guest-bindings` 列出「目標是我」的已完成綁定。主體判定先於任何查詢，所以訪戶、Root、管理員與匿名分別拿到 2011 與 2002——沒有半開的門。本體恰好一格 `ticket`：沒有任何「我要以誰的身分」可填，目標範圍只來自這次會話換出的主體。憑證放本體而不是路徑或查詢串，它才不會進訪問日誌、書籤與快取。

一次成功的確認在同一筆交易裡落地四件事：憑證被一條 `WHERE` 釘住「尚未核銷且尚未到期」的條件式 `UPDATE` 標記核銷；訪戶那一行連同 `retired_at` 一起進入新終態 `retired`（遷移 0011；行與登入名鍵保留，因此名字不可被複用、歷史也仍指得回來，但與刪除通路不同，顯示名**不做**匿名化——那個名字是記錄的一部分）；他名下仍有效的每一枚會話都用停用與重置那同一個原語撤銷；`guest_account_bindings` 追加一行只追加的留痕。目標那一行沒有任何一處被重寫：那條 UPDATE 連目標都沒點名，他的口令雜湊不被複製到任何地方，不繼承任何授予，狀態、顯示名與首改旗標逐字不動——「訪戶經綁定獲得權限」在形狀上就沒有落點。源令牌不會被換成能開目標家門的令牌，它只是從此解析不出主體，而目標繼續以他自己的正常認證進門。任何一步失敗都整體回滾，連那個核銷標記也不留下，原先可用關係完整保留。把一枚已用掉或不屬於你的憑證再打一次，得到的是 2025——五種內部原因刻意收成同一句話，因為分辨「過期」「已用掉」「不是你的」會讓這條通路變成憑證探測器。

執行時重做檢查，才讓一份舊預覽沒辦法被執行：任一側形態變了、資料庫版本推進了、或庫裡此刻多了一張尚未接入綁定預檢的帳戶引用表，請求就以 2026（「重新預檢」）被拒，並且憑證不會被核銷。因此「預檢通過」從來不是永久有權執行，而憑證那一行同時釘著計劃摘要與它被釘住時的那個版本。已被綁走的訪戶不可能再領到第二枚憑證——退休讓他在源頭就離開可綁形態，而留痕表的 `source_account_id` 帶 `UNIQUE`，是「一個訪戶至多被併入一次」的最後一道結構保證。

審計邊界沿用既有規則：普通帳戶本人的動作今日不寫 Root 域審計表，因為「帳戶本人作為審計主體」這一分類尚未批准（與登入、登出、輪換、本人改密同一口徑）。可追溯性並沒有變薄——誰准了這一對、誰同意了、什麼時候、撤了幾枚會話，全在 `guest_bind_tickets` 與 `guest_account_bindings` 兩行不可變的資料裡。

本步覆蓋範圍說清楚：只有帳戶層——帳戶、會話、憑證、綁定留痕與 Root 域審計。活動、成員身分、資料卡與帳本尚未開發，所以「未來的身份歸屬」以合約形式表達（`transfer_future_attribution` 那條影響），不宣稱已驗證。那些模組落地時必須先把自己的帳戶引用登記進 `internal/stdacct/bindpreflight.go` 的處置表，綁定才可能被再次簽發或執行；在那之前 `unknown_references` 把整條通路拒絕掉，任何沒人評估過的東西都不會被靜默合併。


## 釋出後的使用方式（規劃）

- 一人在這臺機器（Windows 或 Linux）上託管服務端
- 其他人在同一區域網內用瀏覽器加入
- 無需第三方註冊；資料只儲存在主機上

## 從原始碼建置

Windows 執行檔的圖示是產生出來的、不納入版本控制：`cmd/evernight-server/resource_windows_*.syso` 由 `assets/icons/EvernightRealmBackendRounded.ico` 推導。全新複製的倉庫在編譯前先執行

    python tools/icons/generate_icons.py

否則產生的執行檔沒有圖示，而 `go build` 不會報錯。`python tools/icons/generate_icons.py --check` 只核對現況，不寫入任何檔案；詳見 `tools/icons/README.md`。

本專案沒有託管 CI：提交前請在本機跑品質入口 `go run ./tools/check`（後端格式、`go vet` 與測試，並連帶前端閘門）。
