# 长夜幻境（EvernightRealm）

> 在自己的机器上，为你的小圈子搭建一座私密的虚拟世界——管理活动、扮演角色、交换虚拟资产。

[English](./README.md) · [简体中文](./README.zh-CN.md) · [繁體中文（台灣）](./README.zh-TW.md) · [日本語](./README.ja-JP.md)

## 这是什么？

长夜幻境是一个自主部署、离线优先的平台，面向小规模玩家群体：一起推进沉浸式活动、扮演角色、交易虚拟资产——全部在局域网内完成，不需要公网、云账号或遥测。

## 功能规划（开发中）

- **沉浸式活动**：为你的群体编排场景、阶段与事件
- **角色与身份**：玩家、NPC 与管理员的角色，共处一个私密世界
- **虚拟资产**：物品有真实归属，交易可审计
- **私密聊天**：消息只留在你自己的服务器上
- **离线优先**：一切运行在你自己的机器上，不依赖云服务

## 当前状态

长夜幻境正在积极开发中，尚未发布稳定版本。服务端现在可以构建为**单一可执行文件**：同一个端口同时提供网页界面（目前是可切换语言、可探测服务器连通性的应用壳，业务功能仍在开发）与 API 端点，浏览器直接打开它的地址即可使用，不需要另外部署静态服务。

服务端还提供一个运维命令来产出**一致性备份包**：单档数据库快照（服务运行中即可产出，不是复制活跃的 WAL 主档），连同配置与媒体／文档／上传目录，逐档记录大小与 SHA-256 并附一份清单。与之配套的 `restore` 命令能把这份包还原成一个**全新的空资料目录**：逐档按清单重算校验和，落地前后各读一次快照的数据库事实并与清单对照，**不覆盖任何既有目录**（要覆盖请先自己备份那个目录），拒绝比当前执行档更新的数据库结构版本，并把这次恢复本身写成一条服务端审计记录。备份包还不能加密，旧包也不会自动清理。

一次性 Root 初始化**只有本机命令这一条入口**：

    evernight-server init-root --password-stdin --data-dir <资料目录>

它从标准输入读口令（前两行是口令与确认），把 Argon2id 编码写进该资料目录的 `config.yaml`，不输出任何秘密——不写明文，也不会自动生成或显示一个“出厂口令”。交出服务器最高权限的授权依据是“能在服务器主机上执行命令”，所以这一步不开任何 HTTP 端点、不占端口；CORS、客户端自报的地址、界面上隐藏按钮都不构成授权。服务持有单写入实例锁时、`ER_SECURITY_ROOT_PASSWORD_HASH` 覆盖着配置文件时、或审计表尚未建立时，本命令一律拒绝；写入成功之后也不会再开放第二次——要换口令，走服务内的已认证改密流程（Root 登录后 `POST /auth/password/change`）；只有口令真的遗失了，才用下面那条本机恢复通路。只读的 `evernight-server root-status` 能回答“现在有没有 Root”，它不建立也不改动任何文件，而且只回答这么多：不给出配置路径、哈希或任何引导秘密。成功与拒绝都会写进 Root 审计表，且不记录口令。

Root 口令遗失后的恢复同样只有本机命令这一条入口：

    evernight-server recover-root --password-stdin --confirm --data-dir <资料目录>

它也只从标准输入读新口令（前两行是口令与确认），不接受命令行上的口令值，并且要求服务已经停止：运行中的服务把凭据读在内存里，改配置文件不会让它回头更新，那样只会做出“终端说成功了、旧口令其实还登得进去”这种比拒绝更难查的状态。恢复不问也不验旧口令——能在这台主机上执行命令、能读写那份配置文件，就是这个动作全部的授权依据；因此它也不设后门口令、不产生可下载的恢复档、不开任何 HTTP 端点。成功时配置文件里那份凭据被覆写为新口令的 Argon2id 编码，Root 名下全部会话在同一笔数据库交易里被撤销（下一个请求即被拒），并留下一条 `server.root_recover` 审计记录；普通账户的会话一枚都不动。撤销与审计写不进去时，配置文件会被换回原本那份凭据、回报失败，可用状态与动手前一致（连回滚都失败的双重故障会以 Error 写进运行日志文件，并明确要求人工补记）。`--confirm` 是必须显式给出的旗标：覆盖的代价是旧口令永久失效加上 Root 全部装置登出。配置文件里还没有凭据时本命令拒绝并指向 `init-root`；已有值即使坏到解不开（那种状态下谁都登不进去）也照样能恢复——这正好是 `init-root` 会拒绝的形态，两条路各自只有一种成功形态。

首次启动的界面要如实显示“还没初始化”，服务端因此另外回答一个只读的 `GET /root/init-status`：只有配置文件是否存在、是否已有 Root 凭据、环境变量覆盖是否处于设定状态这三个布尔值，不返回路径、长度或任何凭据片段，也不写数据库、不写审计。它把“有没有”说出来，不说“怎么改”——初始化 Root 仍然只有 `init-root` 这一条在服务器本机上执行的通路（遗失口令后的覆写是上面那条 `recover-root`，两者都不提供服务端网络入口）。

## 登录与管理自己的账户

身份阶段的功能现在已实现、可以使用：登录、查看当前会话、退出、管理自己的设备、修改自己的口令，以及 Root 开设账户、管理管理员目录、停用与恢复管理员登录、重置管理员登录凭据、软删除管理员（见下一节）、Root 设置服务器的账户创建策略（再下一节），以及管理员在该策略之下创建普通账户、翻阅普通账户目录、读取与维护单笔资料、停用与恢复某个普通账户的登录、重置某个普通账户的登录口令（建号见上一节，目录、资料、停用与凭据各看后面四节）。限制同样如实写在前面两点。其一，账号只从以下几个入口产生：Root 凭据本身由服务器本机的 `init-root` 建立，服务器管理员由 `POST /root/admins` 开设，普通账户则要么由 `POST /admin/accounts` 建立——这一条只在 `admin_create_standard` 开着时成立，且只认已认证的服务器级管理员——要么由自助注册 `POST /auth/register` 产生：它匿名可读、只在 `sign_up_open` 为真时开放，交回的是一个由本人自设密码的普通账户，不签发任何会话，也永远建不出管理员。自助注册现已实现；邀请码与访客账户尚未实现——它们的开关与模式现在可以被配置，但背后的通路还不存在，界面也不提供、不假装提供这两类入口。其二，服务端自己不做 TLS 终结：默认监听是 `127.0.0.1:5206` 上的明文 HTTP，只有当请求确实经 TLS 抵达时（也就是你在它前面自行放一层终结 TLS 的反向代理），会话 Cookie 才标 `Secure`、才下发 HSTS；程序不含任何证书处理，HTTPS 是这套程序之外的部署选择。

身份相关的端点没有版本前缀——没有 `/api/v1`：

- `POST /auth/root/login`（只用 Root 口令）与 `POST /auth/login`（登录名加口令）。每次成功都签发全新会话并覆写旧的 Cookie，旧 Cookie 不会被沿用。
- `GET /auth/session`、`POST /auth/logout` 与 `POST /auth/session/rotate`——读取当前会话、撤销恰好这一枚会话（幂等），或换发本会话的秘密。
- `GET /auth/devices` 与 `POST /auth/devices/revoke`——只列举并撤销当前登录主体名下的会话；没有任何请求能指名别人的设备。
- `POST /auth/password/change`——必须在请求中当场交出当前口令；成功后该主体名下全部会话（含这台设备）一起被撤销。

浏览器路径的会话秘密放在 `HttpOnly` Cookie 里；原生客户端从回应标头读出后以 bearer 秘密携带。登录失败反复发生后按“来源地址与登录目标”限流（HTTP 429，附 `Retry-After`），Root 入口同样适用，且被挡的尝试不会指出撞上的是哪个账户。`device_policy` 设为 `single` 或 `limited` 时，会丢掉较旧的会话，或在名额用尽后拒绝新的登录。带有“首次登录必须改密”标记的账户，只放行当前会话查询、退出与改密流程，其余受保护端点一律回 2010，直到改密完成。

两条运维边界维持不变：备份与恢复仍是 `evernight-server` 子命令，没有 HTTP 入口；审计记录只由服务层写入，仍然没有审计查询端点或网页控制台。运行日志按自然日切档，默认不自动删除（`retention_days=0`）：不让日志无限增长是运维者的工作，程序本身不会随时间给日志总量设上限。

## Root 管理管理员目录

Root 的会话是第一批人力操作者进来的地方：`POST /root/admins` 带 `login_name`、`display_name` 与 `password` 开设账户；`GET /root/admins` 是分页的管理员目录（`page`、`page_size` 上限 100、`status` 可按 `all`／`active`／`disabled`／`deleted` 筛选，依授予时刻由新到旧排序，并回显 `page`、`page_size` 与 `total`）；`GET /root/admins/{account_id}` 读取单笔资料；`PUT /root/admins/{account_id}` 编辑它；`DELETE /root/admins/{account_id}` 软删除该账户，请求本体一个字段都不带——多带任何字段都打成 1004；`PUT /root/admins/{account_id}/status` 停用或恢复该账户的登录，请求本体只有 `status` 与 `expected_status` 两个字段；`PUT /root/admins/{account_id}/password` 重置该账户的登录口令，请求本体只有 `password` 一个字段。让新账户成为管理员的是端点本身，不是请求内容：本里没有 `role`、`account_type` 或 `subject_kind` 可以填，多带的字段会被打成 1004。授权的输入是「这次请求解析出的主体就是 Root」，所以普通账户和管理员自己的会话都拿到 2011（403）——管理员既不能创建或管理同级管理员，也不能把自己升格，重新登录一次同样改变不了这件事。目录只列管理员账户；配置 Root 不是其中一行，也永远不会变成一条可被普通账户接口编辑的记录。

初始口令由 Root 亲自交出、且只用一次。它经的是与其他任何凭据同一套 Argon2id 服务，账户带着 `must_change_password` 落库，服务器在任何响应里都不回显该口令，也不存在任何默认口令。于是那个人首次登录拿到的会话，只被允许访问查看当前会话、退出与改密这一组入口——其余受保护端点一律回 2010，直到改密完成——而改密成功会让该账号的所有设备退出。这些规则本就适用于任何账户，本步补上的是那面旗标的来源。

登录名的唯一性走的是与登录通路同一个正规化键（NFKC 加全量大小写折叠），并由账户表上的唯一索引兜住：已被占用的名字回 2012 且不创建任何东西，所以连点两次、或在响应丢失后整笔重试都不会多出第二个账户，而那一句拒绝也不会回显已有账户的任何资料或任何凭据。创建账户、授予 `server_admin`、把 `admin.create` 追加进 Root 审计，全部落在同一个事务里——任何一处失败都不会留下半成品管理员，也不会留下无痕的特权变更——而审计记录里只有身份字段，绝没有口令或其哈希。

编辑的白名单只有一个字段：`display_name`，连同它所依据的现值 `expected_display_name` 一起提交。状态、凭据、首次改密旗标与账户类型不在这条通路之内，UPDATE 语句也只碰这一栏——「保存普通资料顺带覆盖隐藏字段」在语句形状上就不存在。若存储的值在页面打开之后已被改动，整个编辑以 2013（409）被拒绝且什么都不写入，这与改密使用的同一套 compare-and-set 保护同源。标识格式不对、账户不在目录、账户确实不存在，都收到同一个 1001，这个端点因此不是枚举探针。响应只含可展示事实——绝不带密码哈希、会话秘密、恢复码或任何配置——Root 的每次成功编辑都会追加一条 `admin.profile_update` 审计，仅带显示名的前后值；被拒的编辑不写任何记录。

停用与恢复走另一条只有一个字段的端点。停用后新登录被拒绝（与其他登录失败同形，服务器不会说“这个人被锁了”），该账户现有会话在同一数据库事务里全部撤销，并追加一条带前后状态、`disabled_at` 前后值与 `revoked_sessions` 的 `admin.disable` Root 审计；主体此刻是否可用按每个请求现读数据库，被停用者的既有会话在任何受保护入口都换不出受信主事人。恢复（`admin.enable`）只恢复重新登录的能力：停用时撤销的会话保持已撤销、不会复活，尚未完成的首次改密义务仍然有效；Root 与管理员停用其他管理员都不构成合法目标。状态写入是对调用端所见现状的一次 compare-and-set——对着过期依据或重复操作都以 2014（409）拒绝且什么都没发生：不改状态、不撤会话、不记审计。已经明确完成的操作不倒退，只有停用生效之后发起的新操作被拒绝。UPDATE 语句只碰 `status` 与 `disabled_at` 两栏，“停用顺带清凭据或旗标”在语句形状上就没有发生点；被停用者仍留在目录里（授予行保留），这正是他可被恢复的前提。

重置登录凭据是第三条单子栏子资源端点。`PUT /root/admins/{account_id}/password` 只带 `password` 一个字段——Root 亲自交出的临时口令，交付语义与开设时同一套批准方案：服务器不生成口令、任何响应不回显，口令只在请求本体里出现一次；日志、审计与响应都不含口令材料，线下交付管道在协议之外。一次成功的重置在同一事务里落地三件事：旧口令立即失效、名下全部会话即刻撤销（`revoked_sessions` 是权威计数）、该账户下次登录必须改密（沿用与本人改密同一个 2010 门闸）。它与本人改密是两个用例而不是同一个：本人改密要交出现行口令作再认证并清掉义务，Root 重置他人恰恰发生在拿不出——也不该拿出——现行口令的场合，成功后义务被重新设为生效。重置因此不带 compare-and-set 依据值：任何凑出来的锚点验证的都不是它宣称的东西；重复提交不是 2013/2014 那种「陈旧依据被拒」，每一次都是完整生效的重置，各留一笔 `admin.password_reset` 审计（记改密义务旗标前后值与撤销数量，绝无凭据），所以界面在结果不明时不得自动补发。重置不改的事实同样真实：UPDATE 语句不碰 `status` 与 `disabled_at`——对停用中的目标重置成功，目标仍停用、新登录仍被拒（与其他登录失败同形），要恢复登录仍走 status 那条通路；重置也不是撤权、改名或删除，授予行原样保留。格式不对的标识、幽灵标识、未持有授予的账户与已物理删除的目标一律回 1001——已软删除的目标回 2015，因为那里的记录确实还在，拒绝的是它的状态；非 Root 回 2011，形状不合格的口令回 1004 并点名 `password` 字段。

删除管理员是一种状态，不是清库。`DELETE /root/admins/{account_id}` 不带请求本体，一次成功在同一事务里落地三件事：登录停止、名下全部会话即刻撤销（回应给出权威计数 `revoked_sessions`）、追加一条 `admin.delete` 的 Root 审计，内容正是后来者解释这次删除所需的身份快照——登录名、改写前与改写后的显示名、状态前后值、`deleted_at` 前后值、撤销数量——且绝不含任何凭据材料。账户那一行本身留下：它的标识、它的登录名键、它的授予行、它的会话行、它的审计行，全都仍然指向同一个稳定账户，因此历史操作不会变成指向虚无，也不会被悄悄改记到 Root 名下。物理清库因此不在本步实现，也不是随手能做的事：被引用的行根本删不掉。删除是终态。没有恢复入口——`PUT /status` 会拒绝，因为停用与删除是两种状态，既有的恢复登录通路不得让已删除账户复生——而对已删除的目标发起编辑、重置凭据或再次删除，都以 2015（409）答复，这个机器码的意思就是「这个人存在，但已删除」。数据库层面另有一道触发器让已删除的行不可再被改写，未来任何写通路都没法悄悄把它捞回来。有一处可展示资料在删除时被匿名化：`display_name` 改写为 `DEL_<UTC 日期>_<原名>` 形状的占位串，长度沿用同一份预算，于是当前记录不再把旧名字呈现为现行名字。而只追加的历史刻意不动——删除之前写下的审计仍保留它当时记录的名字，那正是旧操作至今可解释的理由。登录名的正规化键继续占用，因此不可复用：已删除账户的名字没法再注册一次。已删除的管理员仍列在目录里（`status=deleted`，目录与单笔回应带 `deleted_at`），其详情只读。不提供批量删除，请求也不带原因文本；配置的 Root 凭据不是目录里的一行，因此永远不构成删除目标。

另有两个响应字段按「只增不删」的演进规则补上：登录与查看当前会话的回应现在带 `roles`，内容是服务端为该主体现读到的授予（没有授予时字段缺席），客户端据此决定载入哪些入口。它本身不授予任何东西——每个端点仍在每次请求上重读可信主体。


若部署要让组态白名单里的跨源浏览器调用这些端点，`cors.allowed_methods` 必须把 `PUT` 与 `POST` 一起列入，删除端点还要列入 `DELETE`——出厂默认仍是 `GET`／`HEAD`／`OPTIONS`，来源白名单始终是组态决定，本节不为此放宽任何边界。

## 服务器账户创建策略

三个值说明这个部署对“新增可登录的普通账户”的打算：`admin_create_standard`（管理员能否创建普通账户）、`self_register_mode`（`closed`、`open` 或 `approval`；`invite` 是已批准的名字，但它对应的流程还没上线）与 `guest_enabled`（能否创建临时的访客账户）。`GET /root/account-policy` 读取这三个值，`PUT /root/account-policy` 把它们当成一份文档一次写入。读写都只有 Root 可以：管理员自己的会话拿到 2011，没带凭据拿到 2002，跨站来源在碰到数据库之前就被 2005 挡下——“管理员能不能创建普通账户”是这个端点会设置的值，而“管理员能不能改服务器策略”根本不是一个值。三个字段彼此独立，而且一个都不能少：漏掉一个开关会被打成 1004 并点名那个字段，因为沉默是界面漏了字段，不是“把那个入口关掉”的决定。

这里刻意没有 compare-and-set 依据值，因为这是一份只有 Root 会写的文档：重复保存是同一次状态的再一次确认，每次都追加一条 `server.account_policy_update` 的 Root 审计，内容是每个真的变动过的字段的前后值（此外没有任何东西——不含账户标识，也不含任何凭据材料）。值持久在迁移 `0008` 建立的那张单行记录表里，所以保存好的变更对下一条请求立即生效，重开程序后不需要任何重启动作也会读回同一份值，而且一律不写回 `config.yaml`；那一行删不掉，也不可能多出第二行。

策略值不等于能力。三条通路里已经存在的是「管理员创建普通账户」与「自助注册」这两条；访客那条还没有实现，所以还没登录的浏览器能问到的入口答案，只在那条通路真的存在时才可能是开：`GET /auth/capabilities` 匿名可读、`no-store`，响应恰好两个布尔——`sign_up_open` 与 `guest_open`——各自的算法都是“策略说要开”**而且**“这条通路真的存在”。它不回显模式名字、不回显 `updated_at`、不含管理员建号开关、不含任何账户列表或阈值。写入 `invite` 会被打成 2016（400），这句话的意思是“名字认得，流程还没上线”，与 1004 那句“这个值不存在”是刻意分开的两句话；`approval` 在收申请那条通路落地之后已经写得进去了（见「待审批的自助注册」一节），而模式名字仍然不会从匿名入口出去；任何不认识的值永远不会被往下收成 `closed`，也不会被往上放成最宽松的模式。日后某条流程真的上线时，它会登记自己的那一项能力，并在自己那笔事务里现读当下生效的策略，而不是缓存一份先前读到的值。

这三个开关也不会伸到 Root 自己身上：创建管理员（`POST /root/admins`）与服务器本机的凭据命令（`init-root`、`recover-root`）都不读这张表，所以把 `admin_create_standard` 关掉，不会让一台服务器落到“既没有管理员、也没有找回来的路”的状态。与其余写入端点相同，开放跨来源调用的部署要把 `PUT` 列进 `cors.allowed_methods`，出厂默认仍然只放行 `GET`、`HEAD` 与 `OPTIONS`。

## 管理员创建普通账户

已认证的服务器级管理员通过 `POST /admin/accounts` 一次建立一个普通账户。请求本体恰好带 `login_name`、`display_name` 与一次性 `password` 三个字段：没有角色、账户类型、审批状态或活动的格子，因为「新建的是哪一类主体」由端点决定而不是由请求决定——`standard`、启用中、不带任何服务器级授予、`must_change_password` 为真，与 Root 开设管理员使用同一套一次性凭据策略。

通路开不开在写入那一刻判定：建立交易现读策略行，`admin_create_standard` 关闭时回 2017（403）——Root 走这条端点也一样被拒，这个开关不豁免任何主体；没有服务器级权限的主体回 2011，登录名（正规化后）已被占用回 2012。这里刻意没有给管理员的「开关预读」端点：策略现值仍然只有 Root 读得到，权威答案永远出自建立交易内部的那次现读。新账户之后和其他账户走同样的路使用系统：首次登录必须改密（改完之前其余受保护入口一律 2010）。建出来的账户只是一个账户——没有活动档案、没有资产、不在任何名册上——界面如实说明，不冒充已经配置好的活动大厅。

一次成功建立会在 Root 域审计追加一条 `account.create_standard`，操作者是真实发起的那位管理员（账户级身份，不是 Root，也不是 system）：服务器级动作不会去借一个它并不拥有的 `activity_id`，那张表的结构上也没有这一栏。本功能不新增任何审计查询入口：能建号的管理员依旧读不到 Root 域审计，那仍然归 Root 自己。与其余写入端点相同，开放跨来源呼叫的部署要把 `POST` 列进 `cors.allowed_methods`；出厂默认仍只放行 `GET`、`HEAD` 与 `OPTIONS`。

## 管理员打理普通账户目录

已认证的服务器级管理员除了建号，还能翻阅与修剪这本名册：`GET /admin/accounts` 是分页目录（`page`、`page_size` 上限 100、`status` 按 `all`／`active`／`disabled` 筛选、`type` 按 `all`／`standard`／`guest` 筛选、`q` 按登录名或显示名做子串匹配），依建立时刻由新到旧排序，并回显 `page`、`page_size` 与 `total`；`GET /admin/accounts/{account_id}` 读取单笔详情；`PUT /admin/accounts/{account_id}` 编辑它，请求本体只有 `display_name` 与它所依据的 `expected_display_name` 两个字段。

这本目录的范围是一条边界而不是一句偏好：它列的是**不携带任何服务器级授予**、且未进入删除终态的账户（普通与访客都在内，`account_type` 那一栏就是把来源如实讲出来）。持有 `server_admin` 的人——包括敲这条端点的操作者自己——归 Root 的管理员目录；配置 Root 根本不在 `accounts` 表里，结构上不可能成为一行。两本目录因此互斥，谁也不会「顺手」把对方的人列进来。没有服务器级管理权的主体读目录、读详情与编辑都拿 2011（403），匿名拿 2002：普通账户与访客因此没有办法枚举全站账户，这件事成立在服务层的判定上，不靠界面藏起入口。标识格式不合法、账户不存在、他是管理员、他已被删除，四种输入都收到同一个 1001，这条端点因此不是「某个人是不是管理员」的探针。

显示名的编辑沿用第一部分与 Root 那侧已经批准的规则：登录名自建号起是不可修改的身份锚点（界面也这么讲），而凭据、权限与安全状态（口令、首次改密旗标、账户类型，以及另走一条子资源的状态）都不在这张资料表单里——本体多带任何隐藏字段都打成 1004，UPDATE 语句里那些栏位连出现都没出现。并发保护是同一形的 compare-and-set：依据值已不是数据库现值时整个编辑不发生并回 2013（409），处置与 Root 那边逐字相同（重读服务端现值再决定），所以本步不新增任何机器码。被拒的编辑不留审计，成功的编辑在 Root 域追加一条 `account.profile_update`，操作者是真实发起的那位管理员（账户级身份，不是 Root 也不是 system），前后只有显示名那一栏的旧值与新值；本功能同样不新增任何审计查询入口。

响应只有可展示事实——绝不含口令明文、Argon2id 哈希、会话材料或登录名的内部规范化键。单笔详情也不放活动、资产与消息这三块：那些模块尚未实现，这里不拿空数组或 0 冒充一份查得到的真相。普通账户的删除与改角色同样还没开放——那两样能力今天只有 Root 对管理员的一侧；普通账户的登录停用与恢复见下一节，凭据重置见再下一节。跨来源部署的浏览器要读这条目录得把 `GET` 列进 `cors.allowed_methods`（出厂默认已含 `GET`、`HEAD` 与 `OPTIONS`），要保存资料则还得列入 `PUT`；默认配置未做任何放宽。

## 管理员停用与恢复普通账户登录

`PUT /admin/accounts/{account_id}/status` 停用或恢复一个普通账户的登录，请求本体只有 `status`（`active` 或 `disabled`）与它所依据的 `expected_status` 两个字段。动的是这个账户在整台服务器上的登录能力，不是某一场活动里的玩家限制：停用之后新登录被拒绝，他在每台设备上的现有会话全部被撤销、需要重新登录。活动内的禁言、交易冻结与阵营限制不在这里，也尚未实现。

停用与恢复复用 Root 那侧已经批准的同一条底层机制（状态写入与会话撤销落在同一个事务里），但目标资格独立判定：这条通路只认不携带任何服务器级授予、且未进入删除终态的账户，所以普通管理员动不了另一位管理员，也动不了自己——那三种情形与「查无此人」同样收敛成 1001；配置 Root 不在 `accounts` 表里，结构上就不是一行。授权档位仍是服务器级管理权（没有它回 2011，匿名回 2002），本功能没有把任何活动作用域的角色放大成服务器级停用，也没新增权限档位。

恢复只恢复「重新登录」这一件事：停用期间被撤销的会话保持失效、不会复活（撤销是不可逆的事实，恢复通路一个会话都不碰），尚未完成的首次改密仍然欠着（重新登录后照旧被 2010 挡住），账户的其他限制也不因恢复而解除，已被删除的账户更不能被这样恢复。多重限制从来不是一个 Active 布尔值：`status` 管能不能登录、`must_change_password` 管登录后要不要先改密、`account_type` 讲来源、删除是终态，四件事各由各自的字段与通路回答。

并发与重复由同一形的 compare-and-set 处理：`expected_status` 已不是数据库现值时整个操作不发生——状态没改、会话没撤、审计没记——并回 2014（409）。这句话与 Root 那侧逐字相同，处置也一样：重读目标现状并重新确认，而不是把那颗按钮再点一次，因此本功能不新增任何机器码。SQLite 的单写者把并发串行化，先提交完成的写入是不倒退的事实，停用生效之后的新操作在会话解析边界就被拒。一次成功的变更在 Root 域追加一条 `account.disable` 或 `account.enable`，操作者是真实发起的那位管理员（账户级身份，不是 Root 也不是 system），带前后状态、前后停用时刻与这次撤销的会话数量；被拒的变更不留审计，本功能同样不新增任何审计查询入口。

响应回显变更后的服务端现值与 `revoked_sessions`，绝不含口令、凭据哈希或会话材料；访客账户走同一条通路，因为今日他没有可登录的凭据通路，那次停用通常撤不到会话（数量为 0），而状态落库仍是如实事实。界面在提交前用确认对话框讲完目标、影响范围与「这不是删除」，成功后重新读取目录与详情的真实状态。跨来源部署要保存这条状态得把 `PUT` 列进 `cors.allowed_methods`；出厂默认未做任何放宽。

## 管理员重置普通账户凭据

`PUT /admin/accounts/{account_id}/password` 把某个普通账户的登录口令换成管理员亲自交出的那一个一次性口令，请求本体只有 `password` 一个字段。它复用 Root 重置管理员凭据时建立的那套组件——同一个口令派生实作点、同一条强制替换哈希的仓储写法、同一把定向撤销会话的刀——但操作者、目标类型与管理范围各自校验：授权档位仍是服务器级管理权（没有它回 2011，匿名回 2002），目标范围仍是「不携带任何服务器级授予、且未进入删除终态」那一本目录。所以普通管理员重置不了另一位管理员，也重置不了自己，更碰不到配置 Root——那几种形态与「查无此人」同样收敛成 1001，这条通路不回答「差哪一半」。

一次成功的重置落地三件事，缺一件都是半套：现行口令立即失效（哈希整栏换掉，拿旧明文永远过不了校验）、该账户名下全部现有会话在同一事务里被撤销（`revoked_sessions` 就是这次落库的数量）、首次改密义务被重新设为生效（他下次登录照旧被 2010 挡住，直到自己改掉为止）。交付方案沿用已批准的形态：口令由操作者亲自交、服务器不生成、不在任何响应里回显、不设默认口令，线下的交付管道在协议之外。界面上那串字只活在输入框到请求之间那一小段：发出请求前就清空，之后任何一处都不再显示，也不写进日志、审计、可读偏好或自动复制的剪贴板。

重置不改的事实同样要如实列出：停用状态原样保持（那条 UPDATE 语句里没有 `status` 与 `disabled_at` 两栏，重置之后他仍然登不进去，要恢复登录仍走 `/status` 那条通路），删除终态不能被这样复活，还欠首次改密的人不会因为被重置就免掉义务。待审批与已拒绝的申请不在这本目录的范围里：拿这两种状态的账户标识来重置口令，得到的是与「查无此人」同一句 1001。所以这条通路既不会替谁放行，也碰不到一个还没获准的人——批准不是这三条写入门的任何副作用。

访客账户（`account_type` 为 `guest`）不在这条通路的职责里：他的口令格在数据库里就被冻结成空值，替他写一个进去等于把身份从访客升级成普通账户，而那该由后续一条明确的访客升级通路决定。他因此拿到本功能唯一的新机器码 2018（403）。那句话与 1004「改改口令写法」、1001「换个目标」、2011「换个身分」都不是同一种处置——权限够、写法也没错，要等的是那条通路做出来；而目录按定义把访客列得进去，这里也不讲「他不在这本名册上」。

并发与重复：这条端点刻意没有依据值——操作者拿不出「现行哈希」这类诚实的锚点，任何凑出来的依据值验证的都不是它宣称的东西。SQLite 的单写者把每次重置串行化，每一次成功都是完整的「换哈希＋撤会话＋审计」；重复提交是如实地再做一次重置（再撤一轮可能新签发的会话、再留一笔审计），不是 2014 那种「陈旧依据被拒」。界面据此不在结果不明时自动补发，把那颗按钮再按一次不是重试。一次成功的重置在 Root 域追加一条 `account.password_reset`，操作者是真实发起的那位管理员（账户级身份，不是 Root 也不是 system），带首次改密旗标的前后值与这次撤销的会话数量；被拒的重置不留审计，本功能同样不新增任何审计查询入口。

响应回显重置后的服务端现值与 `revoked_sessions`，绝不回显口令的任何影子（连前缀与长度都不给）。跨来源部署要保存这条凭据得把 `PUT` 列进 `cors.allowed_methods`；出厂默认（`GET`、`HEAD`、`OPTIONS`）未做任何放宽。邮件找回、Root 的网络恢复入口与独立的一次性恢复码体系都不在这里，也不因这一步而存在。

## 待审批的自助注册与本人的状态查询

`self_register_mode` 设为 `approval` 时，`POST /auth/register` 不再创建一个马上能登录的账户，而是收下一份申请。白名单仍然是那三个字段，口令仍然由本人自选，建的仍然是不带任何服务器级授予的普通账户——唯一的差别落在状态上：`pending` 而不是 `active`。稳定的账户标识从提交那一刻就存在，因为统一账户模型下，申请人不该在被人批准的那天变成另一个人。登录名从那一刻起被占用，`must_change_password` 保持关闭：申请人等的是批准，不是一份口令。

“等待”不是半个可用状态，而且这不靠措辞维持。登录判定问的是账户是否 `active`，`pending`（以及 `rejected`）在这一问上与“口令打错”完全同形——同样回 2001，不透露哪个名字存在。会话存储拒绝为非可用账户签发或解析主体，因此没有 Cookie、没有 bearer 秘密，也没有一枚“受限会话”能让待审批的人去碰普通业务。管理员的普通账户目录把这两种状态都排在范围之外，而按标识直打四条通路（详情、改显示名、停用／恢复、重置口令）都得到 1001——“这本名册没这个人”。批准与拒绝在本版本都还没实现：没有 HTTP 入口、没有控制台、也没有任何后门，所以这里没有人能被顺手放行。

申请人若想知道自己的申请怎么样了，可以走 `POST /auth/registration-status`，而答案只有重新证明凭据才拿得到：本体只有 `login_name` 与 `password`，用与登录同一个 Argon2id 凭据校验。成功的回应只给结局（`pending`、`approved` 或 `rejected`）、提交时刻，以及在已有决定时的决定时刻——没有别的。没有审核人是谁、没有拒绝理由、没有排队位次、没有别人的申请，也没有任何会话材料：这条通路不写 `Set-Cookie`、不产生会话行，因此也就不需要一枚要有寿命与撤销边界的“临时状态证明”。它只有 POST，理由相同：秘密不进 URL、不进查询字符串、不被预取、不会被贴进位址栏。查无此名、访客账户与口令不符一律收成同一句 2001，这条通路对“谁的名字存在”不新增信号；限流用的是登录守卫那一份账——多开一扇门不多发一份猜口令的预算。2020（403）是唯一一种必须在“已经证明你是谁”之后才会出现的回答：这个账户存在、你就是它的主人，但它根本没走审批通路，所以处置是“改用登录入口”，而不是“等一等”或“换个名字”。

切换模式只管新的提交，历史申请原地保留。Root 把模式改回 `closed` 或转成 `open`，都不替任何一份已经交上来的申请说话：已落的行仍是 `pending`，仍能被本人查到，既不被放行也不被删除。这也意味着用同一个登录名重复提交会撞上与所有人同一个唯一索引（2019）——待审批与已拒绝的行都继续占用那个名字，被拒绝的人不能拿同一个名字再来一次，别人也拿不走。

迁移 `0009` 给账户状态集合加上 `pending` 与 `rejected`，并新增一栏 `reviewed_at`：状态查询通路就是靠它把“曾被批准、后来被停用”与“从没申请过”分开——决定时刻不可能挂在还在等待或已被拒绝的行上，新建的行也不可能被塞进一个决定时刻。提交仍在 Root 域追加一条 `account.self_register` 审计，操作者是系统主体（匿名请求本来就没有可信主体可记），而记录里的 `status` 就是实际落成的那个状态，所以“我们收了一份申请”与“我们建了一个能登录的人”在审计上可分，而不需要新造一个审计查询入口。跨来源部署要把 `POST` 列进 `cors.allowed_methods` 才存得了这两条路径；出厂默认（`GET`、`HEAD`、`OPTIONS`）一字未动。登录前的入口能力仍然只有两个布尔——模式名字，以及“立刻可用还是要等”这个问题，都由写入本身回答，不靠多一个匿名字段去猜。

## 发布后的使用方式（规划）

- 一人在这台机器（Windows 或 Linux）上托管服务端
- 其他人在同一局域网内用浏览器加入
- 无需第三方注册；数据只保存在主机上

## 界面语言

简体中文、繁体中文（台湾）、English、日本語。

## 从源码构建

Windows 可执行文件的图标是生成的、不纳入版本控制：`cmd/evernight-server/resource_windows_*.syso` 由 `assets/icons/EvernightRealmBackendRounded.ico` 推导。全新克隆的仓库在编译前先执行

    python tools/icons/generate_icons.py

否则生成的可执行文件没有图标，而 `go build` 不会报错。`python tools/icons/generate_icons.py --check` 只核对现状，不写入任何文件；详见 `tools/icons/README.md`。

本项目没有托管 CI：提交前请在本地跑质量入口 `go run ./tools/check`（后端格式、`go vet` 与测试，并连带前端闸门）。
