# 长夜幻境（EvernightRealm）

> 在自己的机器上，为你的小圈子搭建一座私密的虚拟世界——管理活动、扮演角色、交换虚拟资产。

[English](./README.md) · [简体中文](./README.zh-CN.md) · [繁體中文（台灣）](./README.zh-TW.md) · [日本語](./README.ja-JP.md)

## 这是什么？

长夜幻境是一个自主部署、离线优先的平台，面向小规模玩家群体：一起推进沉浸式活动、扮演角色、交易虚拟资产——全部在局域网内完成，不需要公网、云账号或遥测。

## 功能规划（开发中）

- **沉浸式活动**：为你的群体编排场景、阶段与事件
- **角色与身份**：玩家、NPC 与管理员的角色，共处一个私密世界
- **虚拟资产**：物品有真实归属，交易可审计
- **私密聊天**：消息只留在你自己的服务器上
- **离线优先**：一切运行在你自己的机器上，不依赖云服务

## 当前状态

长夜幻境正在积极开发中，尚未发布稳定版本。服务端现在可以构建为**单一可执行文件**：同一个端口同时提供网页界面（目前是可切换语言、可探测服务器连通性的应用壳，业务功能仍在开发）与 API 端点，浏览器直接打开它的地址即可使用，不需要另外部署静态服务。

服务端还提供一个运维命令来产出**一致性备份包**：单档数据库快照（服务运行中即可产出，不是复制活跃的 WAL 主档），连同配置与媒体／文档／上传目录，逐档记录大小与 SHA-256 并附一份清单。与之配套的 `restore` 命令能把这份包还原成一个**全新的空资料目录**：逐档按清单重算校验和，落地前后各读一次快照的数据库事实并与清单对照，**不覆盖任何既有目录**（要覆盖请先自己备份那个目录），拒绝比当前执行档更新的数据库结构版本，并把这次恢复本身写成一条服务端审计记录。备份包还不能加密，旧包也不会自动清理。

一次性 Root 初始化**只有本机命令这一条入口**：

    evernight-server init-root --password-stdin --data-dir <资料目录>

它从标准输入读口令（前两行是口令与确认），把 Argon2id 编码写进该资料目录的 `config.yaml`，不输出任何秘密——不写明文，也不会自动生成或显示一个“出厂口令”。交出服务器最高权限的授权依据是“能在服务器主机上执行命令”，所以这一步不开任何 HTTP 端点、不占端口；CORS、客户端自报的地址、界面上隐藏按钮都不构成授权。服务持有单写入实例锁时、`ER_SECURITY_ROOT_PASSWORD_HASH` 覆盖着配置文件时、或审计表尚未建立时，本命令一律拒绝；写入成功之后也不会再开放第二次——要换口令，走服务内的已认证改密流程（Root 登录后 `POST /auth/password/change`）；只有口令真的遗失了，才用下面那条本机恢复通路。只读的 `evernight-server root-status` 能回答“现在有没有 Root”，它不建立也不改动任何文件，而且只回答这么多：不给出配置路径、哈希或任何引导秘密。成功与拒绝都会写进 Root 审计表，且不记录口令。

Root 口令遗失后的恢复同样只有本机命令这一条入口：

    evernight-server recover-root --password-stdin --confirm --data-dir <资料目录>

它也只从标准输入读新口令（前两行是口令与确认），不接受命令行上的口令值，并且要求服务已经停止：运行中的服务把凭据读在内存里，改配置文件不会让它回头更新，那样只会做出“终端说成功了、旧口令其实还登得进去”这种比拒绝更难查的状态。恢复不问也不验旧口令——能在这台主机上执行命令、能读写那份配置文件，就是这个动作全部的授权依据；因此它也不设后门口令、不产生可下载的恢复档、不开任何 HTTP 端点。成功时配置文件里那份凭据被覆写为新口令的 Argon2id 编码，Root 名下全部会话在同一笔数据库交易里被撤销（下一个请求即被拒），并留下一条 `server.root_recover` 审计记录；普通账户的会话一枚都不动。撤销与审计写不进去时，配置文件会被换回原本那份凭据、回报失败，可用状态与动手前一致（连回滚都失败的双重故障会以 Error 写进运行日志文件，并明确要求人工补记）。`--confirm` 是必须显式给出的旗标：覆盖的代价是旧口令永久失效加上 Root 全部装置登出。配置文件里还没有凭据时本命令拒绝并指向 `init-root`；已有值即使坏到解不开（那种状态下谁都登不进去）也照样能恢复——这正好是 `init-root` 会拒绝的形态，两条路各自只有一种成功形态。

首次启动的界面要如实显示“还没初始化”，服务端因此另外回答一个只读的 `GET /root/init-status`：只有配置文件是否存在、是否已有 Root 凭据、环境变量覆盖是否处于设定状态这三个布尔值，不返回路径、长度或任何凭据片段，也不写数据库、不写审计。它把“有没有”说出来，不说“怎么改”——初始化 Root 仍然只有 `init-root` 这一条在服务器本机上执行的通路（遗失口令后的覆写是上面那条 `recover-root`，两者都不提供服务端网络入口）。

## 登录与管理自己的账户

身份阶段的功能现在已实现、可以使用：登录、查看当前会话、退出、管理自己的设备、修改自己的口令，以及 Root 开设账户与管理管理员目录（见下一节）。限制同样如实写在前面两点。其一，能创建账号的主体仍然只有 Root：Root 凭据本身由服务器本机的 `init-root` 建立，服务器管理员由 `POST /root/admins` 开设，而管理员创建普通账户、自助注册、邀请码与访客账户都尚未实现——所以既不是 Root 也不是管理员的账户目前没有任何途径存在，界面也不提供、不假装提供注册入口。其二，服务端自己不做 TLS 终结：默认监听是 `127.0.0.1:5206` 上的明文 HTTP，只有当请求确实经 TLS 抵达时（也就是你在它前面自行放一层终结 TLS 的反向代理），会话 Cookie 才标 `Secure`、才下发 HSTS；程序不含任何证书处理，HTTPS 是这套程序之外的部署选择。

身份相关的端点没有版本前缀——没有 `/api/v1`：

- `POST /auth/root/login`（只用 Root 口令）与 `POST /auth/login`（登录名加口令）。每次成功都签发全新会话并覆写旧的 Cookie，旧 Cookie 不会被沿用。
- `GET /auth/session`、`POST /auth/logout` 与 `POST /auth/session/rotate`——读取当前会话、撤销恰好这一枚会话（幂等），或换发本会话的秘密。
- `GET /auth/devices` 与 `POST /auth/devices/revoke`——只列举并撤销当前登录主体名下的会话；没有任何请求能指名别人的设备。
- `POST /auth/password/change`——必须在请求中当场交出当前口令；成功后该主体名下全部会话（含这台设备）一起被撤销。

浏览器路径的会话秘密放在 `HttpOnly` Cookie 里；原生客户端从回应标头读出后以 bearer 秘密携带。登录失败反复发生后按“来源地址与登录目标”限流（HTTP 429，附 `Retry-After`），Root 入口同样适用，且被挡的尝试不会指出撞上的是哪个账户。`device_policy` 设为 `single` 或 `limited` 时，会丢掉较旧的会话，或在名额用尽后拒绝新的登录。带有“首次登录必须改密”标记的账户，只放行当前会话查询、退出与改密流程，其余受保护端点一律回 2010，直到改密完成。

两条运维边界维持不变：备份与恢复仍是 `evernight-server` 子命令，没有 HTTP 入口；审计记录只由服务层写入，仍然没有审计查询端点或网页控制台。运行日志按自然日切档，默认不自动删除（`retention_days=0`）：不让日志无限增长是运维者的工作，程序本身不会随时间给日志总量设上限。

## Root 管理管理员目录

Root 的会话是第一批人力操作者进来的地方：`POST /root/admins` 带 `login_name`、`display_name` 与 `password` 开设账户；`GET /root/admins` 是分页的管理员目录（`page`、`page_size` 上限 100、`status` 可按 `all`／`active`／`disabled` 筛选，依授予时刻由新到旧排序，并回显 `page`、`page_size` 与 `total`）；`GET /root/admins/{account_id}` 读取单笔资料；`PUT /root/admins/{account_id}` 编辑它。让新账户成为管理员的是端点本身，不是请求内容：本里没有 `role`、`account_type` 或 `subject_kind` 可以填，多带的字段会被打成 1004。授权的输入是「这次请求解析出的主体就是 Root」，所以普通账户和管理员自己的会话都拿到 2011（403）——管理员既不能创建或管理同级管理员，也不能把自己升格，重新登录一次同样改变不了这件事。目录只列管理员账户；配置 Root 不是其中一行，也永远不会变成一条可被普通账户接口编辑的记录。

初始口令由 Root 亲自交出、且只用一次。它经的是与其他任何凭据同一套 Argon2id 服务，账户带着 `must_change_password` 落库，服务器在任何响应里都不回显该口令，也不存在任何默认口令。于是那个人首次登录拿到的会话，只被允许访问查看当前会话、退出与改密这一组入口——其余受保护端点一律回 2010，直到改密完成——而改密成功会让该账号的所有设备退出。这些规则本就适用于任何账户，本步补上的是那面旗标的来源。

登录名的唯一性走的是与登录通路同一个正规化键（NFKC 加全量大小写折叠），并由账户表上的唯一索引兜住：已被占用的名字回 2012 且不创建任何东西，所以连点两次、或在响应丢失后整笔重试都不会多出第二个账户，而那一句拒绝也不会回显已有账户的任何资料或任何凭据。创建账户、授予 `server_admin`、把 `admin.create` 追加进 Root 审计，全部落在同一个事务里——任何一处失败都不会留下半成品管理员，也不会留下无痕的特权变更——而审计记录里只有身份字段，绝没有口令或其哈希。

编辑的白名单只有一个字段：`display_name`，连同它所依据的现值 `expected_display_name` 一起提交。状态、凭据、首次改密旗标与账户类型不在这条通路之内，UPDATE 语句也只碰这一栏——「保存普通资料顺带覆盖隐藏字段」在语句形状上就不存在。若存储的值在页面打开之后已被改动，整个编辑以 2013（409）被拒绝且什么都不写入，这与改密使用的同一套 compare-and-set 保护同源。标识格式不对、账户不在目录、账户确实不存在，都收到同一个 1001，这个端点因此不是枚举探针。响应只含可展示事实——绝不带密码哈希、会话秘密、恢复码或任何配置——Root 的每次成功编辑都会追加一条 `admin.profile_update` 审计，仅带显示名的前后值；被拒的编辑不写任何记录。

另有两个响应字段按「只增不删」的演进规则补上：登录与查看当前会话的回应现在带 `roles`，内容是服务端为该主体现读到的授予（没有授予时字段缺席），客户端据此决定载入哪些入口。它本身不授予任何东西——每个端点仍在每次请求上重读可信主体。


若部署要让组态白名单里的跨源浏览器调用这些端点，`cors.allowed_methods` 必须把 `PUT` 与 `POST` 一起列入——来源白名单始终是组态决定，本节不为此放宽任何边界。

## 发布后的使用方式（规划）

- 一人在这台机器（Windows 或 Linux）上托管服务端
- 其他人在同一局域网内用浏览器加入
- 无需第三方注册；数据只保存在主机上

## 从源码构建

Windows 可执行文件的图标是生成的、不纳入版本控制：`cmd/evernight-server/resource_windows_*.syso` 由 `assets/icons/EvernightRealmBackendRounded.ico` 推导。全新克隆的仓库在编译前先执行

    python tools/icons/generate_icons.py

否则生成的可执行文件没有图标，而 `go build` 不会报错。`python tools/icons/generate_icons.py --check` 只核对现状，不写入任何文件；详见 `tools/icons/README.md`。

本项目没有托管 CI：提交前请在本地跑质量入口 `go run ./tools/check`（后端格式、`go vet` 与测试，并连带前端闸门）。
